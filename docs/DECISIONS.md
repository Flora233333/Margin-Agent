### D15 · 2026-10-04 · 向量直接存 PostgreSQL（pgvector），精确检索，文档向量沿用 RC6-C 索引 v2

- **决定**：M1 起向量存在 PG 的 `block_vectors` 表（pgvector 扩展，`vector(1024)`），不再用 Chroma 做运行时检索。
  文档向量从 RC6-C 当前用的索引 `rc6-local-qwen3emb06b-q8_0-v2`（RL 环境服务和 E80 都用它，服务器 GPU 建库）
  原样导入（`scripts/import_vectors.py`）；查询向量由本机 CPU 上的 llama.cpp 服务实时计算。不建 HNSW 索引，用精确检索。
- **为什么**：
  - 少维护一个存储；向量和业务数据在同一个库里，以后能用 SQL 一边按条件过滤一边做相似度检索，也支持文档增量入库。
  - 精确检索：1.76 万条顺序扫描约 45ms，相对秒级的模型调用可以忽略；没有近似误差，也没有参数要调。
    pgvector 的 HNSW 有个坑：`ef_search` 默认 40，一次最多只返回约 40 条，而向量路一次要 256 条。
- **验证（2026-10-04）**：
  - 本机 CPU 重算 20 个文档块（含最长 5 块，最长 9,606 字）与 v2 存的向量比，余弦最低 0.99947、平均 0.99969。
  - 导入 PG 后读回，与 Chroma 里的 float32 逐位相同（最大误差 0）。
  - E80 的 80 个问题：`search_docs` 最终给模型的 8 个文档（含顺序和最佳块），pgvector 与 Chroma 完全相同 76/80，
    文档集合相同 77/80，文档重合 99.4%。差异来自 Chroma 本身是近似检索（HNSW）：
    Chroma 与精确结果相比，前 256 块只重合 96.4%。
- **代价**：检索结果和 RC6-C（Chroma 近似检索）有约 5% 的题不完全一样；对自训模型的影响要在 E80 上实测。
- **替代**：继续用 Chroma（与 RC6-C 完全一致，但多一套存储，无法与业务数据联查）；
  pgvector HNSW `ef_search=300`（前 10 与精确完全一致，但多一个要调的参数，数据量小时没有速度优势）。

### D17 · 2026-10-05 · 租约方案修订：接管从断点继续、超时预算 + 监督者、卡死进程直接结束

- **决定**：见 PLAN §5.2（完整推导、时间线和 10 条问答见 `review/03_架构对齐与租约方案.md` 第四版）。
  核心四条：① 接管与重试分开，接管从最后一个已提交步骤之后继续（每步存断点）；② 每类操作有超时预算，
  心跳线程兼任监督者，“举旗后 60 秒无回应”判定卡死并 `os._exit` 结束子进程；③ 任何写入都带 epoch 条件，
  被取代的 worker 立即停止、释放资源；④ Celery `acks_late=True` + `prefetch_multiplier=1`，队列只是唤醒信号。
- **为什么**：原方案的心跳只证明进程活着、不证明任务在推进（主线程卡住时租约永不过期）；接管后从头执行浪费
  每题约 36 万输入 token；没有 Inspector 时崩溃的任务永远没人接手；早确认 + 预取会让空闲 worker 拿不到任务。
- **依据**：E80 实测 2,881 次模型调用最长 120.6 秒、单题最长 687 秒，超时预算不会误杀正常请求。
  十个工具都是只读的，被打断的一轮整轮重做没有副作用。
- **代价**：Harness 要支持断点恢复（`run_episode` 增加 checkpoint / on_step / should_stop 参数），
  断点每步覆盖写一次 JSONB；`os._exit` 不执行 finally，资源靠操作系统、PG 断连回滚和 Redis 名额过期兜底。
- **作者补充**：只结束监督者线程也能保证正确性（租约过期后被接管、旧主线程写入被 epoch 拒绝），
  结束整个子进程只是让槽位和内存立刻回收，不必等 25 分钟硬时限。

### D18 · 2026-10-05 · M1 实现时的取舍

- **新依赖**：pydantic-settings（配置集中、缺项启动即报错、报错不带输入值以免密钥进日志）；
  SQLAlchemy 2（ORM + 连接池）+ Alembic（表结构版本化，`alembic check` 能发现模型与迁移不一致）；
  FastAPI + uvicorn（接口与自动文档）；Celery[redis]（后台任务队列）。都写在 pyproject，镜像和 CI 用同一份。
- **M1 加入最小巡检**：dispatcher 每 15 秒把租约过期的 running attempt 判为失败并 epoch+1。
  原因：Celery 硬时限只杀进程、不改库，没有巡检时崩溃的任务会永远停在 running。M4 把“判失败”改成“接管”。
  实测：执行中途 `docker compose kill worker`，86 秒后被判为 `lease_expired`，已完成的 6 步保留。
- **推迟到用到时再做**：`attempts.checkpoint` 和 Harness 的 checkpoint / should_stop 参数推迟到 M4（接管时才读断点，
  先写不读的数据没有测试能保护）；`llm_calls` 表推迟到 M3 开发者视图，M1 的耗时和 token 记在 steps 上。
  以后加列 / 加表正好用第二个迁移演示 Alembic 的增量升级。
- **模型调用超时**：连接 10s、等数据 60s、总时长 180s。httpx 的读超时只有一个值，区分不了“首块”和“块间”，
  所以块间是 60s 而不是方案里的 30s；worker 一律走流式，等数据的超时才对每一块生效。
- **事件序号**：由 `runs.last_seq` 行锁分配，而不是全表自增 id：自增 id 的分配顺序不等于提交顺序，
  按 “id 大于上次” 读会永久漏掉后提交的小 id。
- **错误信息**：写进库、展示给用户的只有异常类型或 HTTP 状态码（如 `llm_http_502`），因为 httpx 的报错文本带网关地址。
- **实测**：worker 容器在 1 个子进程加载语料 + BM25 后约 1.2GB；4 个子进程都加载后估计约 4.5GB（未满载实测，本机 23GB）。
  容器内向量查询 47ms；Windows 经 localhost 连 WSL 时发送大于约 20KB 的请求会固定多约 45ms（转发层的问题，
  与 PG 无关），所以本机跑脚本时向量查询约 92ms。

### D19 · 2026-10-06 · 任务队列换成 RabbitMQ；巡检增加消息丢失对账（M1.5）

- **起因（M1 review）**：dispatcher 投递并标记 sent 后，如果消息在 Redis 里丢失（compose 里的 Redis 没挂数据卷、
  没开 AOF，重启即清空），attempt 会永远停在 pending；M1 的巡检只处理 running，重新生成也会因为“有 pending 的执行”返回 409。
- **决定**：
  1. Celery 的消息中转站从 Redis 换成 RabbitMQ：原生消息确认（worker 断开时消息立即回队列，不用等 2 小时的可见性超时）、
     队列和消息持久化、发送确认（收到确认才标记 sent）、自带管理界面。Redis 保留实时通知、限流、缓存。
  2. 巡检增加对账 `requeue_lost`：用“水位线（比我晚投递的已被领取）/ 队列为空 / 30 分钟兜底”判定消息丢失，
     复用同一行 outbox 补发，最多 3 次，之后把 attempt 判为 `delivery_lost` 失败。细节见 PLAN §5.7。
- **为什么两件都做**：RabbitMQ 让消息很少丢，但不能保证不丢（队列被清空、磁盘损坏）；PG 才是唯一的裁判，
  对账不管用哪种队列都需要。对账只用超时会在积压时误判，只看“队列为空”又会在持续有流量时一直等，所以以水位线为主。
- **代价**：多运维一个服务（启动、监控、数据卷、密码），集成测试环境也要能起它；`consumer_timeout` 必须调到
  大于 Celery 硬时限（定为 1 小时），否则超时会关闭整个通道、让所有在执行的任务的消息回到队列。
- **替代**：
  - 只修对账、继续用 Redis（再挂数据卷、开 AOF）：也能用，但 Redis 的确认机制是模拟的；作者希望用上标准的消息队列。
  - 把 PG 当队列（SKIP LOCKED + LISTEN / NOTIFY）：不需要 Outbox，也不存在丢消息，但 PG 压力和连接数上升，
    并且失去 Celery 的 worker 管理。当前规模其实够用，作为面试时的对比方案。
  - Kafka / RocketMQ：前者是事件流，不适合少量长任务的确认与取消（D3）；后者 Python 客户端弱。
- **同时**：dispatcher 从每秒轮询改为 PG LISTEN / NOTIFY 唤醒（写 outbox 的事务里 NOTIFY，提交后才发出），
  保留最长 10 秒的兜底扫描处理退避重试和错过的通知（通知不持久）。SSE 的“有新事件”通知是否也用它，M2 再定（PLAN §5.4）。
- **是否需要重新评测**：不需要，不涉及模型接口和检索。

### D20 · 2026-10-06 · M2 的“有新事件”通知用 PG LISTEN / NOTIFY，不用 Redis

- **决定**：SSE 不再每秒查 events 表。`add_event` 在写事件的同一事务里 `NOTIFY run_events, '<run_id>'`；
  每个 API 进程只开一条专用的 LISTEN 连接，收到后在内存里转给关注该 run 的 SSE 连接，再按 seq 查库；保留低频兜底查询。
- **为什么**：事件本来就存在 PG，NOTIFY 随事务提交才发出，天然不会出现“通知到了、事件还没提交”；
  和 M1.5 里 dispatcher 的唤醒用同一套机制，少一种做法要维护。
- **替代**：Redis 通知（worker 提交事务后再 publish）——要自己保证“先提交后通知”，且多一个依赖点；没选。
- **不变**：模型逐字输出的思考片段仍走 Redis pub/sub（不落库、量大，NOTIFY 单条上限 8KB 且会经过 PG）。
- **是否需要重新评测**：不需要。

### D21 · 2026-10-06 · M1.5 实现时的取舍（待作者 review 确认）

执行时作者不在场，按“选最稳妥的方案继续、记进 STATUS”处理；作者确认后本条即为定稿。细节和实测见
`review/02_代码导读/M1.5_队列与对账.md`。

- **发送确认开在 dispatcher 自己的 Celery 实例上**（`dispatcher.make_publisher`），不在 worker.py 的 `celery_app` 上：
  只有 dispatcher 发任务消息；它的连接还要加 socket 读写超时，不想影响 worker 的连接。两处都用默认的任务队列 `celery`。
- **发送要有超时，且关掉 Celery 内部重试**：实测（celery 5.6.3 / RabbitMQ 4.3.6）连不上、拒收、迟迟不确认三种失败都抛
  `kombu.exceptions.OperationalError`，所以 except 范围不变；但 RabbitMQ 内存告警时，只设 `confirm_timeout` 会让
  dispatcher 永远卡在关闭通道，加 `read_timeout` / `write_timeout` 10 秒后约 27 秒抛出。Celery 默认的 3 次立即重试会再放大 4 倍，
  dispatcher 已有退避，所以 `task_publish_retry=False`。代价：RabbitMQ 重启后第一条投递失败一次、2 秒后重发（演练已见）。
- **dispatcher 的时间用 `clock_timestamp()`**：`now()` 是事务开始时间，发送耗时超过退避时间时退避失效；同一批的 `sent_at`
  完全相同会让水位线分不出先后。是 M1 就有的问题，被新的退避测试暴露。
- **水位线的“已被领取”用 `attempts.started_at IS NOT NULL`**（PLAN §5.7 原写 `status <> 'pending'`）：判为
  `delivery_lost` 的 attempt 不是 pending 但从未被领取，按状态算会抬高水位线、误判前面正常排队的任务。
- **读队列状态时队列不存在当作“没有消费者”**：否则 `NotFound` 会让 dispatcher 每 15 秒崩溃一次。
- **worker 的远程控制 / 事件队列改为独占**（`control_queue_exclusive`、`event_queue_exclusive`）：RabbitMQ 4 禁止
  不持久又不独占的队列，worker 启动即报错。
- **注意**：py-amqp 的 `read_timeout` 按 Linux 格式设置 `SO_RCVTIMEO`，在 Windows 上会被当成毫秒。
  dispatcher 只跑在容器里不受影响；在 Windows 上做 RabbitMQ 实验时数字不可信。
- **是否需要重新评测**：不需要，不涉及模型接口和检索。

### D23 · 2026-10-06 · 回答形态（M2.5）：先 finalize 再撰写，引用只提醒一次，实验只用 DeepSeek

方案细节见 PLAN §5.8。

- **决定**：
  - 交答案仍用原来的 `finalize`（短答案，供评测打分）；Harness 结束后，同一个模型再用一份独立提示词把证据写成带 [n] 的回答（“撰写”）。
    答题前也用同一个模型做一次“理解题目”（标题、结论说明、答案格式），用户不再手选格式、不再填选项。
  - 产品模式下没有引用就交答案时，`finalize` 提醒一次（工具错误 `citation_required`），第二次照收；
    没有引用的回答在页面上标出“本回答没有引用原文”。评测回放和自训模型对照实验不开这条。
  - 实验（E1–E5）只用学校网关的 DeepSeek；GLM 不再单独跑；自训模型等实验室服务器空出来后按同样的脚本复测。
- **为什么**：
  - 一次交齐（`finalize` 直接带回答正文）更好，但现在的模型没为此训练过，硬改工具说明会改变模型行为；先用“撰写”拿到产品效果，
    E5 做一次交齐的对照，为后续专项 RL 定目标。用 RL 而不是 SFT，是担心 SFT 让自训模型忘掉已有的答题能力（灾难性遗忘）。
  - 硬性要求引用的话，模型确实找不到可引用原文时会连续被拒、触发 `repeated_tool_error` 停止，用户什么都看不到；
    提醒一次既能把“忘了引用”的情况救回来，又不会卡死。
  - 只用一个模型：额外的两次调用不维护第二个模型，配额、并发都按同一个模型算。
- **替代**：硬性要求至少一处引用（没选，理由同上）；`finalize` 改参数直接带回答（等 RL 之后再比较）；用小模型做理解题目（没选，多维护一个模型）。
- **是否需要重新评测**：系统提示词和工具说明不变。产品模式多一种工具错误，E3 对比开 / 关；评测回放不开，不影响已有的 E80 结果。
- **实验结果（2026-10-06，作者确认）**：E2 撰写回答达标（非法 [n] 0、未核实数字 0、中位数 14.7 秒）；E3 提醒开 / 关准确率相同；
  E4 格式判断约 89/90。按结果调整两处：撰写回答的输入不放完整思考；理解题目和 Harness 并行。每道题固定多两次模型调用，
  token 不到 Harness 的 1%，代价主要是结束后多约 15 秒的撰写（流式显示）。细节见 PLAN §5.8“实验结果”。

### D25 · 2026-10-06 · 理解题目猜的答案格式只“软校验”，和给定的格式分开存

- **问题（run 66）**：“金融机构对存量客户的受益所有人识别有什么时间要求？”被理解题目猜成日期。主流程模型看不到格式，

- **决定**：
  - 猜的格式只用来规范化和显示：产品里的题交的答案按猜的格式规范化不了，就按文本收下（结果标 `answer_format_fallback`），不退回；

- **没做**：数字核对仍把提交的答案算作出处（不算的话，模型心算的单位换算也会被标出来，误报多）。
