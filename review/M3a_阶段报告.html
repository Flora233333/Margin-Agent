一、为什么做

M3 要做配额、按用户轮流投递（M3b），前提是系统知道“这个请求是谁发的”。M3a 先把这件事做好，并保证一个人看不到另一个人的题。

M3a 之前

打开网页，不用登录
↓
API 把每个请求都当成 dev（owner_id = 1 写死）
↓
谁打开网页都能看到、重新生成所有题；查询里虽然带了 owner_id，但永远是 1

M3a 之后

没登录 → 跳登录页（登录后回到原来的页面）
↓
登录成功：服务端记一行 session，浏览器拿到 HttpOnly cookie
↓
每个请求从 cookie 查出当前用户，查询带他的 owner_id：别人的题 404，和不存在一样
↓
退出 / 过期 / 改密码 → 服务端那一行删掉或失效，cookie 立刻没用

账号用脚本建（不做注册页，D30）。为什么用服务端 session 而不用 JWT（PLAN §5.5 已定）：浏览器的 EventSource 不能带自定义请求头， 只能靠 cookie；服务端存一行，退出时删掉就立刻作废，JWT 做不到。

cookie 每个属性防什么

属性作用
HttpOnly页面脚本读不到（document.cookie 是空的）。万一页面被注入脚本，偷不走令牌。
SameSite=Lax别的网站发来的 POST 不带这个 cookie（A4 用真浏览器验证过）。从别处点链接进来（GET）仍然带，所以不影响正常打开。
Max-Age=6048007 天。服务端那边也记着同样的到期时间，用着就顺延。
Secure只走 https。本地是 http 所以默认不加，上线（M6）时配置打开。

为什么库里只存令牌的哈希

库要是泄露（备份文件被拿走），拿到的只是哈希，算不回令牌，冒充不了任何人。 令牌本身是 32 字节随机数，不像密码那样有“常用密码表”可以猜，所以用普通的 SHA-256 就够，不用 argon2（每个请求都要查，必须快）。

三道防线

PG 每个查询带 owner_id（M1 起就有，M3a 让它变成真实的人）
API 改数据的请求检查 Origin + cookie 的 SameSite
Redis 登录按“用户名 + IP”限次数

A1 · B 打不开 A 的题

A = test_a（run 196 是他的），B = test_b。curl 各自登录拿 cookie，再分别访问：

请求B（test_b）A（test_a，对照）
GET /runs[][196]
GET /runs/196404200
GET /runs/196/events404200
POST /runs/196/regenerate（带正确 Origin）404 {"detail":"run 不存在"}没试（会真的再跑一次）
GET /runs/999999（不存在的题）404 {"detail":"run 不存在"}

别人的题和不存在的题返回一字不差：B 没法靠响应区分“有这道题但不是我的”和“没有这道题”，也就没法挨个试出别人有哪些题。

A2 · 退出后用旧 cookie 
登录 → 从 cookie 文件里抄下令牌；库里按令牌的 SHA-256 能查到这一行；GET /auth/me 200
POST /auth/logout → 204，set-cookie: margin_session=""; …; Max-Age=0     # 让浏览器删 cookie
库里这一行没了
手动带上抄下的旧令牌：GET /auth/me 401 · GET /runs 401 · POST /runs 401

要点：退出删的是服务端那一行。浏览器删不删 cookie 无所谓——就算有人事先复制了 cookie，也立刻作废。这是选服务端 session 而不是 JWT 的原因。

A3 · session 改成过期再操作页面

浏览器 test_a 打开 /runs/196；psql 执行 UPDATE sessions SET expires_at = now() - interval '1 second' WHERE user_id = 3（2 行）；在页面上点“重新生成”。

库里：被改过期的 session 5、8 在重新登录时被删掉，只剩新的 9；run 196 仍是 2 次执行（401 的那次重新生成没有建出执行）。手动改过期的数据因此不用另外还原。

A4 · 别的网站发来的提交

test_a 的 cookie 有效，用 curl POST /runs，只改 Origin 头，前后数 test_a 有几道题：

Origin结果
https://evil.example403 “请求来源不在允许列表里”
不带（curl 默认）403（取舍 33）
http://localhost:5174（端口不同）403
http://127.0.0.1:5173（同一台机器换个写法）403
http://localhost:5173（对照）202，建出 run 197

真浏览器里试一次：在 127.0.0.1:8766 放一个“别的网站”的页面，打开就自动提交表单到 http://localhost:5173/api/runs。 浏览器发出的请求带 origin: http://127.0.0.1:8766，API 返回 403，库里没有这道题。

再证明 SameSite：本机 localhost:8767 起一个只回显“收到了哪些 cookie”的小服务（cookie 只认域名不认端口，localhost 的 cookie 会发给它）。 从“别的网站”提交表单过去：收到 无；从本站页面提交过去：收到 ['margin_session']。

跨站 POST 浏览器根本不带登录 cookie（第一道防线）；就算哪天带了（老浏览器、配置改了），Origin 检查也会拒绝（第二道防线）。

六、发现并修掉的问题

实验 A1～A6 都一次通过，没有发现代码问题。开发途中和收尾时发现、当场修掉的：

在哪问题怎么发现、怎么修
M3a-4a 测试限流的滑动窗口测试偶尔失败 收尾前重跑集成测试时失败一次。测试用 Windows 的时钟睡，窗口按 Redis 的时钟算，而本机 Redis 在 WSL 虚拟机里—— 量了 5 次，Windows 睡 2.1 秒，Redis 只过约 2.02 秒，慢约 4%。原来那一步离窗口边界只留 0.1 秒，偶尔还没到。 改成每个判断离边界留 0.4 秒以上，连跑 5 次通过。只改测试：限流本身只认 Redis 一个时钟，不受影响。 CI 里测试和 Redis 在同一台机器、同一个时钟，所以 M3a-4 推送时没暴露。
M3a-5 前端从没登录过的人也看到“登录已过期” 浏览器自查时发现。第一版用字符串 'checking' 表示“正在问服务器我是谁”，判断“之前登录着”用的是 typeof who === 'string'，把 'checking' 也算进去了。 改成用 undefined 表示正在问；端到端测试“没登录打开一道题”专门检查不出现“过期”。
M3a-0 设计稿所有提示同时显示 截图自查时发现：提示元素自己设了 display: flex，压过了 hidden 属性。加 [hidden] { display: none !important }。
M3a-6 测试lint 误报 Playwright 夹具的第二个参数文档里叫 use，lint 把它当成 React 的 Hook 报错。改名 provide。
实验操作中出的一次事故（不是代码问题，已处理）：做 A1 时，我把 curl --noproxy * -s 写进了一个没加引号的 shell 变量， * 被展开成当前目录的文件名（如 README.md、AGENTS.md），curl 把它们当成了要访问的网址， 并经本机的 HTTP 代理把两次登录请求（请求体里有 test_a、test_b 的临时密码）发到了这些同名的外部网站。
当场处理：立刻用脚本给 test_a、test_b 换了新密码（同时让旧 session 全部下线），删掉相关 cookie 文件；之后 curl 一律写成带引号的函数。 泄露的只是两个实验账号的随机临时密码，账号只在本机、本次实验存在，现已删除，没有影响。.env 里的密钥没有出现在任何命令里。

七、看到了但按设计不改的

  • 已经开着的事件流不会因为过期被掐断：session 只在连上时检查一次，连着的流会推到这次执行结束。断线重连时才会发现过期、跳登录页 （端到端测试“执行中登录过期”测的就是这条路径）。最多多看一道题的剩余过程，内容本来就是他自己的，没必要每条事件都查一次库。
  • 开发环境里所有人的 IP 都一样（Vite 转发、Docker 网关 172.18.0.1），限流靠键里的用户名区分人。上线放 Nginx 后再按真实 IP（取舍 36）。
  • 手机宽度没有“退出”：侧栏在这个宽度本来就整个藏掉（取舍 40）。
