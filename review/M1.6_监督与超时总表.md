## 1. 一句话

**PG 是唯一的裁判。** RabbitMQ 只负责“叫醒 worker”，该不该执行、执行权归谁，全看 PG 里带条件的 UPDATE。
监督只有两类：

- **执行中的题**（attempt = running）：靠**租约**。worker 每 15 秒续一次，90 秒没续就判失败。
- **发出去还没人领的题**（outbox = sent、attempt = pending）：靠**重发**。1 分钟还没 claim 就重发，最多 3 次。

正常情况下“没人领”的时间只有几毫秒（实测 0～54 毫秒）：先 claim 再加载，而且只在 worker 有空位时才发。
所以 1 分钟没人领，就只能是消息丢了。

---

## 2. 一道题的四个阶段，谁在盯

| 阶段 | PG 里的样子 | 正常停留多久 | 谁在盯 | 判定出事的条件 | 结果 |
|---|---|---|---|---|---|
| ① 排队 | outbox = pending | 等空位：积压多久就停多久 | dispatcher 投递 | 不判出事。只有发送失败才退避 | 发出去 → ② |
| ② 已发出，没人领 | outbox = sent，attempt = pending | 几毫秒 | dispatcher 巡检（10 秒） | 发出 1 / 2 / 4 分钟还没 claim，且队列里没有排队的消息 | 重发；3 次后再等 8 分钟 → `delivery_lost` |
| ③ 执行中 | attempt = running | 30 秒到几分钟 | 续租线程（15 秒）、dispatcher 巡检（10 秒）、worker 主进程（25 分钟） | 90 秒没续租；单个任务超过 25 分钟 | `lease_expired`；超时先杀子进程，再走租约过期 |
| ④ 结束 | completed / failed | 永久 | — | — | 用户可以重新生成（执行中点返回 409） |

## 3. 三个循环

### 3.1 dispatcher：一个进程、一个循环、两件事

```text
while True:
    if 距上次巡检 >= 10 秒:                       # 巡检：每 10 秒，先于投递
        queue = read_queue_state()               #   问 RabbitMQ：就绪几条、几个消费者
        expire_leases()                          #   ③ 的租约过期 → lease_expired
        resend_lost(queue)                       #   ② 的重发
    dispatch_once(容量 = 消费者数 × 子进程数)       # 投递：每次醒来都做，有空位才发
    睡到：有 NOTIFY / 最早的退避到期 / 该巡检了，哪个先到算哪个（最多 10 秒；没有空位时直接睡到巡检）
```

**投递 `dispatch_once`**

1. 算空位：`空位 = 消费者数 × MARGIN_WORKER_CONCURRENCY − 在途数`。
   - 在途数 = attempt 是 running 的条数 + attempt 是 pending 且 outbox 是 sent 的条数；
   - 消费者数用最近一次巡检读到的值；还没读到、或者读不到时，这一轮不发。
2. 按 `outbox.id` 先进先出，取最多“空位”条到期的 pending 行（`FOR UPDATE SKIP LOCKED`）。
3. 逐条 publish，等 RabbitMQ 回“存好了”：
   - 成功：outbox 标 sent，`sent_at = clock_timestamp()`；
   - 失败（抛 `OperationalError`）：`tries + 1`，`next_attempt_at` 推后 2、4、8……最多 60 秒；第一条失败就停下这一轮。

**谁叫醒 dispatcher**

- 提交、重新生成：API 在同一事务里 `NOTIFY outbox`；
- 一道题结束、空出位子：`finish` / `fail` / `expire_leases` / `_fail_undelivered` 同一事务里 `NOTIFY outbox`；
- 重发：不发通知。改回 pending 的行立刻到期，`seconds_until_due` 返回 0，循环不睡。

**巡检里的重发 `resend_lost`**

```text
不判（10 秒后再看）：读不到队列状态 / 消费者数 = 0 / 就绪数 > 0
候选：outbox = sent，attempt = pending，sent_at < now() − 1 分钟 × 2^redeliveries
    redeliveries < 3  → outbox 改回 pending，redeliveries + 1（由投递去发，sent_at 随之更新）
    redeliveries = 3  → attempt 判 delivery_lost（epoch + 1，run 失败，写 attempt_failed）
就绪数连续 2 分钟 > 0 → warning 日志，每段积压记一次（说明子进程数配错、RabbitMQ 刚重启或 worker 卡住）
```

时间线：第一次发出后约 1 分钟重发一次，约 3 分钟第二次，约 7 分钟第三次，约 15 分钟判失败。
再加上巡检间隔，最多晚 10 秒。实测（V4）：消息丢了以后，发出后 68 秒重发，1 毫秒后被 claim。

消费者数是最近一次巡检读的，最多旧 10 秒：worker 刚停的 10 秒内提交的题仍会被发出、在 RabbitMQ 里等，
不丢、不重发（就绪数不为 0），worker 回来后照常执行（实测 V5）。

### 3.2 worker：主进程管消息，子进程管执行

**worker 主进程**（唯一连 RabbitMQ 的进程）

- 开工时 `basic.qos`：未确认最多 4 条（`worker_prefetch_multiplier=1` × 4 个子进程）。
  和 RabbitMQ 断线重连时不临时调低（`worker_enable_prefetch_count_reduction=False`）：Celery 5.6.3 默认会调到 3、
  之后不真正调回，worker 永久少拿一条（实验 V8 发现，M1.6-7a 修）。
- `task_acks_late=True`：子进程做完才替它 ack。子进程死了、超时被杀，也照样 ack（Celery 默认）。
- 硬时限 25 分钟：杀掉子进程，ack，再补一个新的子进程。
- AMQP 心跳：Celery 提 120 秒，RabbitMQ 提 60 秒，取较小值 60 秒。实测（V4）worker 主进程冻住后约 2.6 分钟才被 RabbitMQ 断开；
  这期间它手上的消息满足重发条件（消费者 1、就绪 0），会多重发一次，多出的消息由 claim 挡住。

**worker 子进程**（一道题）：先 claim 再加载

```text
claim（UPDATE … WHERE status='pending'，epoch + 1，lease_until = now + 90 秒）
  └─ 0 行 → 跳过（重复投递或已结束），任务正常返回，主进程 ack
with 续租线程（每 15 秒：lease_until = now + 90 秒；PG 连不上就下一轮再试）:
    理解题目（另一个线程，第一次执行才做，和加载并行）
    加载语料（第一次约 2 秒；缓存丢失约 100 秒，这期间照常续租）
    Harness：每一步 commit_step，先 _fence（WHERE epoch = 我的 AND status = 'running'）
        └─ 0 行 → LeaseLost，事务回滚，停止执行
    撰写回答
    finish（同样先 _fence）
出错（网关报错、超时、加载失败）→ fail → attempt 判失败
```

实测（V2）：BM25 缓存丢失、重建约 100 秒，消息发出 54 毫秒后 claim，重建期间租约剩余 76～89 秒，不触发重发。

### 3.3 API：SSE 推流（M2）

- 每个 API 进程一条 LISTEN 连接（`event_hub`），收到“run 5 有新事件”，叫醒正在看 run 5 的 SSE 连接；断开后 2 秒重连。
- SSE 平时等通知；10 秒没动静就查一次库，同时发一个 `ping`。
- 前端 25 秒什么都没收到，就认定连接已断，用 `?after=最后的 seq` 重连；浏览器放弃重连时，前端自己隔 2 秒重建。
- 实时片段走 Redis，操作超时 1 秒。第一次发失败，这次执行就不再发片段，题目照常做。

| 参数 | 值 | 管什么 | 位置 |

| **dispatcher** | | | |
| 兜底扫描 + 巡检 `TICK_SECONDS` | 10 秒（M1.6 合并了原来的 10 秒和 15 秒） | 通知丢了最多晚 10 秒投递；出事最多晚 10 秒发现 | dispatcher.py |

| **worker / RabbitMQ** | | | |
| Celery 硬时限 | 25 分钟 | 子进程卡死 | worker.py |
| 预取数 | 4（= 子进程数），重连后不调低 | 每个子进程手上只有正在执行的一条 | worker.py |

| 确认期限 `consumer_timeout` | **不配**（M1.6 删除） | RabbitMQ 4.3 的经典队列不检查它，配了也不生效 | 原 deploy/rabbitmq/margin.conf |
| **模型调用** | | | |
| 连接 | 10 秒 | 网关连不上 | llm/client.py |

| **其他** | | | |
| SQL 语句 | 30 秒 | 任何一条 SQL 卡住，PG 主动取消 | db.py |

| event_hub 重连 | 2 秒 | API 的 LISTEN 连接断了 | event_hub.py |
| Redis 操作 | 1 秒 | Redis 卡住，不能拖慢模型输出 | live.py |
| 前端无数据判断断线 | 25 秒 | 连接“半死”（进程没了，代理却没关浏览器那一侧） | useRunStream.ts |

**为什么这样排：**

- 模型调用 180 秒 < 硬时限 25 分钟：先触发的是里层的超时，一次调用卡住只让这道题失败，不用杀进程。
- 续租 15 秒 < 租约 90 秒：PG 偶尔一两次连不上，不会丢租约。
- 重发第一次 1 分钟：先 claim 再加载以后，正常的“发出 → claim”只有几毫秒，1 分钟足够宽裕。

## 5. 故障速查

“多久发现”从出事那一刻算起。

| # | 出了什么事 | 谁发现 | 多久 | attempt 最后 | 用户看到 |
|---|---|---|---|---|---|
| 1 | 投递时 RabbitMQ 连不上 | dispatcher：publish 抛异常 | 立刻 | 仍是 pending，outbox 退避重试，恢复后发出 | 排队中，恢复后正常 |
| 2 | RabbitMQ 内存 / 磁盘告警 | 同上，一条约 27 秒才报错 | 约 27 秒 | 同上；“失败”的消息解除后可能仍被收下，多出的由 claim 挡住（实测 V7：5 条消息、执行 1 次） | 同上 |
| 3 | 有人清空了队列，消息没了 | dispatcher 巡检：发出 1 分钟没 claim | 1 分钟（实测 68 秒） | 重发后正常执行 | 多等约 1 分钟 |
| 4 | 子进程收到消息、claim 之前死了（几毫秒的窗口） | 同上 | 1 分钟 | 同上 | 同上 |
| 5 | 子进程 claim 之后死了（加载或执行中，例如内存不够） | dispatcher 巡检：租约过期 | 75～100 秒 | `lease_expired` | “执行中断”，已完成的步骤保留，可重新生成 |
| 6 | 子进程主线程卡住，续租线程还活着 | worker 主进程：硬时限 | 25 分钟 + 租约 90 秒 | `lease_expired` | 同上（M4 改进） |
| 7 | 整个 worker 容器被 kill | RabbitMQ：TCP 连接断了 | 立刻 | 未确认的消息放回队列。已 claim 的：新 worker claim 失败、跳过，75～100 秒后 `lease_expired`（实测 96.6 秒，排队的题同一秒发出） | 同 5 |
| 8 | worker 主进程卡死、网络断 | RabbitMQ：心跳 | 约 1～3 分钟（实测 2.6 分钟） | 同 7；断开前可能多重发一次，由 claim 挡住 | 同 5 |
| 9 | worker 到 PG 的网络断了 | 续租失败 → dispatcher 巡检 | 75～100 秒 | `lease_expired`；旧执行恢复后写库被 epoch 挡住（LeaseLost） | 同 5；旧执行的逐字片段前端也会丢掉 |
| 10 | 所有 worker 下线 | dispatcher：消费者数 = 0 | ≤10 秒 | 不发（没有空位），也不判重发；题留在 outbox 排队，worker 回来后照常执行（下线前 10 秒内发出的在 RabbitMQ 里等） | 一直排队中（M6 告警） |
| 11 | worker 不认识任务名（升级没对齐） | worker 主进程 reject 并丢掉消息 → dispatcher 重发 | 约 15 分钟（重发 3 次） | `delivery_lost` | 失败，可重新生成 |
| 12 | 模型网关卡住 | 模型客户端：60 秒没数据 / 180 秒总长 | 60～180 秒 | 判失败（错误写在 error 里） | 失败，可重新生成 |
| 13 | dispatcher 崩溃 | compose 重启它；启动先扫一轮 outbox | 几秒 | 不受影响，只是这几秒不投递、不巡检 | 可能多等几秒 |
| 14 | Redis 挂了 | worker 第一次发片段失败 | 1 秒 | 不受影响 | 没有逐字效果，每步结束时整段出现 |
| 15 | API 进程被杀 | 前端：25 秒没数据 | ≤25 秒 | 不受影响 | “连接中断，正在重连…”，恢复后用 `?after=` 续上，不丢不重 |
| 16 | 同一条消息投了两次 | worker：claim 只认 pending | 立刻 | 只执行一次 | 无感 |
| 17 | 多用户、大量积压 | 积压留在 outbox，RabbitMQ 就绪数约等于 0 | — | 按先后顺序执行，**不会误判丢失**（实测 V3：20 道题，就绪数始终 0） | 排队中 |
| 18 | 子进程数配错，RabbitMQ 里出现积压 | dispatcher：就绪数连续 2 分钟 > 0 | 2 分钟 | 暂停重发，避免误判；记 warning | 排队变慢 |
| 19 | 加载语料出错（例如路径配错） | worker：claim 之后加载抛异常 | 立刻 | 判失败（实测 V9：`FileNotFoundError`，0 步） | “执行出错”，改好后可重新生成 |
| 20 | RabbitMQ 停机 | dispatcher：读不到队列状态 | ≤10 秒 | 不投递、不判重发；执行中的题照常跑完；恢复后不丢不重（实测 V6） | 排队中，恢复后正常 |

## 6. 和 M1.5 的差别（一张表）

| | M1.5 | M1.6（现在） |
|---|---|---|
| 加载语料 | claim 之前 | claim 之后，有续租保护 |
| 积压在哪 | RabbitMQ 队列 | PG outbox（有空位才发） |
| 判消息丢了 | 宽限期 2 分钟 + 水位线 / 队列空 / 30 分钟，三选一 | 1 分钟起、间隔翻倍；前提是队列里没有排队的消息 |
| 补发后 NOTIFY | 有（多余） | 没有 |
| 空出位子 | 不通知 | 结束时 NOTIFY，dispatcher 马上补位 |
| dispatcher 时间 | 兜底 10 秒、巡检 15 秒 | 都是 10 秒 |
| `consumer_timeout` | 配了 1 小时（不生效） | 删除 |
| 消息丢了多久发现 | 2 分钟～30 分钟 | 1 分钟（实测 68 秒） |
| 误判的边界 | 排队超过 30 分钟；一个队列 + 先进先出 + 额度等于子进程数 | 子进程数要和配置一致（不一致时暂停重发 + 告警） |
| broker 重连后的预取数 | Celery 调到 3 后不真正调回（当时没发现） | 不调低，始终 4 |

## 7. 仍然管不到的

| 情况 | 现在会怎样 | 计划 |
|---|---|---|
| 执行中的 worker 死了 | 判 `lease_expired`，用户手动重新生成，从头跑 | M4：别的 worker 接管，从断点继续 |
| 主线程卡住、续租线程还活着 | 只能等 25 分钟硬时限 | M4：续租线程顺带检查主线程有没有进展 |
| claim 之后、加载之中死了 | 不再自动补发，等租约过期 | M4 接管后自动接上 |
| worker 全部下线、dispatcher 挂了 | 没有告警 | M6：监控告警 |
| worker 被 kill 后约 100 秒 | 它手上 running 的题仍算在途，别的 worker 的空位少算 | 可以接受；压测时观察 |
| 执行中想停下重来 | 没有“停止生成”，只能等结束 | 未排期 |
