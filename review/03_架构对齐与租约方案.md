## 一、对齐结论

整体理解是对的：**PG 是唯一事实来源，Outbox 保证“写库成功就一定会被投递”，Redis 只做唤醒和实时转发，
租约 + epoch 保证同一时刻只有一个 worker 能写**。下面是需要修正或补充的地方。

### 1. 需要修正的（理解有偏差）

| # | 你的文档 | 实际应该是 | 为什么重要 |
|---|---|---|---|
| ① | “Attempts 表**先查询**有没有被消费、有没有超时，然后 **Lease 表新插入**一条” | **没有 Lease 表**。租约就是 attempts 行上的三个字段；领取是**一条带条件的 UPDATE**，判断和修改在同一条语句里完成 | “先查再写”在并发下会出错：A、B 同时查到“空闲”，然后都写成功，两个 worker 同时执行。单条条件 UPDATE 会锁住这一行，第二个人的 UPDATE 要等第一个提交，然后条件不再成立，更新 0 行 |
| ② | “每个 token 会直接**缓存**到 Redis 中” | Redis **Pub/Sub 不存储**，发出去时没人订阅就丢了 | 断线重连的浏览器拿不到之前的 token；靠“该步结束后，PG 里的完整文本覆盖”来补齐（PLAN §5.4 两层事件） |
| ③ | “按照队列顺序从前到后取出” | Celery 默认**预取**（每个进程先拿 4 条攒着）。长任务下会出现：A 忙着跑一道 10 分钟的题，手里还攥着 3 条消息；B 空闲却拿不到 | 必须设 `worker_prefetch_multiplier=1`：一次只拿一条 |
| ④ | “Celery 接受成功后发布并保存在 Redis” | Celery **不是一个独立的服务器**，它是一个 Python 库：Dispatcher 进程里用它**发**消息（写进 Redis），Worker 进程里用它**收**消息 | 部署时没有“Celery 服务”这个容器，只有 dispatcher、worker 两个进程用到它 |
| ⑤ | 限流 / Lua 信号量“类似 ROS 的参数服务器” | 参数服务器是“共享配置”；这里是**原子计数器**：Lua 脚本在 Redis 里一次性完成“检查 + 加一”，不会被别的请求插进来 | 理解 Lua 的价值在“原子”，不在“共享” |

### 2. 需要补充的（文档里没写到，但计划里有，且和你的三个问题直接相关）

| # | 遗漏 | 说明 |
|---|---|---|
| ⑥ | **Inspector（租约巡检）** | Dispatcher 进程有两份工作：投递 outbox，以及**定期找出租约过期的 attempt、重新投递**。没有它，worker 崩溃后的任务**永远不会被别人接手**——因为消息早被 A 拿走了，队列里没有了 |
| ⑦ | **投递成功后要把 outbox 标记为 sent** | “发出去了但还没来得及标记就崩溃”会导致重复投递；这是 Outbox 的已知代价，由租约去重（第二个 worker 领取失败，直接丢弃消息） |
| ⑧ | **持久事件怎么推给浏览器** | 不只是 token 走 Redis：worker 写完一步（PG 提交后），再往 Redis 发一条“run 100 有新事件 seq=37”的**通知**；FastAPI 收到后从 PG 按 seq 读出来推 SSE |
| ⑨ | **幂等键** | 第一步插入 run 时带 `unique(owner_id, idempotency_key)`；同一个 key 重复提交返回已有的 run，不新建 |
| ⑩ | **原子性的边界**（对应你的第 5 节） | 单条 SQL 是原子的；多条 SQL 要放进一个事务；但“事务里先 SELECT 再 UPDATE”在默认隔离级别（READ COMMITTED）下**仍然不安全**，所以租约一律用条件 UPDATE。Redis 侧的原子性靠 Lua |
| ⑪ | **时间一律用数据库的 `now()`** | 租约比较不能用 worker 自己的时钟：两台机器时钟差几秒，就可能误判过期 |

小问题：文档里有两个“4.”；Ngnix → Nginx。

## 二、先把两个概念分开：“接管”和“重试”

原计划里这两件事混在一起（§5.2 的 SQL 是“同一个 attempt 被重新领取”，§4 又说“重试就新建一条 attempt”）。
修订后明确区分：

| | **接管（takeover）** | **重试（retry）** |
|---|---|---|
| 触发 | worker 出事：崩溃、卡死、失联 → 租约过期 | 执行本身失败：网关报错、模型连续出错 |
| 对象 | **同一个 attempt**，`lease_epoch + 1` | **新建一个 attempt**（attempt_no + 1），旧的标记 failed |
| 从哪继续 | **从最后一个已提交的步骤继续**（见第四节） | **从头开始**（可能换模型，比如 DeepSeek → GLM，中途换模型结果说不清是谁做的） |
| 次数上限 | 最多接管 3 次（epoch > 4 就判 `worker_lost` 失败），防止“一跑就让 worker 崩溃”的毒任务无限循环 | 最多 2 次 |

```text
Run 100
 ├─ Attempt 200（attempt_no=1，DeepSeek）
 │    epoch 1：Worker A 执行到第 7 步 💥
 │    epoch 2：Worker B 接管，从第 8 步继续 → 网关连续报错 → failed
 └─ Attempt 245（attempt_no=2，GLM）  ← 重试：新 attempt，从头开始
      epoch 1：Worker C 执行 → succeeded
```

## 三、问题 1：worker 卡死、心跳线程没卡死，怎么办？

**问题的本质**：原方案的心跳只证明“进程还活着”，不证明“任务在推进”。主线程卡住（网络调用没超时、死锁、
死循环）时，心跳线程照样续租，租约永不过期，任务永远挂着，也没人接管。

**修订：三层防护，每层对应一种卡法**

```text
第 1 层：预防 —— 所有外部调用都有超时，大部分“卡住”会变成异常，正常走失败流程
  ├─ LLM：连接 10s，两个数据块之间最多 120s（现在是一个 600s 总值，要拆开）
  ├─ embedding：30s
  ├─ PG：statement_timeout 30s
  └─ Redis 信号量：获取最多等 60s

第 2 层：进度看门狗 —— 心跳线程“有进展才续租”
  ├─ 主线程：每收到一个流式片段 / 每完成一个工具，就更新 last_progress
  └─ 心跳线程：每 15 秒醒一次
       ├─ 距离 last_progress < 5 分钟，且总时长 < 30 分钟 → 续租
       └─ 否则 → 不再续租 + 举起“停止标志” → 租约最多 90 秒后过期 → 被接管

第 3 层：硬兜底 —— Celery 的时间限制（只在 Linux 的 prefork 进程池下有效，我们的 worker 正好是）
  ├─ soft_time_limit = 35 分钟：在任务里抛异常，让它自己清理退出
  └─ time_limit = 40 分钟：直接杀掉这个子进程，Celery 再起一个新的，内存和连接由操作系统回收
```

阈值依据（E80 实测）：单题最长 687 秒（约 11.5 分钟）；不开流式时单轮最长 90 秒。
流式下模型思考时片段持续到达，正常情况下 5 分钟没有任何进展只可能是真卡住了。

## 四、问题 2：A 的租约过期后，B 怎么恢复？

### 4.1 谁来叫醒 B：Inspector

A 拿走消息时 Celery 已经确认（ack），队列里没有这条消息了，所以**必须由 Inspector 重新投递**：

```sql
-- Inspector 每 15 秒执行一次：给“租约过期、还在 running”的 attempt 补一条投递
INSERT INTO outbox (attempt_id, status, next_attempt_at)
SELECT id, 'pending', now() FROM attempts
WHERE status = 'running' AND lease_until < now()
ON CONFLICT (attempt_id) WHERE status = 'pending' DO NOTHING;
-- outbox 上建部分唯一索引：同一个 attempt 最多一条 pending 投递，巡检多少次都不会刷屏
```

同时巡检另一种“卡住”：attempt 是 `pending`、outbox 已标记 sent，但消息丢了（例如 Redis 重启）超过 2 分钟
→ 同样补一条投递。

为什么不用 Celery 自带的“任务失败重投”（`acks_late`）：Redis 作为队列时，没确认的消息在
`visibility_timeout`（默认 1 小时）后会被**再发一次**，长任务会被重复投递；而且 worker 卡住但没死时它不会触发。
统一原则：**队列只是唤醒信号，什么时候该执行、由谁执行，只看数据库**（这也是 D3 的原意）。

### 4.2 B 领取：和 A 第一次领取是同一条 SQL

```sql
UPDATE attempts
SET status = 'running', lease_owner = :me, lease_epoch = lease_epoch + 1,
    lease_until = now() + interval '90 seconds'
WHERE id = :id
  AND (status = 'pending' OR (status = 'running' AND lease_until < now()))
RETURNING lease_epoch;
-- 0 行：别人已经领了，或租约其实还有效 → 丢弃这条消息，什么都不做
```

### 4.3 B 从哪里继续：断点（checkpoint）

现在 Harness 的进度全在 A 的内存里（对话历史、EpisodeState、各种计数器），A 死了就没了。
修订：**每提交一步，同时把“继续执行所需的全部内容”存一份断点**，B 读出断点直接接着跑：

```text
attempts.checkpoint（JSONB，每一步覆盖一次）
  ├─ messages        当前发给模型的对话（写笔记后会被压缩，大小有上限）
  ├─ episode_state   搜过哪些文档、可读哪些块、看过的原文、引用、笔记
  └─ loop_counters   已用轮数、连续出错次数、上一次调用的指纹……（停止条件要用）
```

安全性前提：**十个工具都是只读的**（检索、读原文、计算），没有对外的副作用，所以
“A 做到一半的那一轮被丢弃、B 重新做这一轮”不会造成任何重复影响。浪费的只是 A 那一轮的模型调用。

对 Harness 的改动（保持“Harness 不认识数据库”）：

```text
loop.run_episode(task, llm, registry, checkpoint=None, on_step=None, should_stop=None)
   checkpoint   ：有就从断点恢复，没有就从头开始
   on_step      ：每完成一步回调一次，worker 在这里做“带 epoch 的提交”
   should_stop  ：每次调用模型前、每个流式片段、每个工具后检查一次（见第五节）
```

### 4.4 每一步的提交：epoch 检查和写入在同一个事务里

```sql
BEGIN;
UPDATE attempts SET last_step = :n, checkpoint = :cp, lease_until = now() + interval '90 seconds'
WHERE id = :id AND lease_epoch = :my_epoch;           -- 0 行 → 我已被取代 → ROLLBACK，停止
INSERT INTO steps  (attempt_id, step_no, ...) VALUES (...);   -- unique(attempt_id, step_no) 再兜一层
INSERT INTO events (run_id, seq, ...) VALUES (...);
COMMIT;
```

第一条 UPDATE 会锁住这一行，直到提交；这期间 B 的领取 UPDATE 只能等待，等到时 epoch 已经变了或者没变，
不会出现“检查通过之后、写入之前被人接管”的空隙。

### 4.5 时间线

```text
t(s)     0         30        60        90        105       120
Worker A ─执行第7步─💥（崩溃或卡住，不再续租）
PG       lease_until=90s ─────────────────────► 过期
Inspector                                        发现过期 → 写 outbox
Dispatcher                                         投递 → Redis
Worker B                                               领取 epoch=2
                                                       读 checkpoint（第 7 步之后）
                                                       从第 8 步继续 ──►
Browser  收到持久事件：attempt 200 由 B 接管，从第 8 步继续
```

## 五、问题 3：A 已经被取代，怎么及时停下、收回资源？

### 5.1 先区分两种“恢复”

| 情况 | 数据库里 | A 该怎么办 |
|---|---|---|
| **3a**：A 的租约过期了，但**还没人接管**，A 又恢复了 | epoch 没变，lease_owner 还是 A | **继续执行**。A 的续租（按 epoch + owner 条件更新）会成功；之后 Inspector 补发的消息到 B 手里时，B 领取失败（租约有效），直接丢弃 |
| **3b**：A 恢复时**已经被 B 接管** | epoch 已经 +1 | **立即停止**，不写任何东西 |

判断标准只有一个：**我的 epoch 还是不是当前 epoch**。不看“租约是否过期”，因为过期只是“允许别人来抢”，
只要没人抢，A 继续执行完全安全（epoch 保证了同一时刻只有一个合法持有者）。

### 5.2 A 怎么发现自己被取代（三个检查点，越往下越快）

```text
① 心跳续租（每 15 秒）
     UPDATE attempts SET lease_until = now() + '90s'
     WHERE id = :id AND lease_epoch = :my_epoch AND lease_owner = :me
     → 0 行：被取代 → 举起“停止标志”（threading.Event）

② 每一步提交（第四节 4.4）
     → 0 行：被取代 → 回滚，举起停止标志

③ 主线程在三个位置看停止标志（只读一个内存变量，几乎没有开销）
     · 每次调用模型之前
     · 每收到一个流式片段时（on_delta 里）→ 抛 LeaseLost 异常，流式连接立刻断开，模型不再继续生成
     · 每个工具执行完之后
```

检测延迟：最多一个心跳间隔（15 秒）；如果恰好在提交步骤，则是立即。

### 5.3 停下之后怎么收回资源

```text
LeaseLost 异常向上抛出
  ├─ with 块自动关闭 LLM 的 HTTP 流：不再消耗模型 token
  ├─ 数据库事务回滚、连接归还连接池：不占连接
  ├─ finally 里释放 Redis 的模型并发名额：名额本身也带过期时间，进程被杀也能自动回收
  ├─ 心跳线程随停止标志退出
  ├─ 不写任何状态（attempt 现在归 B 管）、只记一行日志 “attempt 200 epoch 1 被取代，已停止”
  └─ Celery 任务正常返回 → 这个 worker 进程空出来，去接下一条消息
```

如果 A 卡得太死，连停止标志都检查不到 → 第三节第 3 层：40 分钟硬时限杀掉子进程，由操作系统回收一切。

### 5.4 前端不会看到“僵尸 A”的输出

A 在被发现之前，可能还会往 Redis 发几个 token。修订：**每个实时片段都带上 epoch**；
B 接管时会先写一条持久事件“epoch=2 接管”，FastAPI / 前端收到后，丢弃 epoch 更小的片段。

| Inspector：补投过期租约、补投丢失的 pending | M4 | dispatcher |
| 实时片段带 epoch，前端丢弃旧 epoch | M2 | SSE |
| 故障注入集成测试（每个对应一个事故场景） | M4 | tests |

M4 的集成测试（按“一个测试一个事故”）：

1. worker 执行到第 3 步被杀 → 另一个 worker 从第 4 步继续，最终步骤编号连续、不重复
2. 旧 worker 在被接管后提交步骤 → 被拒绝，库里没有它的写入
3. 主线程卡住、心跳线程正常 → 5 分钟后不再续租，任务被接管
4. 租约过期但无人接管时 worker 恢复 → 继续执行成功，迟到的恢复消息被丢弃
5. 被取代的 worker 正在流式接收 → 立即断开，模型并发名额被释放
6. 一跑就崩的任务 → 接管 3 次后判 `worker_lost` 失败，不再无限循环
