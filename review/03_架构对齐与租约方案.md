## 一、对齐结论

整体理解是对的：**PG 是唯一事实来源，Outbox 保证“写库成功就一定会被投递”，Redis 只做唤醒和实时转发，
租约 + epoch 保证同一时刻只有一个 worker 能写**。下面是需要修正或补充的地方。

### 1. 需要修正的（理解有偏差）

| # | 你的文档 | 实际应该是 | 为什么重要 |
|---|---|---|---|
| ① | “Attempts 表**先查询**有没有被消费、有没有超时，然后 **Lease 表新插入**一条” | **没有 Lease 表**。租约就是 attempts 行上的三个字段；领取是**一条带条件的 UPDATE**，判断和修改在同一条语句里完成 | “先查再写”在并发下会出错：A、B 同时查到“空闲”，然后都写成功，两个 worker 同时执行。单条条件 UPDATE 会锁住这一行，第二个人的 UPDATE 要等第一个提交，然后条件不再成立，更新 0 行 |
| ② | “每个 token 会直接**缓存**到 Redis 中” | Redis **Pub/Sub 不存储**，发出去时没人订阅就丢了 | 断线重连的浏览器拿不到之前的 token；靠“该步结束后，PG 里的完整文本覆盖”来补齐（PLAN §5.4 两层事件） |
| ③ | “按照队列顺序从前到后取出” | Redis 队列本身是先进先出，但 Celery worker 默认会**预取**：每个执行槽位先从队列里多拿几条消息攒在自己手里（默认 4 条）。攒着的消息别的 worker 拿不到，只能等这个槽位空出来（详见第七节问答 1） | 设 `worker_prefetch_multiplier=1`：每个槽位手里最多一条 |
| ④ | “Celery 接受成功后发布并保存在 Redis” | Celery **不是一个独立的服务器**，它是一个 Python 库：Dispatcher 进程里用它**发**消息（写进 Redis），Worker 进程里用它**收**消息 | 部署时没有“Celery 服务”这个容器，只有 dispatcher、worker 两个进程用到它 |
| ⑤ | 限流 / Lua 信号量“类似 ROS 的参数服务器” | 参数服务器是“共享配置”；这里是**原子计数器**：Lua 脚本在 Redis 里一次性完成“检查 + 加一”，不会被别的请求插进来 | 理解 Lua 的价值在“原子”，不在“共享” |

### 2. 需要补充的（文档里没写到，但计划里有，且和你的三个问题直接相关）

| # | 遗漏 | 说明 |
|---|---|---|
| ⑥ | **Inspector（租约巡检）** | Dispatcher 进程有两份工作：投递 outbox，以及**定期找出租约过期的 attempt、重新投递**。没有它，worker 崩溃后的任务**永远不会被别人接手**——因为消息早被 A 拿走了，队列里没有了 |
| ⑦ | **投递成功后要把 outbox 标记为 sent** | “发出去了但还没来得及标记就崩溃”会导致重复投递；这是 Outbox 的已知代价，由租约去重（第二个 worker 领取失败，直接丢弃消息） |
| ⑧ | **持久事件** | 浏览器看到的不只是 token：“第 3 步开始 / 结束、调用了什么工具、结果是什么、最终答案、被接管”这些也是事件，它们写进 PG 的 events 表（带序号 seq），刷新页面或断线重连时从 PG 补读。worker 写完 PG 后往 Redis 发一条“run 100 有新事件 seq=37”的**通知**，FastAPI 收到后按 seq 从 PG 读出来推给浏览器（详见第七节问答 2） |
| ⑨ | **幂等键** | 第一步插入 run 时带 `unique(owner_id, idempotency_key)`；同一个 key 重复提交返回已有的 run，不新建 |
| ⑩ | **原子性的边界**（对应你的第 5 节） | 单条 SQL 是原子的；多条 SQL 要放进一个事务；但“事务里先 SELECT 再 UPDATE”在默认隔离级别（READ COMMITTED）下**仍然不安全**，所以租约一律用条件 UPDATE。Redis 侧的原子性靠 Lua |
| ⑪ | **时间一律用数据库的 `now()`** | 租约比较不能用 worker 自己的时钟：两台机器时钟差几秒，就可能误判过期 |

小问题：文档里有两个“4.”；Ngnix → Nginx。

## 二、先把两个概念分开：“接管”和“重试”

原计划里这两件事混在一起（§5.2 的 SQL 是“同一个 attempt 被重新领取”，§4 又说“重试就新建一条 attempt”）。
修订后明确区分：

| | **接管（takeover）** | **重试（retry）** |
|---|---|---|
| 触发 | worker 出事：崩溃、卡死、失联 → 租约过期 | ① 自动：执行失败（网关报错、模型调用超时重试后仍失败）<br>② **手动：用户对答案不满意，点“重新生成”**（只能在上一个 attempt 结束后点） |
| 对象 | **同一个 attempt**，`lease_epoch + 1` | **新建一个 attempt**（attempt_no + 1），旧的标记 failed |
| 从哪继续 | **从最后一个已提交的步骤继续**（见第四节） | **从头开始**（可能换模型，比如 DeepSeek → GLM，中途换模型结果说不清是谁做的） |
| 次数上限 | 最多接管 3 次（epoch > 4 就判 `worker_lost` 失败），防止“一跑就让 worker 崩溃”的毒任务无限循环 | 自动重试最多 1 次（换备用模型）；手动重试不限次数，但计入用户配额 |

```text
Run 100
 ├─ Attempt 200（attempt_no=1，DeepSeek）
 │    epoch 1：Worker A 执行到第 7 步 💥
 │    epoch 2：Worker B 接管，从第 8 步继续 → 网关连续报错 → failed
 └─ Attempt 245（attempt_no=2，GLM）  ← 重试：新 attempt，从头开始
      epoch 1：Worker C 执行 → succeeded
```

## 三、问题 1：worker 卡死、心跳线程没卡死，怎么办？——超时预算 + 进度监督

**问题的本质**：原方案的心跳只证明“进程还活着”，不证明“任务在推进”。主线程卡住时心跳照样续租，任务永远挂着。
修订：给每一类操作规定**最长时间（超时预算）**，由心跳线程兼任**监督者**逐项检查。

### 3.1 超时预算（依据 E80 实测：2,881 次模型调用，中位 3 秒，P99 61 秒，最长 120.6 秒；单题最长 687 秒）

| 操作 | 上限 | 超时后怎么处理 |
|---|---|---|
| 单次 LLM 请求 | **总时长 180 秒**；首个数据块 60 秒内要到；两个数据块之间最多 30 秒 | 这一轮作废，从断点重试 1 次；仍超时 → attempt 失败 → 自动重试（新 attempt，换备用模型） |
| 检索（embedding + PG 查询） | 30 秒 | 作为工具错误返回给模型（可重试），模型自己决定换个查询或重试 |
| 单个工具 | 60 秒 | 同上 |
| 整个 attempt | **20 分钟** | attempt 失败（`deadline_exceeded`），不自动重试，用户可手动重试 |
| 卡死兜底 | 停止标志举起后 60 秒没反应（判定方法见问答 9） | 监督者结束子进程，Celery 补新进程；任务由别的 worker 接管 |
| 冻住兜底 | Celery 硬时限：单个任务 25 分钟 | 整个进程冻住时由 Celery 主进程从外面杀掉 |

关于 LLM 的三个数字：

- 流式响应是一小块一小块到达的。“两个数据块之间最多 30 秒”管的是**中途断流**：模型在正常生成时，
  数据块每秒都有很多个，30 秒一个都没来，说明连接已经卡住。它**不限制总时长**，一个持续出数据的请求可以跑很久。
- “首个数据块 60 秒”管的是**网关排队**：公用网关忙时，请求可能半天不开始返回。
- “总时长 180 秒”才是上限。你提的 120 秒在 E80 里会误杀 1 次（DeepSeek 一轮思考 120.6 秒），
  公用网关负载还会波动，所以留到 180 秒。E80 里没有任何一轮超过它。

### 3.2 监督者：心跳线程每 5 秒检查一次

```text
主线程（执行 Agent）
  ├─ 开始一个操作时登记：begin("llm", 上限 180 秒)
  ├─ 操作结束时登记：end()
  └─ 每个流式数据块、每次调用模型前、每个工具后，看一眼停止标志
       └─ 看到就抛异常，按 3.1 表格处理（重试这一轮 / 返回工具错误 / attempt 失败）

心跳线程（监督者），每 5 秒醒一次
  ├─ 当前操作超过它的上限了吗？
  ├─ 整个 attempt 超过 20 分钟了吗？
  ├─ 我的 epoch 还有效吗？（每 15 秒顺带续租一次）
  └─ 任何一项有问题 → 举起停止标志，写明原因

主线程卡死、对停止标志 60 秒没反应（卡在某个不响应的调用里，判定方法见问答 9）
  ├─ 监督者直接结束自己所在的子进程（os._exit）
  │    操作系统回收内存和网络连接；PG 发现连接断开，自动回滚未提交的事务
  ├─ Celery 主进程发现子进程没了，立刻补一个新的子进程，继续接任务
  └─ 这道题的租约不再有人续 → 最多 90 秒后过期 → Inspector 补投 → 别的 worker 从断点接管

只有一种情况监督者也救不了：整个进程冻住（例如 C 扩展死锁、一直占着 Python 的全局解释器锁 GIL），
监督者线程自己也跑不起来。这时靠 Celery 主进程从外面计时：单个任务超过 25 分钟就杀掉它（硬时限）。
```

大部分情况根本走不到监督者：LLM、embedding、PG 的客户端本身都设了超时，到点就抛异常。
监督者只兜“客户端超时没生效”的情况（程序 bug、死锁、纯计算死循环）。

## 四、问题 2：A 的租约过期后，B 怎么恢复？

### 4.1 谁来叫醒 B：Inspector

A 拿走消息时 Celery 已经确认（ack），队列里没有这条消息了，所以**必须由 Inspector 重新投递**：

```sql
-- Inspector 每 15 秒执行一次：给“租约过期、还在 running”的 attempt 补一条投递
INSERT INTO outbox (attempt_id, status, next_attempt_at)
SELECT id, 'pending', now() FROM attempts
WHERE status = 'running' AND lease_until < now()
ON CONFLICT (attempt_id) WHERE status = 'pending' DO NOTHING;
-- outbox 上建部分唯一索引：同一个 attempt 最多一条 pending 投递，巡检多少次都不会刷屏
```

同时巡检另一种“卡住”：attempt 是 `pending`、outbox 已标记 sent，但消息丢了（例如 Redis 重启）超过 2 分钟
→ 同样补一条投递。

为什么不用 Celery 自带的“任务失败重投”（`acks_late`）：Redis 作为队列时，没确认的消息在
`visibility_timeout`（默认 1 小时）后会被**再发一次**，长任务会被重复投递；而且 worker 卡住但没死时它不会触发。
统一原则：**队列只是唤醒信号，什么时候该执行、由谁执行，只看数据库**（这也是 D3 的原意）。

### 4.2 B 领取：和 A 第一次领取是同一条 SQL

```sql
UPDATE attempts
SET status = 'running', lease_owner = :me, lease_epoch = lease_epoch + 1,
    lease_until = now() + interval '90 seconds'
WHERE id = :id
  AND (status = 'pending' OR (status = 'running' AND lease_until < now()))
RETURNING lease_epoch;
-- 0 行：别人已经领了，或租约其实还有效 → 丢弃这条消息，什么都不做
```

### 4.3 B 从哪里继续：最后一个已提交的步骤之后

是的，就是**从数据库里最后保存的那一步之后继续**。一“步”= 一轮：模型调用一次 + 执行它要的那个工具；
工具执行完、这一轮提交进数据库，才算这一步完成。

```text
A：第 1 步 ✓ … 第 7 步 ✓（已提交） 第 8 步：模型调用到一半 💥
B：读出“第 7 步之后”的断点 → 从第 8 步开始，第 8 步整轮重做
```

只靠 steps 表还不够：steps 记录的是“发生了什么”，而 B 要接着跑，还需要 A 内存里的东西
（当前对话上下文、EpisodeState、各种计数器）。所以**每提交一步，同时把这些存一份断点**：

```text
attempts.checkpoint（JSONB，每一步覆盖一次）
  ├─ messages        当前发给模型的对话（写笔记后会被压缩，大小有上限）
  ├─ episode_state   搜过哪些文档、可读哪些块、看过的原文、引用、笔记
  └─ loop_counters   已用轮数、连续出错次数、上一次调用的指纹……（停止条件要用）
```

安全性前提：**十个工具都是只读的**（检索、读原文、计算），没有对外的副作用，所以
“A 做到一半的那一轮被丢弃、B 重新做这一轮”不会造成任何重复影响。浪费的只是 A 那一轮的模型调用。

对 Harness 的改动（保持“Harness 不认识数据库”）：

```text
loop.run_episode(task, llm, registry, checkpoint=None, on_step=None, should_stop=None)
   checkpoint   ：有就从断点恢复，没有就从头开始
   on_step      ：每完成一步回调一次，worker 在这里做“带 epoch 的提交”
   should_stop  ：每次调用模型前、每个流式片段、每个工具后检查一次（见第五节）
```

### 4.4 每一步的提交：epoch 检查和写入在同一个事务里

```sql
BEGIN;
UPDATE attempts SET last_step = :n, checkpoint = :cp, lease_until = now() + interval '90 seconds'
WHERE id = :id AND lease_epoch = :my_epoch;           -- 0 行 → 我已被取代 → ROLLBACK，停止
INSERT INTO steps  (attempt_id, step_no, ...) VALUES (...);   -- unique(attempt_id, step_no) 再兜一层
INSERT INTO events (run_id, seq, ...) VALUES (...);
COMMIT;
```

第一条 UPDATE 会锁住这一行，直到提交；这期间 B 的领取 UPDATE 只能等待，等到时 epoch 已经变了或者没变，
不会出现“检查通过之后、写入之前被人接管”的空隙。

### 4.5 时间线

```text
t(s)     0         30        60        90        105       120
Worker A ─执行第7步─💥（崩溃或卡住，不再续租）
PG       lease_until=90s ─────────────────────► 过期
Inspector                                        发现过期 → 写 outbox
Dispatcher                                         投递 → Redis
Worker B                                               领取 epoch=2
                                                       读 checkpoint（第 7 步之后）
                                                       从第 8 步继续 ──►
Browser  收到持久事件：attempt 200 由 B 接管，从第 8 步继续
```

## 五、问题 3：A 已经被取代，怎么及时停下、收回资源？

### 5.1 先区分两种“恢复”

| 情况 | 数据库里 | A 该怎么办 |
|---|---|---|
| **3a**：A 的租约过期了，但**还没人接管**，A 又恢复了 | epoch 没变，lease_owner 还是 A | **继续执行**。A 的续租（按 epoch + owner 条件更新）会成功；之后 Inspector 补发的消息到 B 手里时，B 领取失败（租约有效），直接丢弃 |
| **3b**：A 恢复时**已经被 B 接管** | epoch 已经 +1 | **立即停止**，不写任何东西 |

判断标准只有一个：**我的 epoch 还是不是当前 epoch**。不看“租约是否过期”，因为过期只是“允许别人来抢”，
只要没人抢，A 继续执行完全安全（epoch 保证了同一时刻只有一个合法持有者）。

### 5.2 A 怎么发现自己被取代（三个检查点，越往下越快）

```text
① 心跳续租（每 15 秒）
     UPDATE attempts SET lease_until = now() + '90s'
     WHERE id = :id AND lease_epoch = :my_epoch AND lease_owner = :me
     → 0 行：被取代 → 举起“停止标志”（threading.Event）

② 每一步提交（第四节 4.4）
     → 0 行：被取代 → 回滚，举起停止标志

③ 主线程在三个位置看停止标志（只读一个内存变量，几乎没有开销）
     · 每次调用模型之前
     · 每收到一个流式片段时（on_delta 里）→ 抛 LeaseLost 异常，流式连接立刻断开，模型不再继续生成
     · 每个工具执行完之后
```

检测延迟：最多一个心跳间隔（15 秒）；如果恰好在提交步骤，则是立即。

### 5.3 停下之后怎么收回资源

```text
LeaseLost 异常向上抛出
  ├─ with 块自动关闭 LLM 的 HTTP 流：不再消耗模型 token
  ├─ 数据库事务回滚、连接归还连接池：不占连接
  ├─ finally 里释放 Redis 的模型并发名额：名额本身也带过期时间，进程被杀也能自动回收
  ├─ 心跳线程随停止标志退出
  ├─ 不写任何状态（attempt 现在归 B 管）、只记一行日志 “attempt 200 epoch 1 被取代，已停止”
  └─ Celery 任务正常返回 → 这个 worker 进程空出来，去接下一条消息
```

如果 A 卡得太死，连停止标志都检查不到 → 第三节第 3 层：40 分钟硬时限杀掉子进程，由操作系统回收一切。

### 5.4 前端不会看到“僵尸 A”的输出

A 在被发现之前，可能还会往 Redis 发几个 token。修订：**每个实时片段都带上 epoch**；
B 接管时会先写一条持久事件“epoch=2 接管”，FastAPI / 前端收到后，丢弃 epoch 更小的片段。

M4 的集成测试（按“一个测试一个事故”）：

1. worker 执行到第 3 步被杀 → 另一个 worker 从第 4 步继续，最终步骤编号连续、不重复
2. 旧 worker 在被接管后提交步骤 → 被拒绝，库里没有它的写入
3. 主线程卡在一个不响应的调用里、心跳线程正常 → 监督者停止续租，任务被接管
4. LLM 请求超过 180 秒 → 这一轮从断点重试一次，第二次仍超时 → attempt 失败并自动换模型重试
5. 租约过期但无人接管时 worker 恢复 → 继续执行成功，迟到的恢复消息被丢弃
6. 被取代的 worker 正在流式接收 → 立即断开，模型并发名额被释放
7. 一跑就崩的任务 → 接管 3 次后判 `worker_lost` 失败，不再无限循环

## 七、问答（2026-10-05 第二轮反馈）

### 1. 预取：worker 数量是自己设定的，每个 worker 取一个任务去完成，不对吗？

“每个执行槽位同时只**执行**一个任务”是对的；问题在于它**拿**的不止一个。

- 一个 Celery worker 是一个主进程 + N 个子进程（`--concurrency=N`），N 就是你说的“worker 数量”，每个子进程同一时间只跑一道题。
- 主进程会**提前**从 Redis 多拿消息存在自己手里，数量 = N × `prefetch_multiplier`（默认 4）。
  被拿走的消息在 Redis 里就没了，别的 worker 看不到。

```text
两个 worker 容器，各 1 个子进程，默认预取 4 条；队列里有 8 道题
  worker 1 拿走 1 2 3 4   → 第 1 题要跑 10 分钟，2 3 4 在它手里干等
  worker 2 拿走 5 6 7 8   → 很快跑完，然后空闲
结果：第 2 题比第 8 题晚开始很多，worker 2 闲着也帮不上忙
```

所以“不是严格按队列顺序”：**出队是先进先出，但开始执行的顺序取决于消息被谁攒着、那个槽位什么时候空**。
设 `prefetch_multiplier=1`，再配合 `acks_late=True`（见问答 6），每个子进程手里就只有正在跑的那一条，
空了才去拿下一条，就基本按提交顺序执行了。
另一个好处：worker 崩溃时，它攒着、还没开始执行的消息不会被困住
（Redis 要等 `visibility_timeout`，默认 1 小时，才会把这些消息还回队列）。

### 2. 持久事件是什么？不是 Redis 传 token 给 SSE 显示在浏览器上吗？

token 只是浏览器看到的一部分。浏览器上的时间线其实由两类东西组成：

| | 瞬时增量（token） | 持久事件 |
|---|---|---|
| 是什么 | 思考和回答的一个个字 | “第 3 步开始”“调用 search_docs，参数…”“工具结果…”“第 3 步完整思考”“最终答案”“被 B 接管”“失败 / 取消” |
| 存在哪 | 不存，Redis Pub/Sub 转发完就没了 | PG 的 events 表，每个 run 内序号 seq 递增 |
| 用途 | 让你看到逐字打出来的效果 | 刷新页面、断线重连、过几天再打开这道题，都能完整还原 |

```text
worker 每完成一步：
  ① PG 事务：写 steps + 写 events（seq=37：第 3 步完成，含完整思考和工具结果）
  ② 事务提交后，Redis 发通知：“run 100 有新事件 seq=37”
生成过程中：
  ③ 每个 token → Redis Pub/Sub（不落库）

FastAPI 的 SSE 连接：
  浏览器连上（或重连，带上“我收到的最后一个 seq=30”）
    → 先从 PG 读出 seq 31..37 补发
    → 然后同时监听：Redis 通知（来了就去 PG 读新事件）+ Redis token（直接转发）
```

为什么不全走 Redis：Pub/Sub 不存消息，浏览器断开那几秒的内容就永远丢了；
为什么不全进 PG：每个 token 写一次库，一道题几万次写入，数据库扛不住（写放大）。

### 3. 重试还可能是用户不满意，点了重试

对，已补进第二节：用户点“重新生成”= 在同一个 run 下新建一个 attempt，从头执行，旧答案保留（前端可以切换查看第 1 次 / 第 2 次）。
只能在上一个 attempt 结束后点；还在执行时要先取消。手动重试计入用户配额。

### 4. LLM“两个数据块之间最多 120 秒”是什么意思？能不能按操作规定超时？

见新的第三节：按你给的思路改成了“超时预算 + 进度监督”，四个数字只把 LLM 从 120 秒调到 180 秒（理由在 3.1）。
原方案里的“30 分钟”只是整题的总上限，不是唯一手段，现在改成 20 分钟，并且每一类操作都有自己的上限。

### 5. 从哪里继续：就是从数据库最后保存的 step 开始吗？

是的，见 4.3：从最后一个已提交的步骤之后继续，正在做的那一轮整轮重做。

## 八、问答（第三轮反馈）

### 6. 能不能设置每个 worker 只取一个任务，然后多开几个 worker？现在的方案是什么？

能，而且就应该这样。但只设 `prefetch_multiplier=1` 还差一点，这是我上一版写错的地方：

- Celery 默认“早确认”：任务一**开始执行**就向 Redis 确认这条消息，然后这个子进程马上又去预取一条。
  所以“早确认 + 预取 1”时，每个子进程手里是“正在跑的 1 条 + 攒着的 1 条”（Celery 官方文档的原话：
  `-c 10` 的 worker 最多会占着 20 条）。
- 改成 `acks_late=True`（任务**跑完**才确认）后，正在跑的那条还没确认，不会再去拿新的，
  每个子进程手里就**只有正在跑的那一条**。

`acks_late` 的副作用和处理：

| 副作用 | 处理 |
|---|---|
| Redis 队列有 `visibility_timeout`：消息被拿走后，超过这个时间还没确认，Redis 会把它还回队列，交给别人再执行一次 | 设成 2 小时，远大于单题上限 25 分钟，正常任务不会被重复投递 |
| worker 崩溃时，没确认的消息会在 2 小时后被重新投递 | 无害：那时数据库里这道题要么已被接管完成，要么已结束，新 worker 领取租约会失败，直接丢弃消息 |

“多开几个 worker”有两种开法，效果一样，都是“同时能跑几道题”：

```text
开法 A：一个 worker 容器，里面开 N 个子进程
  celery worker --concurrency=4

开法 B：开多个 worker 容器
  docker compose up --scale worker=3
```

方案：**M1 先用开法 A，一个容器 4 个子进程**。数字 4 的依据：
- 公用网关同时能扛的请求有限；E80 用 4 并发 × 2 个模型跑了 160 题，网关没有出错。
- 每个子进程都要把语料和 BM25 索引装进内存，M1 先实测一个进程占多少内存，再定能开几个。

以后要扩容就把容器数调大（开法 B）；不管开几个，所有 worker 共用 Redis 里的“模型并发名额”（PLAN §5.5），
总的模型请求数不会超过网关的承受能力。

### 7. 卡住的进程为什么要等 Celery 硬时限杀？能不能直接杀？25 分钟是不是“进程不管死没死都最多跑 25 分钟”？

先澄清硬时限的含义：

- 它计的是**单个任务**（一次 attempt 的执行）的时长，从这个任务开始执行算起；不是进程的寿命，也不是单轮模型调用。
- 一个健康的子进程会一道接一道地跑题，每道题单独计时。正常的题在 20 分钟内就会结束（attempt 上限），
  所以 25 分钟的硬时限**永远碰不到正常任务**，只会碰到“卡死且没人处理”的任务。
- 单轮模型调用的上限是 180 秒（3.1），和它无关。

“能不能直接杀”——能，而且上一版让卡死的进程白白多占资源最多二十几分钟，确实不合理。改为：

```text
停止标志举起 60 秒后，主线程还没反应
  └─ 监督者线程直接结束自己所在的子进程（os._exit）
       ├─ 操作系统回收内存、关闭网络连接；PG 看到连接断开，回滚未提交的事务
       ├─ Redis 里的模型并发名额带过期时间，到期自动收回
       ├─ Celery 主进程立刻补一个新子进程，这个槽位马上能接新任务
       └─ 这道题的租约没人续了，最多 90 秒后过期 → 别的 worker 从断点接管
```

为什么敢“硬杀”：这道题的进度都在数据库里（已提交的步骤和断点），未提交的那一轮本来就要重做；
租约 + epoch 保证被杀的进程即使“没死透”也写不进任何东西。

为什么还留 25 分钟硬时限：监督者是同一个进程里的一个线程，**整个进程冻住**时（例如 C 扩展死锁、
一直占着 GIL），它自己也跑不起来，这时只有进程外面的 Celery 主进程能动手。这是最后一道保险，正常情况下用不到。

人工也可以随时处理：`celery control revoke <任务ID> --terminate` 结束某道题的子进程，或者直接重启 worker 容器；
效果和上面一样，因为进度都在数据库里，不会丢。

## 九、问答（第四轮反馈）

### 8. 租约过期不是数据库自动判定的吗？

“过期”**不是数据库主动做的一件事**，而是一个时间比较：

```text
attempts 里这一行：status = 'running'，lease_until = 12:01:30
  12:01:29 有人问“过期了吗？”  lease_until < now() 为假 → 没过期
  12:01:31 有人问“过期了吗？”  lease_until < now() 为真 → 过期了
  这一行本身从头到尾没被改过，status 还是 running
```

- 数据库不会在 12:01:30 自动把它“置为过期”，也不会通知任何人（PG 没有“到点触发”的机制）。
- 领取 SQL 里写着 `lease_until < now()`，所以过期之后**谁来领取都能成功**——这一点是“自动”的，不用任何人先去标记。
- 但 worker 不会自己去数据库里找活干，它们只听队列里的消息。所以需要 **Inspector 定期去问一次
  “有哪些过期了”**，再往队列里放一条消息，worker 才会来领取。数据库是“账本”，Inspector 是“查账的人”。

### 9. 超时不代表主线程没反应，监督者怎么判断主线程真的没反应？

对，**超时多半是外部原因**（网关慢、网络卡），这时主线程是正常的，只是在等。两种情况要分开：

| | 主线程状态 | 举起停止标志后会怎样 |
|---|---|---|
| 外部慢 | 正常，在等网络数据 | 很快回到检查点：下一个数据块到来时就看到标志；就算一块都不来，客户端自己的超时（块间 30 秒）也会让它抛异常回来 |
| 真卡死 | 卡在某处，回不到检查点 | 永远看不到标志 |

判定方法是**举旗 + 等回应**：

```text
监督者在 T 时刻举起停止标志
  └─ 主线程看到标志 → 退出当前操作 → 调用 end() 登记“我结束了”（这就是回应）

监督者在 T + 60 秒检查：当前操作还登记着没结束吗？
  ├─ 已结束 → 主线程正常，按超时类型处理（重试这一轮 / 返回工具错误 / attempt 失败）
  └─ 还没结束 → 判定“真卡死” → 结束子进程
```

为什么 60 秒能分清这两种情况：主线程里所有会阻塞的调用都有自己的超时，最长的是“块间 30 秒”
（embedding、PG 都是 30 秒）。所以只要主线程是正常的，**无论外面多慢，30 秒内它一定能回到检查点**。
宽限取 60 秒，比 30 秒多留一倍余量；超过 60 秒还没回应，只剩一种解释：卡在了一个没有超时的地方
（程序 bug、死锁、死循环）。上一版写的 30 秒和客户端超时一样长，可能把正常的“外部慢”误判成卡死，已改为 60 秒。

### 10. 监督者是心跳线程，它 exit，主线程会一起退出吗？

取决于用哪个“退出”：

| 写法 | 效果 |
|---|---|
| `sys.exit()` | 只是在当前线程里抛一个 SystemExit 异常，**只结束监督者线程自己**，主线程照常运行 |
| `os._exit()` | 直接调用操作系统的退出，**整个进程立刻结束，进程里所有线程一起消失**，包括卡住的主线程 |

所以方案用的是 `os._exit()`。Python 没有“从一个线程杀掉另一个线程”的办法，只能结束整个进程；
这也是为什么每道题要在独立的子进程里跑（Celery prefork）：结束的只是这一个子进程，
Celery 主进程和其他子进程不受影响，主进程会立刻补一个新的子进程。

`os._exit()` 不会执行 `finally`、不会关闭连接，所以它只用在“已经确认卡死”的时候。资源由操作系统和对方兜底：
内存和网络连接由操作系统回收，PG 发现连接断开会回滚未提交的事务，Redis 的模型并发名额到期自动收回。

反过来，如果卡死的是**心跳线程**本身（主线程正常）：没人续租 → 租约过期 → 别的 worker 接管 →
主线程下一次提交步骤时 epoch 不对，被拒绝，自己停下（第五节）。
