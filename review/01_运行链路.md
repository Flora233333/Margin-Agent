# 运行链路：什么拉起什么，什么提供服务

更新：2026-10-04（M0.5 结束时的状态；M1 会加 Redis、API、worker）

## 一、全景：东西都在哪

```text
Windows 10（你的电脑）
│
├── D:\competition\margin-agent\                代码仓库（Windows 上编辑）
│   ├── src\  scripts\  tests\                  Python 代码，在 Windows 上运行
│   ├── models\Qwen3-Embedding-0.6B-Q8_0.gguf   embedding 模型（唯一一份）
│   ├── .cache\bm25\  .cache\chroma\            BM25 缓存、v2 索引原件
│   └── compose.yaml                            告诉 Docker 要起哪些容器
│
├── D:\competition\finetune\data\               语料 blocks.jsonl、别名表（只读）
│
└── WSL2：一台 Ubuntu 虚拟机（只因为 Docker 装在这里）
    │
    ├── dockerd：Docker 守护进程，虚拟机开机时由 systemd 自动启动
    │   ├── 容器 postgres：PostgreSQL 18 + pgvector
    │   │       数据存在 Docker 卷 margin-agent_pgdata
    │   └── 容器 embedding：llama.cpp 服务（CPU）
    │           通过 /mnt/d 只读读取上面那份模型
    │
    └── 整台虚拟机存成一个文件：
            C:\Users\Flora\AppData\Local\Packages\
            CanonicalGroupLimited.Ubuntu22.04LTS_...\LocalState\ext4.vhdx

外部：学校模型网关（DeepSeek 主用 / GLM 备用），HTTPS，地址和密钥只在 .env
```

## 二、启动链：谁拉起谁

```text
你在 Windows 终端执行：
  wsl -d Ubuntu-22.04 -- bash -lc "cd /mnt/d/competition/margin-agent && docker compose up -d --wait"
   │
   ▼
① WSL 虚拟机启动（如果还没开）
   │  虚拟机里的 systemd 开机自启 dockerd
   ▼
② docker compose 读 compose.yaml，让 dockerd 创建并启动两个容器
   ├─► postgres  ：初始化 / 打开数据卷 → 监听 5432 → 健康检查 pg_isready 通过
   └─► embedding ：从 /models 读 GGUF（约 3 秒）→ 监听 8080 → 健康检查 /health 通过
   │
   ▼
③ 端口转发：容器端口 → WSL → Windows 的 127.0.0.1
      127.0.0.1:5432   →  postgres
      127.0.0.1:18082  →  embedding
   │
   ▼
④ 你再执行（Windows，conda 环境 margin）：
  conda run -n margin --no-capture-output python scripts/run_episode.py "问题" --model DeepSeek
   → 一个 Python 进程，解完这一道题就退出
```

停止 / 自动恢复：

- WSL 空闲一段时间会自动关机，两个容器随之停止（数据卷里的数据不丢）。
- 两个容器都设了 `restart: unless-stopped`：只要 WSL 和 dockerd 再次启动，容器会被自动拉起。
  所以平时只需运行任意一条 `wsl` 命令把虚拟机唤醒即可。

## 三、调用链：解一道题时，谁调用谁

```text
run_episode.py（Windows 上的 Python 进程）
 │
 ├─ 启动时准备
 │    读 .env → 加载语料（内存）→ 加载 BM25 缓存 + 别名表（内存）→ 连接 PG
 │
 └─ Agent 主循环 run_episode()：重复 ①②③，直到模型提交答案
      │
      ├─ ① 把对话历史发给模型
      │      run_episode.py ──HTTPS──► 学校网关（DeepSeek）
      │      返回：思考 + “调用工具 X(参数)”
      │
      ├─ ② 执行工具 X（ToolRegistry.execute：先校验参数）
      │      例：search_docs("宁德时代 2025 研发投入")
      │      ├─ BM25：内存里算分
      │      ├─ 实体别名：内存里精确匹配
      │      ├─ 向量：
      │      │    问题 ──HTTP :18082──► embedding 容器
      │      │         返回 1024 维向量（约 0.2 秒）
      │      │    向量 ──SQL :5432────► postgres 容器
      │      │         返回最相近的 256 个文档块（约 45 毫秒）
      │      └─ 三路结果用 RRF 融合 → 前 8 个文档
      │
      ├─ ③ 工具结果作为一条消息追加到对话历史 → 回到 ①
      │
      └─ 结束：模型调用 finalize（提交答案）或 escalate（放弃作答）
             打印答案和统计
```

其他工具（read_section 读原文、cite 引用、compute 计算……）只用内存里的语料，不连任何服务。

## 四、谁提供什么服务

| 服务 | 在哪运行 | 由谁拉起 | 地址 | 被谁调用 | 做什么 |
|---|---|---|---|---|---|
| PostgreSQL + pgvector | WSL 的 Docker 容器 | docker compose | 127.0.0.1:5432 | DenseSearcher（向量检索） | 存 17,596 个文档块的向量；M1 起还存任务、步骤等业务数据 |
| embedding（llama.cpp） | WSL 的 Docker 容器 | docker compose | 127.0.0.1:18082 | EmbeddingClient | 把“问题”变成 1024 维向量 |
| 学校模型网关 | 校外 | — | .env 里配置 | OpenAICompatibleClient | 大模型：思考 + 决定调用哪个工具 |
| run_episode.py | Windows，conda 环境 margin | 你手动运行 | — | — | 解一道题（M1 改为 API 收题 + 后台 worker 执行） |

## 五、为什么是两个容器，而不是一个容器同时跑 PG 和 embedding

“一条命令拉起”靠的是 **docker compose**，不是“把东西装进同一个容器”。
compose 管理的是一组容器（一个 project），`docker compose up` 一次就把它们全部起来。

Docker 的惯例是**一个容器只跑一个服务（一个主进程）**，原因：

1. **各自独立的生命周期**：embedding 挂了，Docker 只重启它，PG 不受影响；升级 llama.cpp 只换它的镜像。
2. **直接用官方镜像**：PG 和 llama.cpp 都有官方镜像，拿来就能用。合成一个容器得自己写镜像，
   还要装一个“进程管理器”（如 supervisord）同时看管两个进程，这正是 Docker 想避免的事。
3. **健康检查、日志、资源限制各管各的**：`docker compose logs embedding` 只看它的日志；
   以后可以只给 embedding 限 CPU。
4. **能单独扩展或搬走**：将来 embedding 可以多开几份，或者挪到另一台机器，PG 不用动。

M1 之后 compose 里会有 5 个服务（postgres、redis、embedding、api、worker），依然是一条命令全部启动。

## 六、常用命令

```bash
# 启动 / 查看 / 看日志 / 停止（都在 WSL 里执行，前缀省略：wsl -d Ubuntu-22.04 -- bash -lc "cd /mnt/d/competition/margin-agent && ..."）
docker compose up -d --wait
docker compose ps
docker compose logs -f embedding
docker compose stop          # 停容器，数据保留
docker compose down          # 删容器，数据卷保留；加 -v 才会连数据一起删（慎用）
```
