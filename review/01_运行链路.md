# 运行链路：什么拉起什么，什么提供服务

更新：2026-10-06（M2 结束时的状态：8 个服务 + 前端开发服务器；任务队列是 RabbitMQ；SSE 由 PG 通知驱动，思考片段经 Redis 实时推送）

## 一、全景：东西都在哪

```text
Windows 10（你的电脑）
│
├── D:\competition\margin-agent\                代码仓库（Windows 上编辑）
│   ├── src\  scripts\  tests\  migrations\     Python 代码和数据库迁移
│   ├── web\app\                                前端（React）；npm run dev 在 Windows 上起 Vite 开发服务器 :5173
│   ├── Dockerfile                              应用镜像：api / worker / dispatcher / migrate 共用
│   ├── compose.yaml                            告诉 Docker 要起哪些容器
│   ├── models\Qwen3-Embedding-0.6B-Q8_0.gguf   embedding 模型（唯一一份）
│   └── .cache\bm25\  .cache\chroma\            BM25 缓存（worker 容器也挂载它）、v2 索引原件
│
├── D:\competition\finetune\data\               语料 blocks.jsonl、别名表（只读，挂载给 worker）
│
└── WSL2：一台 Ubuntu 虚拟机（只因为 Docker 装在这里）
    │
    └── dockerd：Docker 守护进程，虚拟机开机时由 systemd 自动启动
        │
        ├── 基础服务（官方镜像）
        │   ├── postgres   PostgreSQL 18 + pgvector，数据在 Docker 卷 margin-agent_pgdata
        │   ├── rabbitmq   Celery 的任务队列，数据在 Docker 卷 margin-agent_rabbitmqdata
        │   ├── redis      实时思考片段的 pub/sub（M1.5 起不再是任务队列）
        │   └── embedding  llama.cpp（CPU），只读挂载上面那份模型
        │
        └── 应用服务（同一个镜像 margin-app，启动命令不同）
            ├── migrate     执行数据库迁移，完成后退出
            ├── api         FastAPI，收请求、读写数据库
            ├── dispatcher  把 outbox 投递到 RabbitMQ；每 15 秒巡检过期租约 + 对账补发
            └── worker      Celery，4 个子进程，真正执行 Agent

外部：学校模型网关（DeepSeek 主用 / GLM 备用），HTTPS，地址和密钥只在 .env，
      由 compose 在运行时注入容器（不进镜像）
```

## 二、启动链：谁拉起谁

```text
你在 Windows 终端执行：
  wsl -d Ubuntu-22.04 -- bash -lc "cd /mnt/d/competition/margin-agent && docker compose up -d --build --wait"
   │
   ▼
① WSL 虚拟机启动（如果还没开），systemd 自启 dockerd
   │
   ▼
② docker compose build：按 Dockerfile 构建应用镜像 margin-app（代码没变时直接用缓存）
   │
   ▼
③ 按 depends_on 的顺序启动：
   │
   ├─► postgres、rabbitmq、redis、embedding 先起，各自健康检查通过
   ├─► migrate：等 postgres 健康 → alembic upgrade head → 退出（状态码 0）
   │
   │   下面三个都要等 migrate 成功退出后才启动
   ├─► api：监听 8000，健康检查 /health
   ├─► dispatcher：等 rabbitmq 健康；LISTEN outbox，平时等通知，最多 10 秒自己扫一次 outbox
   └─► worker：等 rabbitmq 健康；4 个子进程待命；第一次接到任务时才加载语料和 BM25（约 2 秒）
   │
   ▼
④ 端口转发到 Windows 的 127.0.0.1：
      5432 → postgres    5672 → rabbitmq（15672 管理界面）    6379 → redis
      18082 → embedding    8000 → api
```

停止 / 自动恢复：

- WSL 空闲一段时间会自动关机，所有容器随之停止（数据卷里的数据不丢）。
- 除 migrate 外都设了 `restart: unless-stopped`：WSL 和 dockerd 再次启动时自动拉起。
  所以平时只需运行任意一条 `wsl` 命令把虚拟机唤醒。

## 三、调用链：提交一道题之后发生什么

```text
浏览器 http://localhost:5173（Vite 开发服务器：页面文件自己出，/api/... 去掉前缀后转发给 api）
 │
 │ ① POST /api/runs   请求头 Idempotency-Key（前端生成，失败重试时复用）
 ▼
api
 │  一个事务里写 3 张表：runs、attempts（pending）、outbox（pending），再写一条事件，
 │  并 NOTIFY outbox（事务提交时才发出）
 │  立即返回 202 {"run_id": 1}
 │
 ▼
dispatcher（被通知叫醒，实测 10 毫秒级；没有通知时最多 10 秒自己扫一次）
 │  ② 从 outbox 取出 pending 记录 → 往 RabbitMQ 发一条消息“执行 attempt 1”
 │     → 等 RabbitMQ 回“收到了”（发送确认）→ 标记 sent
 ▼
rabbitmq（持久队列 celery；worker 执行完才确认，没确认的消息在 worker 断开时回到队列）
 │
 ▼
worker 的某个子进程
 │  ③ 领取：一条条件 UPDATE，attempt 从 pending 改成 running，拿到 epoch
 │     （同一条消息到了两次：第二次领取失败，直接跳过）
 │  ④ 启动续租线程：每 15 秒把租约往后推 90 秒
 │  ⑤ 运行 Harness（和脚本里同一套代码）：
 │      ├─ 调模型 ──HTTPS──► 学校网关（流式；10s 连接 / 60s 等数据 / 180s 总时长）
 │      ├─ 执行工具，例如 search_docs：
 │      │    BM25、别名在内存里算；向量：问题 ──► embedding 容器，向量 ──► postgres
 │      └─ 每完成一步：一个事务里 校验 epoch + 续租 + 写 steps + 写事件
 │         （epoch 不对 = 执行权已被取代 → 回滚并停止）
 │  ⑥ 结束：写最终答案（或错误），run 状态改为 completed / failed
 ▼
postgres（所有结果都在这里）
 ▲
 │  ⑦ GET /api/runs/1/events?after=0（SSE，长连接）：
 │     · worker 每提交一步，同一事务里 NOTIFY run_events → api 进程的 LISTEN 线程叫醒这个连接 → 按 seq 查库推送
 │     · 模型逐字输出的思考：worker PUBLISH 到 redis 的 run:1:live → api 订阅后原样转发（event: delta，不落库）
 │     · 空闲 10 秒：兜底查一次库，并发心跳 event: ping；前端 25 秒什么都没收到就用 ?after=最后的 seq 重连
 │     · 执行结束后关闭；刷新页面就是从 after=0 重新收一遍
 │  ⑧ GET /runs/1：题目、每次执行、每一步
 │
浏览器（时间线、回答、引用旁注都由这些事件算出来）
```

出事时：

- worker 进程死了：没人续租，租约 90 秒后过期 → dispatcher 的巡检把 attempt 判为失败、epoch 加 1
  （实测 86 秒）。用户可以点“重新生成”。M4 改成由别的 worker 从断点接管。
- RabbitMQ 连不上 / 拒收 / 迟迟不确认：outbox 记录保持 pending，dispatcher 隔 2、4、8……最多 60 秒再试。
- 消息在 RabbitMQ 里丢了（队列被清空等）：attempt 停在 pending；dispatcher 每 15 秒对账，
  “比它晚投递的已被领取”或“队列为空”且超过 2 分钟就补发（实测清空队列后 13 秒补发）；补 3 次仍不行判 `delivery_lost`。
- 模型网关报错或超时：这次执行判为失败，错误只记状态码（如 `llm_http_502`），页面显示失败说明。
- api 重启或连接断了：worker 照常执行、事件照常写库；页面 25 秒内发现连接已断（心跳收不到），
  用 `?after=最后的 seq` 重连，把漏掉的事件补齐（M2 实测：停 api 6 秒，事件 1–14 连续无重复）。
- Redis 挂了：只是看不到逐字的思考，每一步结束后的完整内容照常显示。

## 四、谁提供什么服务

| 服务 | 由谁拉起 | 地址（本机） | 被谁调用 | 做什么 |
|---|---|---|---|---|
| postgres | compose | 127.0.0.1:5432 | api、worker、dispatcher、脚本、测试 | 业务数据（任务、步骤、事件、outbox）+ 向量 |
| rabbitmq | compose | 127.0.0.1:5672、15672 | dispatcher 发消息、worker 收消息、浏览器看管理界面 | Celery 的任务队列 |
| redis | compose | 127.0.0.1:6379 | worker 发、api 收思考片段 | 实时推送（pub/sub，不保存） |
| embedding | compose | 127.0.0.1:18082 | worker / 脚本里的 EmbeddingClient | 把问题变成 1024 维向量 |
| migrate | compose，跑完退出 | — | — | 把数据库结构升级到最新迁移 |
| api | compose | 127.0.0.1:8000 | Vite 转发的浏览器请求、curl | 提交、查询、历史列表、重新生成、SSE |
| Vite 开发服务器 | 你手动 `npm run dev` | localhost:5173 | 浏览器 | 前端页面；/api 转发给 api（上线后由 Nginx 做，M6） |
| dispatcher | compose | — | PG 的 NOTIFY 叫醒它 | 投递 outbox、巡检过期租约、对账补发 |
| worker | compose | — | rabbitmq 里的消息 | 执行 Agent，每一步写库 |
| 学校模型网关 | 校外 | .env 里配置 | worker / 脚本 | 大模型：思考 + 决定调用哪个工具 |
| run_episode.py | 你手动运行 | — | — | 不经过服务、直接解一道题（调试用） |

## 五、为什么是多个容器，而不是一个容器跑所有东西

“一条命令拉起”靠的是 **docker compose**，不是“把东西装进同一个容器”。
compose 管理的是一组容器，`docker compose up` 一次就把它们全部起来。

Docker 的惯例是**一个容器只跑一个服务（一个主进程）**，原因：

1. **各自独立的生命周期**：worker 挂了，Docker 只重启它，API 照常响应；升级 llama.cpp 只换它的镜像。
2. **直接用官方镜像**：PG、RabbitMQ、Redis、llama.cpp 都有官方镜像，拿来就能用。
3. **健康检查、日志、资源限制各管各的**：`docker compose logs -f worker` 只看 worker 的日志。
4. **能单独扩展**：任务多了就多开几个 worker 容器，API 和数据库不用动。

api、worker、dispatcher、migrate 用的是**同一个镜像**（同一份代码），只是启动命令不同，
这样四者的代码版本永远一致。

## 六、常用命令

```bash
# 都在 WSL 里执行，前缀省略：wsl -d Ubuntu-22.04 -- bash -lc "cd /mnt/d/competition/margin-agent && ..."
docker compose up -d --build --wait   # 构建并启动全部（改了代码后也用它）
docker compose ps                     # 看状态
docker compose logs -f worker         # 看 worker 日志
docker compose restart worker         # 只重启 worker
docker compose stop                   # 停容器，数据保留
docker compose down                   # 删容器，数据卷保留；加 -v 才会连数据一起删（慎用）
```
