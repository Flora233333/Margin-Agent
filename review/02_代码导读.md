## 二、建议阅读顺序（约 2–3 小时）

按“一道题怎么被解出来”的顺序读，每一步都能接上上一步。

| 顺序 | 文件 | 读什么 | 核心概念 |
|---|---|---|---|

| 2 | `harness/prompt.py` + `prompts/system_rc6c.txt` | 模型一开始看到什么 | 提示词是“模型接口” |
| 3 | `harness/tools/base.py` | 一次工具调用的完整流程 | 参数校验、错误不抛给程序而是**返回给模型修正** |

| 5 | `harness/tools/args.py` | 参数怎么校验 | Pydantic、`extra="forbid"` |
| 6 | `harness/tools/search.py` | 检索工具给模型返回什么 | 口径信号（母公司 vs 合并） |

## 三、一道题的数据流（对应上面的文件）

```text
run_episode.py
  │  组装：Corpus + HybridRetriever(BM25, Alias, Dense) + OpenAICompatibleClient
  ▼
loop.run_episode(task, llm, registry)
  │  messages = [system 提示词, 题目]                       ← prompt.py
  │  循环：
  │    response = llm.chat(messages, 十个工具说明)          ← llm/client.py
  │    检查：每轮必须恰好调用 1 个工具
  │    result = registry.execute(工具名, 参数JSON)           ← tools/base.py
  │               ├ args.py 校验参数，不合格 → bad_args 返回给模型
  │               ├ 调用具体工具 search / reading / actions
  │               └ 包装成 {"ok": true, "data": …} 或 {"ok": false, "error": …, "hint": …}
  │    write_note 成功 → 丢掉历史，只留 [system, 题目, 最新笔记]（压缩）
  │    否则 → 把 result 作为 tool 消息追加到 messages
  │    检查停止条件（打转、重复报错、轮数用完……）
  │    finalize / escalate 成功 → 结束
  ▼
Trace：每一轮的思考、工具、参数、结果、耗时、token
```

## 五、review 时请重点看的地方

1. **`loop.py` 的停止条件**：7 种停止原因的阈值（打转 3 次、同错 3 次、格式错 6 次、30 轮）都照搬 RC6-C，
   是自训模型训练时的规则，改动会让评测结果不可比。
2. **`tools/base.py` 的错误处理**：工具内部的 `KeyError / ValueError / ArithmeticError` 统一转成
   `invalid_request` 返回给模型——这是有意的“错误恢复”。其他异常（如网络错误、TypeError）会直接抛出。
   代价：程序 bug 如果恰好也抛 KeyError，会被当成参数问题交给模型，日志里不显眼。
3. **`dense.py` 的精确检索**：不建 HNSW 索引的理由见 D15（数据量小、近似检索会漏结果）。
4. **两份“模型接口”文件**：`system_rc6c.txt`、`tool_schemas.json` 原样来自 RC6-C，不在本项目里改。
