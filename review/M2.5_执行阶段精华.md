## 1. 一句话

worker 领到题以后，**每做完一件事就在一个事务里“校验执行权 + 写结果 + 写事件”**：
领取（claim）→ 理解题目（另一个线程）→ Harness 每一步（commit_step，带引用编号）→ 交答案（引用提醒、猜格式软校验）
→ 撰写回答（流式 + 代码校验）→ 结束（finish）。任何一步发现执行权已被取代（LeaseLost），立刻停下、什么都不再写。
重新生成就是给同一道题再建一个 attempt，走一遍同样的流程，旧的执行原样保留。

## 3. 几条关键规则

### 3.1 `_fence`：每次写库都先确认“我还是执行者”

```python
update(Attempt).where(Attempt.id == lease.attempt_id,
                      Attempt.lease_epoch == lease.epoch,   # epoch 还是我领的那个
                      Attempt.status == "running")
# 更新到 0 行 → raise LeaseLost → 外层事务回滚，这一步的步骤和事件全部作废
```

`commit_step`、`save_understanding`、`finish`、`fail` 都先走它。`commit_step` 顺便把 `lease_until` 往后推 90 秒，所以每写一步也算续了一次租。
worker 收到 `LeaseLost` 就直接 return，不写失败（`worker.py:209-212`）：执行权已经是别人的了，状态由别人决定。

### 3.2 引用编号（`citations.py`）：后端编，前端照用

三条规则：
1. 只给**通过校验**的 cite 编号（`ok` 且 `grounded=true`）；
2. 同一处原文（同文档、同块、同一段匹配文字）引两次，只编一个号；
3. 按出现顺序，从 1 开始。

M2 时这套规则写在前端，M2.5-1 挪到后端。原因是撰写回答也要用同一套编号：回答里的 [2] 必须对上右侧第 2 张来源卡片。规则只放在后端一处，就不会两边算出不一样的号。
worker 每写一步问一次 `CitationNumbers.number()`，号码跟着 step 事件下发。`compose` 用同样的规则从头重算一遍，结果相同。

### 3.3 引用提醒（`actions.finalize`）

```
第一次 finalize，产品模式（require_citation）且一次 cite 都没成功
  → ToolError("citation_required")：退回，提醒先引用；如果确实没有可引的原文，再交一次
第二次 finalize → 不管补没补都收下；没补的结果里加 "uncited": true，页面写“本回答没有引用原文”
```

只提醒一次，所以不会触发“同一个错误连续 3 次就停”的规则。评测模式（不带 require_citation）完全不受影响。

### 3.4 猜格式的“软校验”（D25，`worker._tools_with_guessed_format`）

产品里的题没有给定答案格式，用理解题目猜的格式。finalize 被替换成下面这个流程：

```
按猜的格式规范化 → 成功：照常
                   ↓ 失败（answer_format_invalid）
去掉单位再试（单位要和结论说明末尾括号里的一字不差）
  例：说明“…经营活动现金流量净额（亿元）”，答案“1,332.20亿元” → “1,332.20”，记 unit_removed = "亿元"
                   ↓ 还是不行
按文本收下，记 answer_format_fallback = 猜的格式，页面按文本显示
```

**不退回让模型改**：主流程的模型看不到格式，只会看到“没法按 date 规范化”，于是开始猜系统要什么，把对的答案改成别的（run 66 被退回 4 次）。
理解题目还没跑完时，`guess()` 会等它的结果（平均 6 秒；Harness 跑到 finalize 通常已经一两分钟，几乎不用真等）。重新生成时直接用库里存的结果。

### 3.5 撰写回答的输入和校验（`compose.py`）

- **输入**：问题、提交结果、编号好的引用原文（前后各带 60 字；引的是表格的一行时，前文换成表头，否则看不出是哪一列）、成功的计算、最新的工作笔记。**不给每一步的思考**。
- **校验**：不存在的 [n] 删掉；数字去掉千分位以后，要能在问题、引用原文、计算、提交的答案里找到，找不到的记进 `unverified`（不删，可能只是换了写法）。
- **失败**：网关报错、超时，或者正文为空（思考型模型偶尔把 token 全用在思考上）→ 返回 `{"error"}`，页面退回显示“短答案 + 依据列表”，这道题仍算完成。

## 4. E 段：重新生成

```
前端点“重新生成” → POST /runs/{id}/regenerate
后端 runs.regenerate（runs.py:114-133）：
  SELECT … FOR UPDATE 锁住这道题        ← 两个请求同时到，排队执行
  还有 pending / running 的执行？→ 409 RunBusy（“这道题还在执行中”）
  attempt_no = 最大值 + 1，_enqueue_attempt(trigger="regenerate")
    → 新 attempt + outbox + NOTIFY dispatcher + attempt_queued 事件，同一个事务
前端：成功后 reopen()，新开 EventSource，?after=已收到的最后 seq
      （原来的流在上一次执行结束时已经关了，新开的流没法自己设 Last-Event-ID，所以用 after）
worker：claim 时发现 runs.title 已有 → 不再理解题目，用库里存的标题和猜的格式
```

| 要点 | 说明 |
|---|---|
| 旧执行全部保留 | 页面上显示“第 1 次执行”“第 2 次执行（重新生成）”，更早的只留结论 |
| 来源只属于最近一次 | 右侧来源卡片和 [n] 只对应最新的执行，旧的不再标引用编号 |
| 旧片段不会串进来 | 新执行的 epoch 不同，前端只显示 (attempt_id, epoch) 和当前执行一致的片段 |
| 为什么用 FOR UPDATE | 不锁的话，两个请求可能同时看到“没有进行中的执行”，各建一个 |
| 按钮一直能点 | 允不允许由后端判断（409）；前端状态可能是旧的，例如另一个标签页刚点过 |

## 5. 失败了会怎样（这一段相关的）

| 出事的地方 | 结果 | 用户看到 |
|---|---|---|
| 理解题目失败 | 退回“问题前 20 字 + 文本格式”，继续答题 | 标题是问题原句的开头，结论按文本显示 |
| Redis 发片段失败 | 这次执行后面不再发片段 | 没有逐字效果，每一步结束时完整思考照常出现 |
| 模型网关报错、超时（Harness 里） | `lease.fail` → attempt failed，写 `attempt_failed` | 失败说明 +“重新生成” |
| 撰写回答失败 | `written = {"error"}`，执行仍算完成 | 短答案 + 依据列表 |
| 执行权被取代（LeaseLost） | worker 立刻停下，不写任何东西 | 由巡检或新的执行决定（见 M1.5 / M1.6 文档） |
| 交答案没引用 | 提醒一次，第二次照收，标 uncited | “本回答没有引用原文” |
| 猜的格式对不上 | 先去单位，再按文本收下 | 结论按文本显示 |

## 6. 值得记住的设计取舍

1. **写结果和写事件放在同一个事务**：页面上看到的永远和库里一致；断线重连按 seq 补发，不会多也不会少。
2. **fencing token（epoch）挡住被取代的 worker**：数据库是唯一的裁判，不靠 worker 自觉。
3. **规则只放一处**：引用编号挪到后端，前端和撰写回答用同一份。
4. **外部模型调用的失败分级处理**：主流程（Harness）失败 → 整题失败；附加环节（理解题目、撰写、实时片段）失败 → 退回默认值，题照常完成。
5. **对模型宽松、对结果严格**：引用只提醒一次，格式对不上不退回；模型写出的 [n] 和数字由代码校验。
