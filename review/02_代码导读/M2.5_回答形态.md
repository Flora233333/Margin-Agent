# M2.5 回答形态：导读

目标（PLAN §5.8、D23）：把“考试式的短答案”变成设计稿那样“带出处的回答”——大号结论 + 带 [1][2] 的段落 + 口径说明，
同时不改模型接口（系统提示词、十个工具的说明）、不破坏评测（E80 仍按 finalize 的短答案打分）。
做法是在 Harness 前后各加一次模型调用（同一个模型、独立的提示词）：

```text
领取 attempt
  -> ① 理解题目（和 Harness 并行）：标题、结论说明、答案格式
  -> ② Harness（原样）：检索、阅读、引用、计算、finalize；产品模式下没引用会被提醒一次
  -> ③ 撰写回答：把“已校验的证据”写成带 [n] 的回答，流式推给前端
  -> 代码校验回答（[n] 合法、数字有出处）-> 写库 -> 结束
```

每个提交一节，格式同前几份导读：改了什么、为什么、一个具体例子、怎么验证的、review 重点。

### M2.5-0：实验 E1–E5（只用 DeepSeek）

**为什么先做实验**：①②③ 的细节（撰写回答要给模型什么输入、引用提醒会不会让答题变差、理解题目准不准、
不经训练的模型能不能一次交齐）都是猜的，先用脚本跑一遍真实模型，按结果定方案，再写产品代码。

**改了什么**：新增 `scripts/experiments/m25/`，手动运行的实验脚本（和 `scripts/run_episode.py` 同类，不进测试，不进产品代码）。

| 文件 | 内容 |
|---|---|
| [common.py](../../scripts/experiments/m25/common.py) | 读题（E80 题干来自训练仓库的题集）、组装检索器和模型、跑一道题并存 JSON、不带工具的模型调用、2 并发、遇到 429 退避重试 |
| [evidence.py](../../scripts/experiments/m25/evidence.py) | 把一次执行的步骤整理成“证据包”（编号的引用 + 前后文、计算、笔记）；检查一段回答：删掉不存在的 [n]，找出没有出处的数字 |
| [e1_baseline.py](../../scripts/experiments/m25/e1_baseline.py) | E1：现有系统跑 5 道开放问题 + 5 道数值题 |
| [e2_compose.py](../../scripts/experiments/m25/e2_compose.py) + [prompts/compose_draft.txt](../../scripts/experiments/m25/prompts/compose_draft.txt) | E2：离线撰写回答，比较两种输入 |
| [e3_cite_reminder.py](../../scripts/experiments/m25/e3_cite_reminder.py) | E3：E80 抽 20 题，引用提醒开 / 关各跑一遍（把提醒包在 finalize 外面，不改 harness） |
| [e4_understand.py](../../scripts/experiments/m25/e4_understand.py) + [prompts/understand_draft.txt](../../scripts/experiments/m25/prompts/understand_draft.txt) | E4：80 道题干 + 10 道开放问题，判断答案格式、写标题 |
| [e5_finalize_v2.py](../../scripts/experiments/m25/e5_finalize_v2.py) | E5：实验里换一份 finalize 说明（多一个 answer_text），看模型能不能一次交齐 |
| [open_questions.json](../../scripts/experiments/m25/open_questions.json) | 10 道开放问题，带期望的答案格式 |

**为什么这样写**

- **不改 harness 也能做实验**：`ToolRegistry` 接受一张“工具名 → (实现, 参数模型)”的表和一份工具说明。
  E3 换掉表里 finalize 的实现（外面包一层提醒），E5 换掉工具说明并给 finalize 换一个多了 `answer_text` 的参数模型。
  产品代码一行没动，`harness/prompts/` 和 `tool_schemas.json` 也没动。
- **数字核对的“出处”不包括工作笔记**：笔记是模型自己写的，里面的数字没有经过 cite 校验。出处只算问题、引用原文（含前后文）、计算结果和提交的短答案。
- **429 重试**：同一天上午 4 并发正常，下午 4 并发全部 429、单个请求正常，说明网关对并发限流。实验改成 2 并发，429 时等 5、10、20、40、60 秒重试。
  产品里的重试由 worker 负责（M4 分层重试），这里只给实验用。
- **错误信息只记状态码**：httpx 的错误信息里带着网关地址；第一次运行时它被打进了 `.cache` 下的日志（不在仓库里），之后改成只记 `HTTP 429` 这样的状态码。

**一个具体例子**：E2 里 run 14（广晟控股 2022 年营业收入）的撰写结果（改提示词后）：

```text
广晟控股2022年营业收入为1204.63亿元。

根据合并利润表，2022年度“营业收入”行金额为12,046,275.40万元[1]，按万元折亿元为1204.63亿元。

口径说明：合并利润表中“营业收入”与“营业总收入”口径不同，本次采用“营业收入”行数据；若采用营业总收入口径，金额会有所不同[1]。
```

第一版提示词写出了“按计算列表……”“提交结果为……”这类内部用语，加了一条规则（第 8 条）后重跑 3 篇，不再出现。

**结果**（同 PLAN §5.8“实验结果”）

| 实验 | 结果 |
|---|---|
| E1 | 数值题 4/5（错的是 res_b_005：22.19% 交成 22.20%）；10 题都 cite 了；只写过 1 次笔记；open03 跑 352 秒只交了一个短语 |
| E2 | 输入 a：13 篇，非法 [n] 0、未核实数字 0，中位数 14.7 秒；输入 b 输入多 4 倍、1 篇有未核实数字 → 用输入 a |
| E3 | 同一批题开 / 关都是 15/19；只有 1 题被提醒（补引用后答对）→ 提醒照原方案上线 |
| E4 | 约 89/90（7 处不一致里 3 处是题集标注错误、3 处是“问多个数字”按规则判文本）；中位数 5.7 秒 → 和 Harness 并行 |
| E5 | 9/10 交了回答正文，非法 [n] 0，2 题有未核实数字，1 题用完轮数 → 不上线，作为以后 RL 的目标 |

**怎么验证的**：脚本都实际跑过一遍（结果在 `.cache/m25/`，报告是同目录下的 `e*_report.md`）；`ruff check scripts` 通过。
实验脚本不写测试（AGENTS.md：测试只覆盖产品代码的事故场景）。

**review 重点**

1. `evidence.py` 里的编号规则（只取通过校验的 cite、同一处原文只编一个号、按出现顺序）和前端 `citations.ts` 一致，M2.5-1 会把它搬到后端，成为唯一的一份。
2. E3 的“平均调用次数”开比关多 2.7 次，但只有 1 题真的被提醒；这是 DeepSeek 同一道题两次运行步数差异大（例如 9 步 vs 21 步），20 题的样本不足以比较调用数。
3. `correct()` 是简化判分（规范化后的字符串相等），正式准确率以 M5 的评测回放为准。

### M2.5-1：引用编号移到后端，随 step 事件下发；迁移 0003 给旧事件补编号

**改了什么**

- 新增 [src/margin/citations.py](../../src/margin/citations.py)：编号规则（只给通过校验的 cite 编号、同一处原文只编一次、按出现顺序），
  M2 时写在前端 `citations.ts`，现在搬到后端，成为唯一的一份。`CitationNumbers` 逐步编号，`number_all` 从一串步骤重新算（撰写回答用）。
- [worker.py](../../src/margin/worker.py#L98)：每次执行建一个 `CitationNumbers`，每写一步就问一次这一步的编号；
  [lease.py](../../src/margin/lease.py#L95) `commit_step` 多一个参数 `citation_no`，写进 step 事件。
- 新增迁移 [0003_step_event_citation_no.py](../../migrations/versions/0003_step_event_citation_no.py)：给迁移之前写下的 step 事件补上 `citation_no`。
- 前端 [citations.ts](../../web/app/src/citations.ts) `citationsOf` 只按 `citation_no` 显示，不再自己编号和去重；
  [timeline.ts](../../web/app/src/timeline.ts) 的 `StepEvent` 加字段 `citation_no`。引文前后文的截取（显示用）仍在前端。
- 测试：后端单元 [test_citations.py](../../tests/test_citations.py)（2 个）；集成 `test_step_events_carry_citation_numbers`（worker 跑一道有重复引用的题）、
  新文件 [test_migrations_pg.py](../../tests/test_migrations_pg.py)（先写旧格式数据、退回 0002、再升级）；前端 citations.test.ts 改为按后端编号。

**为什么**

- **为什么编号必须只有一份**：M2.5-4 的撰写回答在后端写出 `[2]`，前端右侧的第 2 张卡片必须是同一条引用。两边各写一套规则，
  只要有一处细节不同（例如去重的判断），[n] 就会指向别的原文——而且不会报错，只是悄悄指错。
- **为什么编号随事件下发，而不是加一列存在 steps 表里**：前端只读事件；撰写回答在后端，用 `number_all` 从步骤重新算一遍，
  规则相同、输入相同，结果就相同。少一列就少一处要保持一致的数据。
- **为什么要数据迁移**：旧的 step 事件没有 `citation_no`，前端按新规则读，会认为“没有一条引用有编号”，打开旧题时来源卡片全部消失。
  这是“改了数据格式”时的常规做法：要么代码兼容旧格式（以后永远背着两套），要么一次性把旧数据改成新格式。这里选后者。
- **迁移为什么复制一份规则，不 import 应用代码**：迁移文件写好后就不再改，应用代码会继续变。迁移依赖应用代码的话，
  几个月后在一个新库上从头执行全部迁移，0003 跑的是那时的新代码，结果可能和当初不一样，甚至因为函数改名而跑不起来。
- **为什么要专门测迁移**：conftest 每次从空库执行全部迁移，只能测出“表结构能建起来”；空表里没有行，数据迁移的逻辑一行都没执行。
  新测试先按旧格式写入事件，`downgrade` 到 0002 再 `upgrade`，0003 的循环才真正跑到。

**一个具体例子**

```text
run 41（迁移前的题）：来源卡片 1,2,3,4；过程区“引用 [1]…[4]”；回答 [1]…[4]，三处一致（编号由迁移 0003 补上）
run 43（新题，worker 编号）：模型引用了同一行表格两次
  第 6 步  引用 [1] | 营业收入 | 5,229,262.18 | … | 12,046,275.40 |     citation_no=1
  第 7 步  引用      | 营业收入 | 5,229,262.18 | … | 12,046,275.40 |     citation_no=null（重复，不编号）
  右侧只有一张卡片 [1]
```

**怎么验证的**

- 后端单元 53、集成 43（新增 2）、ruff 通过；前端 `npm test` 14（去重的测试移到后端）、build、lint 通过。
- 开发库：重建 migrate / worker / api 容器，迁移 0003 执行后 run 41 的 4 个 cite 事件分别带 1–4；浏览器打开 run 41、新跑 run 43，如上。

**review 重点**

1. `CitationNumbers` 是 worker 内存里的状态。M4 做“接管后从断点继续”时，新 worker 要先用库里已有的步骤（`number_all`）把它恢复出来，
   否则接管后的编号会从 1 重新开始。已在 worker.py 的注释里写明。
2. 迁移 0003 一次读出全部 step 事件、逐行更新。现在只有几千行；数据量很大时要分批，这里没做。
3. 编号只在 step 事件里，不在 steps 表里：`GET /runs/{id}` 返回的步骤没有编号，需要的地方用 `number_all` 算。

### M2.5-2：理解题目（标题、结论说明、答案格式），和 Harness 并行

**改了什么**

- 迁移 [0004_run_title.py](../../migrations/versions/0004_run_title.py)：`runs` 加 `title`、`answer_label`（可空）；`answer_format` 改为可空（空 = 等理解题目回填）。
- 新增 [understand.py](../../src/margin/understand.py) + [prompts/understand.txt](../../src/margin/prompts/understand.txt)（来自实验 E4 的草稿）：
  一次不带工具的模型调用，返回 `Understanding(title, label, answer_format)`；任何失败退回“问题前 20 个字 + text”。
- [llm/client.py](../../src/margin/llm/client.py)：新增 `complete()`（请求里没有 tools）；`chat()` 和 `complete()` 共用 `_send()`（流式 / 非流式）。
  撰写回答（M2.5-4）也用它。
- [lease.py](../../src/margin/lease.py#L120)：`Lease.needs_understanding`（`runs.title` 为空）；`save_understanding` 校验 epoch、写 runs、写 `run_understood` 事件，在同一个事务里。
- [worker.py](../../src/margin/worker.py#L90)：第一次执行时在 `ThreadPoolExecutor` 的线程里理解题目；没给格式时，把工具表里的 finalize 换成“先等格式再提交”的版本。
  [harness/tools](../../src/margin/harness/tools/__init__.py) 的 `build_registry` 多一个可选参数 `tools`（harness 本身没有别的改动）。
- [api.py](../../src/margin/api.py) / [runs.py](../../src/margin/runs.py)：提交时 `answer_format` 可选；列表和详情返回 `title`，详情还返回 `answer_label`。
- 测试：单元 [test_understand.py](../../tests/test_understand.py)（2 个）；集成 3 个（worker：格式来自理解、理解失败不影响答题、重新生成不再调用）+ 1 个（接口：不带格式也能提交）。
  [fakes.py](../../tests/fakes.py) 的 FakeLLM 多一个 `texts`，给 `complete()` 用。

**为什么**

- **为什么并行，而不是先理解再答题**：E4 中位数 5.7 秒。串行的话每道题首字晚 6 秒；并行时 Harness 第一步检索就已经开始，
  标题 8 秒左右出现在左栏。真正依赖它的只有 finalize（按格式规范化短答案），而那时通常已经过了一两分钟。
- **为什么包装 finalize，而不是在 Harness 里加一个“等待”**：harness 是从比赛项目移植来的、自训模型训练时的执行环境，尽量不碰。
  `ToolRegistry` 本来就是“工具名 → 实现”的一张表，换掉一项就行（实验 E3、E5 也是这样做的）。模型看到的工具说明一个字没变。
- **为什么评测回放不等**：评测题自带格式（题集标注），`held.task["answer_format"]` 不为空就用原来的表；理解题目照样跑（写标题），
  但 `save_understanding` 保留给定的格式，不会被模型的判断覆盖，评测结果不受影响。
- **为什么写库也要校验 epoch**：理解题目在另一个线程里，可能在执行权已被取代之后才返回。和 `commit_step` 一样先 `_fence`，
  旧 worker 写不进去；`LeaseLost` 在线程里吞掉即可，主线程下一次提交步骤时自己会发现并停止。
- **为什么 `with LeaseKeeper(...), ThreadPoolExecutor(...)` 这个顺序**：`with A, B` 退出时先退 B 再退 A。
  线程池退出会等理解题目的线程结束，这期间续租线程还在，写库时租约有效。
- **为什么 finish 前要等一下**：保证事件顺序是 `run_understood` 在 `attempt_finished` 之前，前端按事件流显示，
  不会出现“答案都出来了、标题还是问题原句”的瞬间。理解失败不会走到这里抛错：`understand()` 自己退回默认值。
- **为什么重新生成不再理解**：标题和格式是题目的属性，不是某次执行的属性；判断依据是 `runs.title` 是否为空。

**一个具体例子**（开发库 run 44，DeepSeek，提交时只带问题）

```text
POST /runs {"question": "广晟控股2022年的营业收入是多少亿元？"}
  8.1 秒  run_understood  title=广晟控股 2022 年营业收入
                          label=广晟控股 · 2022 年营业收入（亿元）  answer_format=num
  ……Harness 检索、阅读、引用（和上面同时进行）……
  181 秒  finalize 提交 1206.37（按 num 规范化成两位小数），attempt_finished
GET /runs  -> 列表里这道题的 title 是“广晟控股 2022 年营业收入”
```

**怎么验证的**

- 后端单元 55、集成 47（新增 4）、ruff 通过。迁移测试（退回 0002 再升级）现在也执行了 0004 的 downgrade / upgrade。
- 开发库：重建 migrate / worker / api 容器，`alembic_version` 为 0004；用接口提交 run 44，结果如上。
- 前端这次没改（仍然传答案格式，接口兼容）；M2.5-5 改成只有输入框，并显示标题。

**review 重点**

1. 理解题目和 Harness 用同一个 `llm` 对象、两个线程同时调用。`OpenAICompatibleClient` 每次请求不保存状态，
   底层 `httpx.Client` 是线程安全的；FakeLLM 的 `chat()` 和 `complete()` 也各用各的列表。
2. `_understand` 遇到 `LeaseLost` 返回 `"text"`：此时这次执行已经作废，返回什么都不会写库，只是让 finalize 包装函数不报错。
3. `save_understanding` 里的数据库错误（例如连接断开）会在主线程的 `understood.result()` 抛出，这次执行判为失败、用户可重新生成；
   没有专门为它写重试（M4 统一做）。

### M2.5-3：产品模式的引用提醒（提醒一次、第二次照收、标 uncited）

**改了什么**

- 迁移 [0005_run_require_citation.py](../../migrations/versions/0005_run_require_citation.py)：`runs.require_citation`（布尔，默认 true）。
- [harness/tools/actions.py](../../src/margin/harness/tools/actions.py) `finalize`：在“没搜索过不能交”后面加一条——
  任务带 `require_citation`、一条成功引用都没有、这次执行还没提醒过，就返回工具错误 `citation_required`；
  第二次照收，没有引用时结果里多一个 `"uncited": true`。[state.py](../../src/margin/harness/state.py) 多一个 `citation_reminded`。
- [lease.py](../../src/margin/lease.py) `claim` 把 `require_citation` 放进 task；[runs.py](../../src/margin/runs.py) / [api.py](../../src/margin/api.py) 提交时可以传 `require_citation`（默认 true），幂等比较也带上它。
- 测试：单元 3 个（提醒一次后照收并标记、补了引用不标记、关闭时结果和以前完全一样）；集成 1 个（开关从 runs 一路带到 finalize）。
  其他 worker 测试的假模型不引用，`submit` 默认关掉提醒。

**为什么**

- **为什么不硬性要求引用**：有的问题确实没有可引用的原文（例如问“有没有披露某事”，答案是没有）。硬性要求会让模型反复被拒，
  最后因 `repeated_tool_error` 停下，用户什么都看不到。提醒一次能救回“忘了引用”的情况（E3 里那一题补了引用、答对了），
  坚持不引用的照收，页面明确告诉用户“本回答没有引用原文”，由用户判断。
- **为什么改的是 harness 代码而不是像实验那样包一层**：实验时不想动产品代码；现在它是产品规则，和 `search_required` 是同一类（finalize 的前置条件），
  放在一起读最清楚。模型接口（系统提示词、工具说明）没变，只是产品模式下多一种工具错误，D23 已记录。
- **为什么是 runs 上的一列，而不是按“有没有给答案格式”推断**：推断是隐含的约定，以后评测换一种提交方式就悄悄失效。
  它是提交时决定的、这道题的属性，重新生成也沿用，所以和 `answer_format` 一样存在 runs 上。
- **为什么关闭时不加 `uncited` 键**：评测比较的是 finalize 的结果，关闭时结果要和加这条规则之前逐字节一样，E80 的历史数据才能直接比。
- **为什么只提醒一次就不会触发 `repeated_tool_error`**：那条规则要同一个错误连续 3 次；提醒只出现一次，第二次 finalize 一定成功（或者因为别的错误失败）。

**review 重点**

### M2.5-4：撰写回答（带 [n]、流式、进库前代码校验）

**改了什么**

- 新增 [compose.py](../../src/margin/compose.py) + [prompts/compose.txt](../../src/margin/prompts/compose.txt)（E2 定稿的提示词，原样复制）：
  - `citations_of`：用 `CitationNumbers` 编号（和右侧卡片同一套号），从读过的原文里截前后各 60 字；
  - `computations_of` / `latest_note` / `render`：证据包写成文字，格式和 E2 的输入 a 相同；
  - `check`：删掉不存在的 `[n]`，找出没有出处的数字；返回存库的 `{text, citations, unverified}`；
  - `compose`：调用 `complete()`（流式），失败或正文为空时返回 `{"error": ...}`。
- [worker.py](../../src/margin/worker.py)：Harness 交了答案或放弃作答后调用 `compose`，正文片段以 `kind="answer"` 推到 Redis，轮次排在最后一步之后。
- [lease.py](../../src/margin/lease.py) `finish` 多一个 `written`：存进 `attempts.final.written`，同一事务里先写 `answer_written` 事件、再写 `attempt_finished`。
- 原来 worker 里的 `_describe`（错误只记状态码）移到 [llm/client.py](../../src/margin/llm/client.py) 改名 `describe_error`，compose 也要用。
- [fakes.py](../../tests/fakes.py)：FakeLLM 的 `complete()` 按系统提示词区分“理解题目”和“撰写回答”（参数 `understand=`、`compose=`），不再按调用顺序。
- 测试：单元 [test_compose.py](../../tests/test_compose.py)（1 个）；集成 2 个（编号一致 + 校验后进库 + 事件顺序、撰写失败照常完成），
  实时片段的测试多断言一条回答正文。

**为什么**

- **为什么 FakeLLM 要按提示词区分**：理解题目在另一个线程里，和 Harness、撰写回答谁先调用 `complete()` 不确定。
  按顺序给回复，测试会偶尔拿错（理解题目拿到回答正文），这种“偶尔失败”的测试最难查。
- **为什么输入里不放答案格式和结论说明**：E2 验证过的输入 a 里就没有，结果已经够好（非法 [n] 0、未核实数字 0）。
  加进去还要等理解题目的结果，撰写回答就和它有了依赖，没有必要。
- **为什么校验删 [n] 却不删数字**：不存在的 [n] 在页面上是点了没反应的死链接，删掉没有信息损失；
  数字找不到出处可能只是写法不同（例如“约 1205 亿”），删了会把句子弄坏，所以只标记，页面上轻提示，并作为以后评测的指标。
- **为什么 answer_written 和 attempt_finished 在同一个事务里**：前端看到“结束”时，回答一定已经在了，
  不会有“答案区先空一下再出现”的中间状态；也不会出现回答写进去了、这次执行却因为租约丢失没结束的情况。
- **为什么撰写失败不让这道题失败**：短答案和依据已经齐了，回答只是更好看的呈现。退回短答案 + 依据列表，用户仍然能用；
  `written.error` 让页面提示“回答生成失败，可重新生成”（M2.5-5）。
- **为什么空正文也算失败**：思考型模型偶尔把 `max_tokens` 全用在思考上，`content` 为空；存一段空回答，页面会显示一个空白的答案区。

**一个具体例子**（开发库 run 45，DeepSeek）

```text
第 13 步 cite      [1] 营业收入 | … | 12,046,275.40 |
第 14 步 finalize  1204.63                                09:00:57
answer_written     （撰写 25 秒）                           09:01:22
  广晟控股2022年营业收入为1204.63亿元[1]。

  根据文档披露，营业收入项目2022年对应的金额为12,046,275.40[1]。
  citations [1]，unverified []
attempt_finished                                           09:01:22
```

**怎么验证的**

- 后端单元 59、集成 50（新增 2）、ruff 通过。
- 开发库：重建 worker / api 容器，提交 run 45，结果如上（理解题目 10 秒出标题，全程 176 秒）。
- 前端这次没改：`kind="answer"` 的片段和 `answer_written` 事件现在的页面会忽略，M2.5-5 显示。

**review 重点**

1. `check` 的数字核对是字符串包含（去掉千分位逗号后）：“120.5” 在出处里出现过就算核实，不管它在原文里指的是不是同一个东西。
   它能抓住“模型自己编的数字”，抓不住“数字对、指代错”。
2. 撰写回答的片段推送时还没校验，逐字显示时可能短暂出现之后被删掉的 `[n]`；`answer_written` 到达后前端用校验后的文字替换（同思考片段的规则）。
3. 撰写回答在 `LeaseKeeper` 里面执行，25 秒左右的调用期间续租照常；它不写库，执行权丢了也只是写好的回答随 `finish` 一起被拒。

- **为什么悬停连线从回答的右边缘出发**：和设计稿一致（demo.js 的 `drawConnector`），线只穿过空白，不像删除线一样压在正文上。

### M2.5-5 修订：作者试用反馈的三个问题

**1. 结束后右栏对齐过程区上沿（D24）** —— [Sources.tsx](../../web/app/src/components/Sources.tsx)

- 现象：结束后展开过程区，右栏整体往下走，上面一片空白。原因是卡片对齐的是回答里的 [n]，展开过程区把回答推下去，卡片跟着走。
- 改法：结束后的起点换成 `startOf()`（最近一次 `.work` 的上沿），卡片按编号一张接一张往下排；原来按 [n] 排序、取最大值的那段逻辑删掉了。
  过程区自己展开不影响起点（往下长）；重新生成过的题，上面更早的过程区展开会推动它，仍由 `workShift` 提前算出终点。
- 验证：run 47 收起 / 展开 / 再收起，过程区上沿和第一张卡片上沿都是 224px，卡片不动。

**2. 旁注里出现 `<sub>` 和 `![](images/…)`** —— [citations.ts](../../web/app/src/citations.ts)

- 这是语料本身的样子：年报 PDF 转 markdown 时，上下标变成 `<sub>` 标签，图片变成 `![](images/哈希.jpg)` 链接。数据没错，只是不该原样给人看。
- 改法：`readable()` 把标签去掉、图片换成“〔图片〕”，只改显示；先整理整段原文再截前后文，避免截断处留下半个标签。库里的原文、引文不动，溯源仍以原文为准。
- 撰写回答（后端）收到的证据仍是原文：模型读得懂这些标记，写出的回答里没有出现过它们。

**3. 思考流式输出完、下一步到达时，整段思考重新展开一遍** —— [Work.tsx](../../web/app/src/components/Work.tsx)、[StepItem.tsx](../../web/app/src/components/StepItem.tsx)

- 原因：过程区原来分几块渲染——`{步骤数组}` 和 `{live && <实时思考 key="t3">}`。step 3 到达后，完整思考（也是 key t3）出现在步骤数组里。
  **React 只在同一个数组的兄弟之间按 key 认出同一个元素**：两个 t3 在不同的位置，React 就删掉旧的、新建一个，新建的条目重播 0.5 秒的出现动画
  （`step-in`：从 0 高度展开），一长段思考从上往下重新展开，过程区整体跳一下。原来的注释“key 相同就会原地替换”是错的。
  工具调用没有这个问题：它只出现在步骤数组里，从不换位置。
- 改法：所有条目（理解题目、每一步的思考和工具、实时思考、撰写回答）先放进同一个数组 `items` 再渲染；
  思考的正文也一律用 `StreamingText`，step 到达时 `<p>` 不换成另一种元素，已经淡入完的文字原样留着。
- 验证：在 `.steps` 上挂 MutationObserver，统计执行中被删除的条目。同一道题（中国移动利润分配方案）旧代码删掉重建了多条思考，
  新代码（run 54，5 段思考）为 0；run 52 也为 0。

**review 重点**

1. 第 3 点是 React 列表渲染的一个通用规则（key 只在同一个数组里有效），面试常问“key 的作用”，这是一个真实例子。
2. 第 1 点之后，`anchorOf`（找 [n]）只剩悬停连线在用。

- 原因：刷新后历史事件一下子补发完，卡片数从 0 涨上去，`useAnnounce` 当成“新卡片出现”画线，那时引用那一步多半已滚出屏幕。
- SSE 在补发完历史之后发一个 `event: caught_up`（不带 id，不影响断点续传），前端收到才算“追上”；
  追上的那一次只记下当时的卡片数，之后增加的才画。追上和最后一批历史事件可能在同一次渲染里，所以那一次当成起点、不画。
- 测试：`test_sse_marks_end_of_backlog_then_forwards_live_thinking`（原来测思考片段的那个，顺序变成 历史 → caught_up → 片段 → 新事件）。
- 验证（run 61）：实时出现的卡片画了线；刷新后 2.5 秒内没有画线。

**4. 账目行加耗时** —— [RunPage.tsx](../../web/app/src/pages/RunPage.tsx)、[Answer.tsx](../../web/app/src/components/Answer.tsx)

- 事件里不带时间，用 `GET /runs/{id}` 每次执行的 `started_at / finished_at`：打开时已结束的直接有；看着它跑完的，结束时再取一次。
  一分钟以内写“14.8 秒”，以上写“2 分 56 秒”。

**一个踩坑**：验证时发现页面用的还是旧代码——脚本整文件重写后，开发服务器（Vite）的文件监听偶尔收不到通知，继续提供旧模块。
`touch` 一下文件就好了。第一轮“刷新不画线”的结论就是在旧代码上得出的，重新验证后才算数。

### M2.5-5 修订三：猜的答案格式不再卡住模型（D25）

**问题**（run 66，作者试用）：“有什么时间要求”被理解题目猜成了日期。主流程的模型看不到格式（`render_question` 只放题目和选项），
只在交答案时看到 finalize 说“没法按 date 规范化”。它第一次就交对了（第三十九条原文），被退回 4 次后开始猜“系统要一个日期”，
从施行日推出 2026-07-20、2028-01-20 交上去。页面于是用大号字显示两个法规里没有的日期。

**改了什么**

- [worker.py](../../src/margin/worker.py) `_tools_with_guessed_format`：产品里的题（没有给定格式）的 finalize 先按猜的格式试，
  `answer_format_invalid` 时改按文本收下，结果多一个 `answer_format_fallback`（猜的是什么）；没搜索过、没引用等别的前置条件照常退回。
- 迁移 [0006](../../migrations/versions/0006_run_guessed_format.py)：新列 `guessed_format`；`answer_format` 只放给定的格式。
  已有的、有标题的题（M2.5 之后在页面上提交的）把猜的格式挪过去。[lease.py](../../src/margin/lease.py) `save_understanding` 改写 `guessed_format`；
  `Lease.guessed_format` 给重新生成用。
- [prompts/understand.txt](../../src/margin/prompts/understand.txt)：date 只用于“问的就是某一天”；“有什么时间要求 / 期限多久”是 text。
  只改理解题目这一次调用的提示词，主流程的系统提示词和工具说明不动。
- 前端：格式取“给定的 > 猜的”；某次执行按文本收下了，那次的回答按文本显示（不放大号结论）；“提交答案”一步写明“按文本收下（自动判断的格式是…）”。
- 测试：集成 `test_answer_not_matching_guessed_format_is_accepted_as_text`（第一次执行和重新生成都一次收下）、
  `test_upgrade_moves_guessed_format_out_of_answer_format`（迁移 0006 的数据）；原来两个断言 `answer_format` 的测试改为 `guessed_format`。

**为什么要分两列**：如果猜的格式还写在 `answer_format` 里，重新生成时 `claim` 读到的格式“看起来是给定的”，又会严格校验，问题原样回来。
“格式是谁给的”是题目的一个真实属性，所以单独存，不靠别的列推断。

**怎么验证的**

- 真实模型：run 66 重新生成，猜的仍是日期，模型交的规定原文第一次就收下（`answer_format_fallback = date`），第 1 次执行当时被退回 4 次；
  重新提交同一道题（run 70），理解题目判为文本，回答区没有大号结论，正文是第三十九条的规定。

### M2.5-5 修订四：交卷后按“结论 → 正文”出场、数字滚动、理解题目不再顶一下

**问题**（作者试用）：大字比正文晚一拍——正文逐字写完、执行结束（`attempt_finished`）大字才突然插进来；数字也没有滚动。
“理解题目”那一项完成前一行、完成后两行，过程区整体跳一下。

**1. 交卷那一步到了就有结论** —— [timeline.ts](../../web/app/src/timeline.ts)

- 原来 `final` 只在 `attempt_finished` 里，而撰写回答在交卷之后还要十几秒。
- 现在成功的 finalize / escalate 这一步（step 事件）一到就记下 `final`，内容和之后 `attempt_finished` 带的相同
  （后端 loop.py：`trace.final = {name, ...这一步的结果}`），包括按文本收下时的 `answer_format_fallback`。
- “交卷了没有”的判断 `ended()` 从 Work.tsx 挪到 timeline.ts，reducer、Work、RunPage 共用一份。
- 测试：`交卷那一步到了就有结论：撰写回答的十几秒里，大字不用等执行结束才出现`。

**2. 出场顺序（同设计稿 demo.js 的 `play`）** —— [Work.tsx](../../web/app/src/components/Work.tsx)、[Answer.tsx](../../web/app/src/components/Answer.tsx)、[motion.ts](../../web/app/src/motion.ts)

```text
交卷 ─0.7s─> 过程区收起（0.5s）─> 结论行淡入 + 数字从 0 滚到答案（0.8s）─> 正文逐字出现 ─> 放完后账目行
```

- Work：交卷后停留 `FOLD_DELAY_MS` 再自动收起（用户手动点过就按用户的）。
- Answer：挂载时还在执行（= 交卷那一刻）才走这个顺序，用一个 `phase` 状态（folding → verdict → text）和定时器推进；
  打开一道已经结束的题直接全部显示（数字仍然滚一次）。两个组件共用的时间放在 motion.ts。
- 撰写其实在交卷后立刻开始，先到的正文攒着：`useTypewriter` 轮到正文时每 26ms 放 2 个字，积压多了每次放积压的 1/40；
  `[12]` 被切在中间时先不显示这半个编号。撰写结束（`answer_written`）换成校验后的文字，没放完的接着放；账目行、提示等放完再出现。
- 开放问题（text）不显示结论行；撰写中还不知道会不会失败，失败时的短答案结论行等结束后再显示。
- 百分比也滚动：`countableOf` 去掉 % 再判断是不是单个数，% 作为小一号的单位跟在后面。原来 `61.17%` 带着 % 过不了数字判断，所以不滚。

**3. 理解题目两行先占好** —— [StepItem.tsx](../../web/app/src/components/StepItem.tsx) `UnderstandItem`、[app.css](../../web/app/src/styles/app.css) `.one-line`

- 第一行：“正在理解题目…”上移淡出、“理解题目 “标题””从下方淡入，两段叠在同一格里（同过程区标题的 SwapLabel）。
- 第二行：理解中是一条扫光的占位条，结果到了淡出，同一位置淡入“答案格式 · 说明”。
- 每行只占一行，放不下用省略号，悬停看全文；`::before` 放一个零宽空格，只有占位条时也撑出一整行。打开已理解完的题不播切换。

**4. 顺带修的：收起过程区后满屏空白** —— [clean.css](../../web/app/src/styles/clean.css) `.connector`、[RunPage.tsx](../../web/app/src/pages/RunPage.tsx)

- 现象（长题，8 步的 run 76）：交卷后过程区收起，屏幕一片空白，结论在屏幕上方 4000px。
- 逐个量 `.app` 的子元素，撑高页面的是连线的 SVG：画线时它的高度被设成当时的整页高度（设计稿的写法），
  之后正文变矮它不变，`.app` 仍能滚到原来的深度，跟随滚动又把页面滚到底。原来收起发生在执行结束、页面会重新滚动，所以没暴露。
- 改成固定 1px 高、`overflow: visible` 画在框外，不再参与滚动高度。不能是 0：Chrome 不画高度为 0 的 SVG 框外的内容（实测线消失）。
- 右栏交卷后就按“结束后”排（`live` 改成“还没交卷”）：不会再有新卡片，过程区也收起了，卡片不用再吸顶。

**踩坑**：用 Python 字符串写 CSS 时，`"\200b"` 在 heredoc 里少了一层转义，变成了控制字符 + 字母 b，显示出来压在文字下面（截图里的“图解题目”）。
改完扫了一遍源码里的控制字符。

**怎么验证的**

- 真实模型逐帧采样（run 86，美的集团 2024 年资产负债率）：20.4 秒过程区已收起、结论透明度 0；0.5 秒内淡入、

  连线 SVG 先改成 0 高，悬停 [1] 的线不见了，改 1px 后正常画出（截图对比）。
