### M1.5-1：迁移 0002——outbox 加补发次数 + 部分索引

**改了什么**

- 新增 [migrations/versions/0002_outbox_redeliveries.py](../../migrations/versions/0002_outbox_redeliveries.py)：
  - `upgrade()`（[第 23 行](../../migrations/versions/0002_outbox_redeliveries.py#L23)）：outbox 加一列
    `redeliveries int not null default 0`，再建部分索引 `ix_outbox_sent_at`（只收录 `status='sent'` 的行）。
  - `downgrade()`：反过来删索引、删列。
- [src/margin/models.py](../../src/margin/models.py#L138)：`Outbox` 同步加上同一个索引和 `redeliveries` 字段
  （[第 146 行](../../src/margin/models.py#L146)）。

**为什么**

- 下一步的对账（PLAN §5.7 第二层）要记“这条 outbox 被补发过几次”，补到 3 次就不再补、把 attempt 判失败。
- 不复用已有的 `tries`：`tries` 是“发消息失败”的次数，dispatcher 用它算退避时间（2、4、8……秒）。
  如果补发也加到 `tries` 上，一条被补发过 3 次的记录下次发送失败时会直接退避 16 秒，两件事搅在一起。
- 部分索引（partial index）：普通索引收录表里每一行；部分索引只收录满足 `WHERE` 条件的行。
  水位线查询只看 `status='sent'` 且最近 1 小时投递的记录，所以只给已发送的行建 `sent_at` 索引，索引更小。
- `models.py` 和迁移要写同样的东西：迁移负责“真的去改数据库”，`models.py` 是 Python 代码眼里的表结构。
  两者不一致时 `alembic check` 会报差异——这就是为什么每次改表都要两边一起改。

**一个具体例子**

开发库里已有 M1 跑出来的数据（1 个 run、2 次执行、19 步、25 个事件、2 条 outbox、17,596 个向量），
版本号是 `0001`。执行 `alembic upgrade head`：

1. Alembic 读 `alembic_version` 表发现当前是 `0001`，只执行 `0002` 这一个文件；
2. `ALTER TABLE outbox ADD COLUMN redeliveries integer NOT NULL DEFAULT 0`：PG 11 起，加“带常量默认值”的列
   只改表的元数据，不重写已有的行；读旧行时 PG 直接给出默认值 0；
3. `CREATE INDEX ix_outbox_sent_at ON outbox (sent_at) WHERE status = 'sent'`；
4. `alembic_version` 改成 `0002`。

升级后两条旧 outbox 读出来是 `(1, 'sent', tries=0, redeliveries=0)`、`(2, 'sent', 0, 0)`，各表行数不变。

**怎么验证的**

- 空库：集成测试的 `engine` fixture 每次会话都新建 `margin_test` 并 `upgrade head`（现在会依次执行 0001、0002），
  24 个集成测试全部通过。
- 有数据的库：开发库升级前后各表行数相同（见上面的例子）；再 `alembic downgrade -1` 回到 0001、
  `upgrade head` 回到 0002，都成功。
- `alembic check` 输出 `No new upgrade operations detected.`（模型和数据库一致）。
- 这一步没有新增自动化测试：新列和索引还没有代码在用，下一步的对账测试会用到它们。

**review 重点**

1. 迁移文件的 `down_revision = "0001"`：Alembic 靠它把迁移串成一条链，知道 0002 要在 0001 之后执行。
2. `server_default="0"` 而不是 Python 侧的 `default=0`：前者写进数据库的列定义，旧行和别的程序插入的行也有值。

### M1.5-2：compose 加 RabbitMQ + 配置项 `MARGIN_BROKER_URL`

这一步只把 RabbitMQ 跑起来、把地址配好；worker / dispatcher 还没改，仍然走 Redis（下一个提交切换）。

**改了什么**

- [compose.yaml](../../compose.yaml#L74) 新增 `rabbitmq` 服务：
  - 镜像 `rabbitmq:4-management-alpine`（RabbitMQ 4.3.6 + 管理界面插件）；
  - `hostname: rabbitmq`（[第 81 行](../../compose.yaml#L81)）：固定主机名；
  - 两个端口只绑本机：5672 是 AMQP 协议端口（收发消息），15672 是管理界面；
  - 命名卷 `rabbitmqdata`（[第 90 行](../../compose.yaml#L90)）保存队列和消息；
  - 把 [deploy/rabbitmq/margin.conf](../../deploy/rabbitmq/margin.conf) 只读挂载为 `conf.d/20-margin.conf`
    （[第 92 行](../../compose.yaml#L92)），里面只有一行 `consumer_timeout = 3600000`；
  - 健康检查 `rabbitmq-diagnostics -q ping`。
- 应用服务的公共环境变量加 `MARGIN_BROKER_URL`（[第 19 行](../../compose.yaml#L19)），指向容器名 `rabbitmq`。
- [src/margin/settings.py](../../src/margin/settings.py#L44)：新增 `broker_url`，默认值指向本机 5672，
  本机跑脚本 / 测试时 `.env` 里不写也能用。
- [.env.example](../../.env.example)：加 `MARGIN_MQ_PASSWORD`、`MARGIN_BROKER_URL`，并把 Redis 的说明改成“M2 起推送思考片段”。

**为什么**

- 固定主机名（PLAN §5.7 第一层、STATUS 交接）：RabbitMQ 的节点名是 `rabbit@主机名`，
  数据目录 `/var/lib/rabbitmq/mnesia/rabbit@主机名` 也带着它。Docker 默认给容器的主机名是随机的容器 id，
  `docker compose up` 重建容器后主机名一变，RabbitMQ 会当成一个新节点、建一个新目录，旧的队列和消息就“不见了”
  （数据其实还在卷里，只是没人读）。
- `consumer_timeout`（确认期限）：worker 是“执行完才确认”，一道题最长可以跑到 Celery 硬时限 25 分钟。
  RabbitMQ 4 默认 30 分钟，余量太小；一旦触发，RabbitMQ 会关闭这个消费者的**整个通道**，
  通道上所有没确认的消息（也就是这个 worker 进程正在执行的任务）都会回到队列。所以设成 1 小时，保证正常执行永远不触发。
  配置文件放 `conf.d/` 是官方镜像推荐的做法：不用覆盖镜像自带的 `10-defaults.conf`，只追加自己的那一行。
- 账号密码沿用 PG 的写法：compose 从 `.env` 读 `MARGIN_MQ_PASSWORD`，没有就用开发密码 `margin_dev`。
  只绑 127.0.0.1，开发密码不会暴露到局域网。

**一个具体例子**

`docker compose up -d --wait rabbitmq` 之后：

```text
$ docker compose exec rabbitmq rabbitmq-diagnostics -q environment | grep consumer_timeout
      {consumer_timeout,3600000},          ← 配置文件生效了
$ docker compose exec rabbitmq rabbitmqctl -q status | grep "Node name"
Node name: rabbit@rabbitmq                 ← 节点名来自固定的主机名
$ curl -u margin:margin_dev http://127.0.0.1:15672/api/overview
{"management_version":"4.3.6", ...}        ← Windows 上能打开管理界面
```

**怎么验证的**

- `docker compose config -q` 通过（compose 文件语法正确）；rabbitmq 容器健康检查通过，见上面三条命令的输出。
- 单元测试 51 个、集成测试 24 个、ruff 全部通过（这一步没有改业务代码）。
- 没有新增自动化测试：只是部署配置，下一个提交切换 worker / dispatcher 后用“提交一道题能跑完”来验证。

**review 重点**

1. `hostname: rabbitmq` 和数据卷要一起用：只挂卷不固定主机名，重建容器后数据照样“丢”。
2. 地址末尾的 `//`：`amqp://用户:密码@主机:端口/虚拟主机`，默认虚拟主机的名字就是 `/`，所以写成两个斜杠。

### M1.5-3：worker / dispatcher 改用 RabbitMQ，打开发送确认

**改了什么**

- [src/margin/worker.py](../../src/margin/worker.py#L34)：broker 改读 `broker_url`；删掉 Redis 专用的
  `visibility_timeout`；保留 `task_acks_late=True`、`worker_prefetch_multiplier=1`（[第 39 行](../../src/margin/worker.py#L39) 起）；
  新增 `control_queue_exclusive` / `event_queue_exclusive`（[第 50 行](../../src/margin/worker.py#L50)）。
- [src/margin/dispatcher.py](../../src/margin/dispatcher.py#L78)：新增 `make_publisher(broker_url)`，返回一个
  “发出去、等到 RabbitMQ 确认才返回”的函数；`main()` 用它代替原来从 worker 导入的 `celery_app`
  （[第 116 行](../../src/margin/dispatcher.py#L116)），dispatcher 不再导入 worker 模块（也就不再间接导入 Harness）。
- `dispatch_once` 的时间从 `now()` 改成 `clock_timestamp()`（[第 69、73 行](../../src/margin/dispatcher.py#L69)）。
- [compose.yaml](../../compose.yaml#L145)：worker、dispatcher 的 `depends_on` 从 redis 换成 rabbitmq（等它健康再启动）。
- [pyproject.toml](../../pyproject.toml)：`celery[redis]` → `celery`（AMQP 客户端 `amqp` / `kombu` 本来就是 Celery 的依赖）。
- [tests/test_worker_pg.py](../../tests/test_worker_pg.py#L97)：“中转站不可用时退避”改用真实的 `make_publisher`。

**为什么，以及实现时实测出来的三件事**

PLAN §5.7 只写了“打开发送确认、except 加上拒收 / 未确认”。STATUS 交接要求“抛什么异常要实际验证后再写”。
我用一个小脚本对本机 RabbitMQ 做了三种故障（2026-10-06，celery 5.6.3 / kombu 5.6.2 / amqp 5.4.0 / RabbitMQ 4.3.6）：

| 故障 | 怎么制造 | 抛出的异常 | 耗时 |
|---|---|---|---|
| 连不上 | 连一个没人监听的端口 | `kombu.exceptions.OperationalError`（原因 `ConnectionRefusedError`） | Windows 上约 6 秒，Linux 上立即 |
| 拒收（nack） | 给队列加策略 `max-length=0, overflow=reject-publish` | 同上（原因 `amqp.exceptions.MessageNacked`） | 立即 |
| 迟迟不确认 | `rabbitmqctl set_vm_memory_high_watermark absolute 1MB` 触发内存告警，RabbitMQ 暂停所有发送方 | 同上（原因 `TimeoutError`） | 等确认超时 5 秒 |

结论和对应的改动：

1. **except 不用改**：三种都是 `kombu.exceptions.OperationalError`（kombu 把底层异常统一包装成自己的异常类型），
   M1 的 `except OperationalError` 已经覆盖。注释里写明了实测结果，测试用真实的 publisher 走了一遍“连不上”。
2. **必须加超时，否则 dispatcher 会永远卡住**：等确认默认没有上限；更隐蔽的是，即使给了 `confirm_timeout`，
   超时后 kombu 关闭通道时还要等 RabbitMQ 回一个“关闭好了”，告警期间等不到——实测进程卡在 `channel.close()` 里不动
  （用 `faulthandler` 打出的调用栈确认）。所以 publisher 的连接加了 socket 读写超时 10 秒（`read_timeout` / `write_timeout`），
   加上之后同样的故障 5 秒就抛异常、进入退避。
3. **关掉 Celery 自带的发送重试（`task_publish_retry=False`）**：Celery 默认失败后立即再试 3 次，告警时一次投递会卡
   4 × 5 = 20 秒；dispatcher 自己已经有“2、4、8……60 秒”的退避，一层就够了。

另外两处：

- **为什么 publisher 单独建一个 Celery 实例，而不是在 worker.py 的 `celery_app` 上打开发送确认**：只有 dispatcher 发任务消息；
  socket 读超时如果加到 worker 的连接上，会影响 worker 空闲等消息时的读取，没有必要冒这个险。
  两个实例的任务名（`margin.execute_attempt`）和队列名（默认 `celery`）相同，消息进的是同一个队列。
  这一条和 PLAN 的字面写法（“worker.py 打开发送确认”）不同，记进了 STATUS“执行中的取舍”。
- **`now()` → `clock_timestamp()`**：PG 的 `now()` 是**事务开始**的时间，同一个事务里调用多少次都一样。
  `dispatch_once` 整轮是一个事务，而“连不上”要 6 秒才失败，于是 `next_attempt_at = now() + 2 秒` 写进去时已经是过去的时间，
  下一轮立刻又试——退避失效。新测试第一次运行就因此失败（断言 `next_attempt_at > 现在` 不成立），这是 M1 就有的问题，
  只是 Redis 连不上时失败得快没暴露出来。`sent_at` 同样改了：同一批发出的消息原来 `sent_at` 完全相同，
  下一步对账的水位线（“比我晚投递”）就分不出先后。
- **RabbitMQ 4 禁止“不持久、也不独占”的队列**：第一次起 worker 时报 `Feature transient_nonexcl_queues is deprecated`
  并不停重启。原因是 worker 除了任务队列，还给自己建了两个临时队列：远程控制（`celery inspect` 用）和事件广播。
  按 Celery 文档改成独占队列（只属于建它的连接，连接断开自动删除）。

**一个具体例子：一道题现在怎么走**

```text
POST /runs  →  runs / attempts(pending) / outbox(pending) 同一个事务写入，返回 {"run_id": 3}
dispatcher（≤1 秒后）
   send_task("margin.execute_attempt", [attempt_id])  ──►  RabbitMQ 把消息写进持久队列 celery
                                                      ◄──  basic.ack（发送确认）
   收到确认，outbox.status = 'sent', sent_at = clock_timestamp()        日志：投递 1 条
RabbitMQ 把消息推给 worker 的消费者通道（预取上限 4，正好 4 个子进程）
worker 子进程：claim → 13 步 → finish → 向 RabbitMQ 发 basic.ack（acks_late：执行完才确认）
```

**怎么验证的**

- 自动化：单元 51 个、集成 24 个、ruff 全部通过。`test_broker_down_keeps_outbox_pending_and_backs_off`
  （连不上时 outbox 保持 pending、`tries=1`、`sent_at` 仍为空、下次投递时间在将来）在 Windows 上要 6 秒左右，
  是 Windows 对“连接被拒绝”会重试几次的缘故。
- 端到端（compose 全部 8 个服务，真实 DeepSeek）：提交“广晟控股 2023 年营业收入”，dispatcher 日志 `投递 1 条`，
  worker 日志 `Task margin.execute_attempt[...] received`，13 步完成，答 1275.99（标准答案）。
- 管理界面 / `rabbitmqctl`：

  ```text
  $ rabbitmqctl list_queues name durable exclusive messages consumers
  celery@ec058edfb06b.celery.pidbox               false  true   0  1   ← 远程控制，独占
  celeryev.7988a6af-...                           false  true   0  1   ← 事件，独占
  celery                                          true   false  0  1   ← 任务队列，持久
  $ rabbitmqctl list_channels name prefetch_count consumer_count
  ... (1)  4  1                                                         ← worker 消费通道，预取 4
  ```

**review 重点**

1. `make_publisher` 的 docstring：三种失败的实测表、为什么只设 `confirm_timeout` 不够。
2. `dispatch_once` 里 `now()` 和 `clock_timestamp()` 的区别——这是 PG 很常见的面试点（`now()` = `transaction_timestamp()`）。
3. 新测试用真实 publisher 而不是“抛一个假异常”：假异常只能证明 `except` 接得住**我以为**会抛的东西。
