## 逐步记录

### M1.5-1：迁移 0002——outbox 加补发次数 + 部分索引

**改了什么**

- 新增 [migrations/versions/0002_outbox_redeliveries.py](../../migrations/versions/0002_outbox_redeliveries.py)：
  - `upgrade()`（[第 23 行](../../migrations/versions/0002_outbox_redeliveries.py#L23)）：outbox 加一列
    `redeliveries int not null default 0`，再建部分索引 `ix_outbox_sent_at`（只收录 `status='sent'` 的行）。
  - `downgrade()`：反过来删索引、删列。
- [src/margin/models.py](../../src/margin/models.py#L138)：`Outbox` 同步加上同一个索引和 `redeliveries` 字段
  （[第 146 行](../../src/margin/models.py#L146)）。

**为什么**

- 下一步的对账（PLAN §5.7 第二层）要记“这条 outbox 被补发过几次”，补到 3 次就不再补、把 attempt 判失败。
- 不复用已有的 `tries`：`tries` 是“发消息失败”的次数，dispatcher 用它算退避时间（2、4、8……秒）。
  如果补发也加到 `tries` 上，一条被补发过 3 次的记录下次发送失败时会直接退避 16 秒，两件事搅在一起。
- 部分索引（partial index）：普通索引收录表里每一行；部分索引只收录满足 `WHERE` 条件的行。
  水位线查询只看 `status='sent'` 且最近 1 小时投递的记录，所以只给已发送的行建 `sent_at` 索引，索引更小。
- `models.py` 和迁移要写同样的东西：迁移负责“真的去改数据库”，`models.py` 是 Python 代码眼里的表结构。
  两者不一致时 `alembic check` 会报差异——这就是为什么每次改表都要两边一起改。

**一个具体例子**

开发库里已有 M1 跑出来的数据（1 个 run、2 次执行、19 步、25 个事件、2 条 outbox、17,596 个向量），
版本号是 `0001`。执行 `alembic upgrade head`：

1. Alembic 读 `alembic_version` 表发现当前是 `0001`，只执行 `0002` 这一个文件；
2. `ALTER TABLE outbox ADD COLUMN redeliveries integer NOT NULL DEFAULT 0`：PG 11 起，加“带常量默认值”的列
   只改表的元数据，不重写已有的行；读旧行时 PG 直接给出默认值 0；
3. `CREATE INDEX ix_outbox_sent_at ON outbox (sent_at) WHERE status = 'sent'`；
4. `alembic_version` 改成 `0002`。

升级后两条旧 outbox 读出来是 `(1, 'sent', tries=0, redeliveries=0)`、`(2, 'sent', 0, 0)`，各表行数不变。

**怎么验证的**

- 空库：集成测试的 `engine` fixture 每次会话都新建 `margin_test` 并 `upgrade head`（现在会依次执行 0001、0002），
  24 个集成测试全部通过。
- 有数据的库：开发库升级前后各表行数相同（见上面的例子）；再 `alembic downgrade -1` 回到 0001、
  `upgrade head` 回到 0002，都成功。
- `alembic check` 输出 `No new upgrade operations detected.`（模型和数据库一致）。
- 这一步没有新增自动化测试：新列和索引还没有代码在用，下一步的对账测试会用到它们。

**review 重点**

1. 迁移文件的 `down_revision = "0001"`：Alembic 靠它把迁移串成一条链，知道 0002 要在 0001 之后执行。
2. `server_default="0"` 而不是 Python 侧的 `default=0`：前者写进数据库的列定义，旧行和别的程序插入的行也有值。

### M1.5-2：compose 加 RabbitMQ + 配置项 `MARGIN_BROKER_URL`

这一步只把 RabbitMQ 跑起来、把地址配好；worker / dispatcher 还没改，仍然走 Redis（下一个提交切换）。

**改了什么**

- [compose.yaml](../../compose.yaml#L74) 新增 `rabbitmq` 服务：
  - 镜像 `rabbitmq:4-management-alpine`（RabbitMQ 4.3.6 + 管理界面插件）；
  - `hostname: rabbitmq`（[第 81 行](../../compose.yaml#L81)）：固定主机名；
  - 两个端口只绑本机：5672 是 AMQP 协议端口（收发消息），15672 是管理界面；
  - 命名卷 `rabbitmqdata`（[第 90 行](../../compose.yaml#L90)）保存队列和消息；
  - 把 [deploy/rabbitmq/margin.conf](../../deploy/rabbitmq/margin.conf) 只读挂载为 `conf.d/20-margin.conf`
    （[第 92 行](../../compose.yaml#L92)），里面只有一行 `consumer_timeout = 3600000`；
  - 健康检查 `rabbitmq-diagnostics -q ping`。
- 应用服务的公共环境变量加 `MARGIN_BROKER_URL`（[第 19 行](../../compose.yaml#L19)），指向容器名 `rabbitmq`。
- [src/margin/settings.py](../../src/margin/settings.py#L44)：新增 `broker_url`，默认值指向本机 5672，
  本机跑脚本 / 测试时 `.env` 里不写也能用。
- [.env.example](../../.env.example)：加 `MARGIN_MQ_PASSWORD`、`MARGIN_BROKER_URL`，并把 Redis 的说明改成“M2 起推送思考片段”。

**为什么**

- 固定主机名（PLAN §5.7 第一层、STATUS 交接）：RabbitMQ 的节点名是 `rabbit@主机名`，
  数据目录 `/var/lib/rabbitmq/mnesia/rabbit@主机名` 也带着它。Docker 默认给容器的主机名是随机的容器 id，
  `docker compose up` 重建容器后主机名一变，RabbitMQ 会当成一个新节点、建一个新目录，旧的队列和消息就“不见了”
  （数据其实还在卷里，只是没人读）。
- `consumer_timeout`（确认期限）：worker 是“执行完才确认”，一道题最长可以跑到 Celery 硬时限 25 分钟。
  RabbitMQ 4 默认 30 分钟，余量太小；一旦触发，RabbitMQ 会关闭这个消费者的**整个通道**，
  通道上所有没确认的消息（也就是这个 worker 进程正在执行的任务）都会回到队列。所以设成 1 小时，保证正常执行永远不触发。
  配置文件放 `conf.d/` 是官方镜像推荐的做法：不用覆盖镜像自带的 `10-defaults.conf`，只追加自己的那一行。
- 账号密码沿用 PG 的写法：compose 从 `.env` 读 `MARGIN_MQ_PASSWORD`，没有就用开发密码 `margin_dev`。
  只绑 127.0.0.1，开发密码不会暴露到局域网。

**一个具体例子**

`docker compose up -d --wait rabbitmq` 之后：

```text
$ docker compose exec rabbitmq rabbitmq-diagnostics -q environment | grep consumer_timeout
      {consumer_timeout,3600000},          ← 配置文件生效了
$ docker compose exec rabbitmq rabbitmqctl -q status | grep "Node name"
Node name: rabbit@rabbitmq                 ← 节点名来自固定的主机名
$ curl -u margin:margin_dev http://127.0.0.1:15672/api/overview
{"management_version":"4.3.6", ...}        ← Windows 上能打开管理界面
```

**怎么验证的**

- `docker compose config -q` 通过（compose 文件语法正确）；rabbitmq 容器健康检查通过，见上面三条命令的输出。
- 单元测试 51 个、集成测试 24 个、ruff 全部通过（这一步没有改业务代码）。
- 没有新增自动化测试：只是部署配置，下一个提交切换 worker / dispatcher 后用“提交一道题能跑完”来验证。

**review 重点**

1. `hostname: rabbitmq` 和数据卷要一起用：只挂卷不固定主机名，重建容器后数据照样“丢”。
2. 地址末尾的 `//`：`amqp://用户:密码@主机:端口/虚拟主机`，默认虚拟主机的名字就是 `/`，所以写成两个斜杠。
