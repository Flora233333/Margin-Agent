## 三、数据流（M2 之后）

```text
浏览器 -- POST /api/runs（Idempotency-Key）--> Vite 代理 --> api -- 202 {run_id}
浏览器 -- GET /api/runs/{id}/events?after=0 --> Vite 代理 --> api（SSE，长连接）

worker 每完成一步：
  一个事务：校验 epoch + 写 steps + 写 events(seq) + pg_notify('run_events', run_id)
    提交后 PG 把通知发给每个 LISTEN 的 API 进程
      |
      v
  api 进程的 event_hub 线程 --> 叫醒关注这个 run 的 SSE 连接 --> 按 seq 查库 --> 推 "id: seq / event: step"

worker 模型逐字输出时：
  DeltaPublisher --> Redis PUBLISH run:{id}:live {attempt_id, epoch, turn, kind, text}
      |
      v
  api 的 forward_deltas（每个 SSE 连接一个订阅）--> 推 "event: delta"（不带 id）

空闲 10 秒：api 查一次库（兜底）并推 "event: ping"

浏览器：
  每个事件 --> timeline.applyEvent：持久事件按 seq 去重；片段只认最近一次 attempt_started 的 (attempt_id, epoch)；
               step 到达后替换这一轮的片段
  最近一次执行结束 --> 主动 close()
  25 秒什么都没收到 / 浏览器放弃重连 --> 用 ?after=lastSeq 新建连接
```

## 六、和方案的差异、已知不足

- **新增**：SSE 心跳从注释改为具名事件 + 前端 25 秒超时重建（M2-8，联调发现）；uvicorn 优雅退出 5 秒。
- **旁注对齐简化**：没有“提前算动画终点”和 [n]↔旁注的连线（设计稿有）。
- **来源上下文只来自读过的步骤**：没有“在原文中打开”，等 M5 的文档浏览接口。
- **浏览器自带的 Last-Event-ID 重连在开发环境没出现过**：Vite 代理从不把断开传给浏览器，续传都走 `?after=`。
  Last-Event-ID 路径由后端测试覆盖，浏览器侧要等 M6 上了 Nginx 再验证。
- **“重新生成”按钮执行中也能点**，由后端 409 拒绝（见 STATUS 取舍）。
- **历史列表不实时**：别的题的状态点在列表重新取的时候才变（打开页面、提交、正在看的题结束时）。
- **联调脚本没进仓库**：仓库里只放单元 / 接口 / 集成测试（AGENTS.md）。如果以后要把这 10 个场景变成自动化的端到端测试，
  可以在 `web/app` 加 Playwright 测试，作为单独的决定。
- **模型输出的思考是英文**（DeepSeek），页面照原样显示。

### M2-1：持久事件改为 PG 通知驱动——`add_event` 同事务 NOTIFY，API 每进程一条 LISTEN

**改了什么**

- [src/margin/runs.py](../../src/margin/runs.py#L49)：`add_event` 写完事件后执行
  `SELECT pg_notify('run_events', '<run_id>')`；频道名常量 `RUN_EVENTS_CHANNEL`（[第 18 行](../../src/margin/runs.py#L18)）。
- 新增 [src/margin/event_hub.py](../../src/margin/event_hub.py#L33)：`EventHub`
  - 一个后台线程 [`_listen_forever`](../../src/margin/event_hub.py#L78)：专用、自动提交的 psycopg 连接上 `LISTEN run_events`，
    收到通知就 [`_wake(run_id)`](../../src/margin/event_hub.py#L72)；连接断了隔 2 秒重连；
  - [`watch(run_id)`](../../src/margin/event_hub.py#L55)：SSE 连接登记“我在看这个 run”，拿到一个 `asyncio.Event`，离开 `with` 自动注销。
- [src/margin/api.py](../../src/margin/api.py#L41)：
  - `lifespan`：进程启动时建 `EventHub` 并启动线程，关闭时停止；
  - 依赖 [`get_hub`](../../src/margin/api.py#L63)（测试里替换成监听测试库的 hub）；
  - SSE 循环（[第 195 行](../../src/margin/api.py#L195) 起）：`asyncio.sleep(1)` 换成“等 wake，最多 10 秒”
    （[第 206 行](../../src/margin/api.py#L206)）；超时时查一次库（兜底）并发一行 `: ping` 保活。
    `SSE_POLL_SECONDS`、`SSE_PING_EVERY` 删除，新增 `SSE_FALLBACK_SECONDS = 10`。
- [tests/conftest.py](../../tests/conftest.py#L104)：`database_url`、`hub` 两个会话级 fixture；
  [tests/test_api_pg.py](../../tests/test_api_pg.py#L92) 新增一个测试。

**为什么**

- **M1 的问题**：每个 SSE 连接每秒查一次 events 表，看的人越多查询越多，而且绝大多数查询什么都查不到。
- **为什么用 PG NOTIFY 而不是 Redis**（D20）：事件本来就存在 PG，`pg_notify` 写在同一个事务里，**提交时才发出**，
  所以 SSE 被叫醒去查的时候事件一定已经能查到；用 Redis 的话 worker 要自己保证“先提交再 publish”。
  这和 M1.5 里 dispatcher 的唤醒是同一套机制。
- **为什么每个 API 进程只开一条 LISTEN**（PLAN §5.4）：LISTEN 要独占一条 PG 连接；每个 SSE 各开一条，
  100 个人在看就占 100 条，PG 默认最多 100 条连接。一条连接收全部通知，在内存里按 run_id 分发。
- **为什么是线程 + 同步 psycopg**：psycopg 的异步连接不支持 Windows 默认的事件循环（Proactor），
  而开发时的 uvicorn 和全部测试都跑在 Windows 上。线程收到通知后不能直接操作 asyncio 的对象
  （它们不是线程安全的），要用 `loop.call_soon_threadsafe(event.set)` 请事件循环自己去 set。
- **为什么还留 10 秒兜底**：通知不持久——LISTEN 连接重连的那几秒里发出的通知没人收。兜底查询保证最多晚 10 秒。
  顺便把原来“15 秒没事件发一次 ping”合并成“每次兜底超时发一次 ping”。
- **两个容易错的顺序**：
  1. 登记之后先补查一次（`wake.set()`，第 197 行）：路由里第一次查库在登记之前，
     两者之间提交的事件发出的通知没人接，不补查就要等 10 秒兜底。
  2. 先 `wake.clear()` 再查库（第 210 行）：如果反过来“查库 → clear”，查库期间到的通知会被 clear 掉，事件就要等兜底。

**一个具体例子**

浏览器打开 run 12 的事件流，worker 正在执行：

```text
浏览器 GET /runs/12/events
  api：查库（404 检查 + 历史事件）→ hub.watch(12) 登记 → 补查一次 → 推出历史 → 等 wake（最多 10 秒）
worker 提交第 5 步：一个事务里 UPDATE attempts / INSERT steps / INSERT events / pg_notify('run_events', '12')，COMMIT
  PG：COMMIT 时把通知送给所有 LISTEN run_events 的连接
  api 的监听线程：收到 payload '12' → _wake(12) → call_soon_threadsafe(event.set)
  SSE 协程醒来：clear → 查 seq > 上次 的事件 → 推出 “id: 9 / event: step”
```

另一个人同时在看 run 13：它的 wake 不会被 run 12 的通知 set，不会白查。

**怎么验证的**

- `test_sse_pushes_new_events_on_notify_without_waiting_for_fallback`：SSE 连接建立后，另一个线程 0.5 秒提交一步、
  再 0.5 秒结束；断言 3 秒内拿到 `attempt_queued → attempt_started → step → attempt_finished` 并关闭（靠兜底至少 10 秒）。
- 原有的 `test_sse_resumes_after_last_event_id_and_closes_when_finished` 不变，仍通过（断点续传逻辑没动）。
- 单元 51、集成 34、ruff 通过；compose 重建 api 后健康检查通过。浏览器里的实际效果在 M2 联调时验证（场景 1、3、10）。

**review 重点**

1. `EventHub` 里的锁：`_watchers` 被两个线程访问（事件循环线程增删、监听线程读取），所以增删和读取都在锁里，
   读取时先复制一份再在锁外 `call_soon_threadsafe`。
2. `stream_events` 的生成器：`with hub.watch(...)` 包住整个循环，浏览器断开时生成器被取消，`finally` 里自动注销。
3. 为什么测试里 `TestClient(app)` 不会触发 `lifespan`：没有用 `with TestClient(app)`，所以 hub 由 fixture 提供并通过依赖替换注入。

  `live_redis`，Celery 任务里用每个子进程一个的 [`_live_redis()`](../../src/margin/worker.py#L74)。
- [src/margin/lease.py](../../src/margin/lease.py#L73)：`attempt_started` 事件带上 `epoch`。
- [pyproject.toml](../../pyproject.toml)：显式依赖 `redis>=5.0`（以前是 `celery[redis]` 顺带装的，M1.5 去掉了）。

**为什么**

- **两层事件**（PLAN §5.4）：思考是一个字一个字出来的，一步几百上千个片段，每个都写 PG 是严重的写放大，而且没有用——
  这一步结束后持久事件里有完整思考。所以片段只走 Redis pub/sub：发出去时有人订阅就收到，没人订阅就丢弃，不保存。
- **为什么一个收件箱**：SSE 现在要同时等两种东西（PG 通知、Redis 片段）。如果分开等，等片段时来了通知就要等下一个片段
  或 10 秒兜底才能处理。放进同一个队列，一个 `await inbox.get()` 就够了，谁先到处理谁。
- **片段为什么不带 `id:`**：浏览器的 `EventSource` 断线重连时，`Last-Event-ID` 是“最后一个带 id 的事件”的 id。
  片段如果也带 id，重连时服务端就会按片段的位置去补发持久事件，造成跳过或重复。
- **为什么带 attempt_id + epoch**（STATUS M2 场景 8）：点“重新生成”或（M4）接管后，旧执行可能还有几条片段在路上。
  前端以最近一次 `attempt_started` 的 `(attempt_id, epoch)` 为准，对不上的片段直接丢弃。所以 `attempt_started` 也要带 epoch。
- **Redis 出问题不影响执行**：实时片段只是“看着它在想”，Redis 挂了不能让题目失败。worker 第一次发送失败就停发并记一条日志
  （不在每个片段上反复超时 1 秒）；API 订阅失败也只记日志，SSE 照常推持久事件。这两种情况各有一个测试。
- **API 每个 SSE 连接各自订阅**（和 PG 不同）：Redis 连接很便宜（默认上限 1 万），没必要像 PG 那样“每进程一条再分发”；
  客户端在请求里建、用完关，也不用操心 asyncio 客户端绑在哪个事件循环上。记进 STATUS“执行中的取舍”。

**一个具体例子**

用真实 DeepSeek 提交一题（run 14），`curl -N` 看 25 秒的 SSE：

```text
event: attempt_queued / attempt_started                 （持久，带 id）
event: delta  ×4      {"attempt_id": 14, "epoch": 1, "turn": 0, "kind": "reasoning", "text": "Let"} ……
event: step                                             （第 0 步结束：完整思考 + 工具结果）
event: delta  ×47     turn 1 的思考
event: step
……                    25 秒内共 545 个 delta、7 个 step
```

前端的处理（M2 后面的提交）：turn 1 的片段逐字拼在“正在思考”区域；收到 `step`（step_no = 1）后，
用里面的完整 `reasoning` 替换掉拼出来的文字，并画出工具卡片。

**怎么验证的**

### M2-3：前端要用的两处接口——SSE 支持 `?after=`，`GET /runs` 历史列表

**改了什么**

- [src/margin/api.py](../../src/margin/api.py#L196)：SSE 多一个查询参数 `after`，起点 = `max(Last-Event-ID, after)`（[第 218 行](../../src/margin/api.py#L218)）。

- [tests/test_api_pg.py](../../tests/test_api_pg.py#L152)：两个测试。

**为什么**

- **`?after=`**：SSE 在这次执行结束后会关闭（M1 的设计）。用户接着点“重新生成”，前端要重新打开一个 `EventSource`，
  但浏览器的 `EventSource` **不能自定义请求头**，`Last-Event-ID` 只有它自己断线重连时才会带。不加参数的话只能从头再收一遍全部事件。
  取两者中大的那个：同一个 `EventSource` 断线重连时，地址里的 `after` 还是创建时的旧值，而请求头里的 `Last-Event-ID` 是最新的。
- **`GET /runs`**：设计稿（D14）左侧有历史提问列表，刷新页面后要能回到之前的题。只返回摘要，不带步骤，列表很轻。
  M3 加登录后同一个查询按真实用户过滤（现在都是开发用户）。

**一个具体例子**

run 1 第一次执行结束时，前端收到的最后一个持久事件是 `id: 5`（attempt_finished），SSE 关闭。用户点“重新生成”：

```text
POST /runs/1/regenerate                     → 202 {"attempt_no": 2}；库里新增事件 6（attempt_queued）
new EventSource("/api/runs/1/events?after=5") → 从事件 6 开始推：attempt_queued、attempt_started、delta……
网络断了一下，浏览器自动重连：
GET /runs/1/events?after=5   Last-Event-ID: 9 → 从 10 开始（取大的 9），不会把 6～9 再推一遍
```

**怎么验证的**

| 测试 | 保护的场景 |
|---|---|
| `test_new_event_source_resumes_with_after_param` | `?after=1` 只推 2、3；`?after=1` + `Last-Event-ID: 2` 只推 3（不重复） |
| `test_run_list_shows_only_my_runs_newest_first` | 新的在前；换成别的用户看到的是空列表 |

单元 51、集成 40、ruff 通过。

**review 重点**

1. `after: Annotated[int, Query(ge=0)]`：负数直接 422，不用自己写校验。
2. `row._asdict()`：SQLAlchemy 查询多列时每行是一个 `Row`，转成字典交给 Pydantic 校验。

**改了什么**

  处理“正常结束”和“浏览器放弃重连”两种断开（[第 57–66 行](../../web/app/src/useRunStream.ts#L57)），并提供 `reopen()`（下一步“重新生成”用）。
- 新增 [components/StepItem.tsx](../../web/app/src/components/StepItem.tsx)：一条思考 / 一次工具调用；

- 新增 [components/Work.tsx](../../web/app/src/components/Work.tsx)：过程区，执行中展开、结束后收起，标题显示进度。
- [pages/RunPage.tsx](../../web/app/src/pages/RunPage.tsx)：拆成 `RunPage`（取题目、处理 404）和 `RunView`（订阅事件流、按执行分组显示）；
  执行结束时通知 App 刷新左侧列表。
- [timeline.test.ts](../../web/app/src/timeline.test.ts)：6 个测试。

**为什么**

- **为什么页面状态全部从事件流算出来，而不是先 `GET /runs/{id}` 拿步骤、再接事件**：两份数据要拼接，就有“GET 之后、SSE 连上之前”
  这段时间的事件漏掉或重复的问题。打开页面时用 `?after=0` 订阅，服务端先把历史事件一次补发完、再边发生边推，
  **刷新页面、从历史点进来、正在执行中，走的是同一条代码路径**，场景 3（刷新不重复不缺失）就不需要特殊处理。
  `GET /runs/{id}` 只用来拿题目文字和 404。
- **为什么合并逻辑写成纯函数**：输入（旧状态 + 一个事件）→ 输出（新状态），不碰浏览器、不碰网络，
  “重连补发重叠”“旧执行的片段迟到”这些不好在浏览器里稳定复现的情况，可以在单元测试里直接构造事件序列来测。
  React 里这种写法就是 reducer（和 `useReducer` 是一个意思）。
- **为什么 hook 里要主动 `close()`**：服务端在执行结束后关闭连接（M1 的设计），但 `EventSource` 把任何断开都当成“网络问题”，
  过 3 秒自动重连；服务端看到 run 已结束，补发 0 条又关闭……变成每 3 秒一次的无意义请求（场景 10 要求没有轮询）。
  所以收到断开时先看时间线：最近一次执行已结束 → 这是正常结束，`close()`。
  判断看的是**最近一次**执行：回放一道重新生成过的题时，第 1 次执行的结束事件后面还跟着第 2 次的 `attempt_queued`，不能在中途断开
  （测试 `回放一道重新生成过的题…`）。
- **为什么还要自己重建连接**：`EventSource` 重连时如果拿到的不是 `200 text/event-stream`（API 重启期间 Vite 代理返回 502），
  按规范会**永久放弃**（`readyState` 变成 `CLOSED`）。这时自己隔 2 秒新建一个，用 `?after=lastSeq` 从断点接上（场景 4 的前提）。
- **为什么时间线另存一份在 `useRef`**：事件处理函数要读“此刻最新的”时间线（判断是否结束、从哪个 seq 接上）；
  `useState` 的新值要到下次渲染才能读到，ref 是一个普通的可变盒子，改了立刻能读。
- **`RunView` 用 `key={runId}`**（[第 57 行](../../web/app/src/pages/RunPage.tsx#L57)）：React 看到 key 变了就把整个组件丢掉重建，
  上一道题的时间线、连接一起清掉，hook 里就不用写“runId 变了要重置什么”的逻辑。
- **实时那一条和完整思考用同一个 key**（[Work 第 57、62 行](../../web/app/src/components/Work.tsx#L57)）：step 到达时 React 认为是同一条，
  只换文字，不会删掉再插入、重播出现动画，看起来就是“逐字出现的文字被整理成完整的一段”。

**一个具体例子**

真实运行 run 15（DeepSeek，“广晟控股2023年净利润是多少亿元？”），浏览器里看到的事件和界面：

```text
0.0s  POST /api/runs → 202 {run_id: 15}；跳到 /runs/15
0.1s  GET /api/runs/15/events?after=0 → 200 text/event-stream
      id 1 attempt_queued          过程区：“排队中，等待 worker 领取…”
```

**为什么**

- **只认 `grounded` 的引用**：`cite` 工具会校验引文是否真的出自模型读过的原文（M0 移植的 harness）。没通过的引用如果也编号显示，
  就是“看起来有出处、其实是编的”——这正是这个产品要避免的事。
- **上下文从已经读过的步骤里找，不新增接口**：模型能引用某段原文，前提是它读过（否则校验不通过），所以原文一定在这次执行的某个步骤结果里，
  前端直接找就行。代价是只能显示模型读到的那一段附近，“在原文中打开”整篇文档要等 M5 的文档浏览接口。
- **旁注对齐的算法**（[`useMarginLayout`](../../web/app/src/components/Sources.tsx#L32)，照搬设计稿 demo.js 第 4 部分）：
  1. 每张卡片找锚点（[`anchorOf`](../../web/app/src/components/Sources.tsx#L22)）：过程区展开时是里面的“引用”步骤，收起后是回答里的 [n]；
  2. 目标高度 = 锚点相对轨道顶部的位置；按目标从上到下排，会压住上一张就往下推（[第 50 行](../../web/app/src/components/Sources.tsx#L50) 起）；
  3. 卡片是绝对定位、不占高度，所以最后自己把轨道撑高。
  什么时候重算：正文各块或卡片的高度变化（`ResizeObserver`）、正文里新增一块（`MutationObserver`，重新生成时）、窗口大小变化。
  同一帧多次触发只算一次（`requestAnimationFrame`）。
- **相比设计稿删掉的部分**：设计稿在过程区折叠的 0.5 秒动画开始时就“预先算出终点”，让旁注和内容同时到达；这里每一帧按当前位置重算，
  卡片会略微跟在内容后面滑动。效果差别很小，代码少一半，记在 STATUS 的取舍里。设计稿里 [n] 和旁注之间的连线也没做。
- **盯正文的子块，而不是正文本身**（[第 81 行](../../web/app/src/components/Sources.tsx#L81) 附近）：轨道被撑高后整个网格行变高，
  正文（`.thread`）被拉伸，之后它自己的高度就不变了，折叠过程区时收不到通知。设计稿注释里专门提醒过这个坑。
- **点 [n] 的“展开 + 闪一下”不用 effect 里 setState**：lint 规则 `set-state-in-effect` 提示这样会多渲染一轮。
  改成由数据推导：记下用户最后一次手动展开 / 收起时的点击计数，之后计数变大就展开（[第 109 行](../../web/app/src/components/Sources.tsx#L109)）。
  “闪一下”是重播 CSS 动画，属于直接操作 DOM，仍放在 effect 里。
- **跟随到底部**：执行中每来一个事件就把滚动位置设到最底；但用户往上翻（离底部超过 80px）就不再跟随，滚回底部又恢复。
  简洁风宽屏时滚动的是 `.app`，窄屏时是整个页面（[`scroller`](../../web/app/src/pages/RunPage.tsx#L138)）。

### M2-7：重新生成与失败说明——新执行接着收事件、409 提示、四类失败原因

**改了什么**

- [pages/RunPage.tsx](../../web/app/src/pages/RunPage.tsx#L91)：标题栏加“重新生成”按钮。`onRegenerate`：`POST /runs/{id}/regenerate` 成功后
  标记“结束时要刷新左栏”、立刻刷新左栏（这道题变回执行中）、`reopen()` 重新打开事件流；失败（409 等）把说明显示在正文末尾。
  执行结束时清掉过时的提示（[第 76 行](../../web/app/src/pages/RunPage.tsx#L76)）。
- 新增 [components/Failure.tsx](../../web/app/src/components/Failure.tsx)：[`failureMessage`](../../web/app/src/components/Failure.tsx#L11) 把 `attempt_failed` 的错误码翻成一句话：
  `llm_http_502`（模型网关报错）、异常类名（如 `ReadTimeout`）、`lease_expired`（worker 没按时续租）、`delivery_lost`（M1.5 的投递放弃）。
  失败的执行显示这段说明，已完成的步骤留在上面（[第 137 行](../../web/app/src/pages/RunPage.tsx#L137)）。
- [components/Answer.tsx](../../web/app/src/components/Answer.tsx)：`citations` 传 `null` 表示“更早的执行”，只显示结论行
  （[RunPage 第 144 行](../../web/app/src/pages/RunPage.tsx#L144)）。

**为什么**

- **重新生成后为什么要 `reopen()`**：上一次执行结束时流已经被主动关闭（M2-5），新执行的事件要新开一个 `EventSource` 来收；
  地址带 `?after=lastSeq`（M2-3 加的参数），从已收到的最后一个事件之后接着收，旧执行的事件不会再推一遍。
- **按钮为什么执行中也能点**：允不允许重新生成，以后端为准（`runs.regenerate` 用 `FOR UPDATE` 锁住 run 再检查）。
  前端的状态可能是旧的——另一个标签页刚点过、或者事件还没推到——前端自己禁用按钮反而会出现“能点但其实不该点”或“不能点但其实可以”。
  后端拒绝时返回 409“这道题还在执行中”，前端原样显示。这条记在 STATUS 的取舍里（常见的做法是执行中禁用按钮，可以再加）。
- **失败说明不显示原始异常文字**：worker 写进库里的只有错误码或异常类名（`worker._describe`），因为 `str(exc)` 里带网关地址（密钥相关信息不能出现在前端）。
  前端只认这几类码，其余原样显示类名。
- **更早的执行只留结论行**：引用编号和右侧旁注只对应最近一次执行；旧执行的答案还在，方便对比两次的结论。
  第一版里旧执行也显示了“0 处引用”的账目行，容易误解成“那次没有引用”，改成只留结论。

**一个具体例子**

run 15 已完成（第 1 次执行，事件 1–15），在浏览器里：

```text

                   GET /api/runs（左栏这道题变回呼吸点）
                   GET /api/runs/15/events?after=15 → 事件 16 attempt_queued(attempt 16, no 2) …
7.7s 再点一次      POST /api/runs/15/regenerate → 409 → 正文末尾“这道题还在执行中”
12.6s 第 2 次执行完成（8 步）→ 流关闭、提示清掉、GET /api/runs（左栏变回绿点）
页面：“第 1 次执行” 只剩结论 23.39；“第 2 次执行（重新生成）” 完整的结论、依据 [1] 和右侧旁注
```

**怎么验证的**

- 前端没有新增纯函数测试：重新生成的事件顺序（第 1 次结束后还有第 2 次）已由 M2-5 的 `回放一道重新生成过的题…` 覆盖，
  409 由后端测试 `test_regenerate_is_rejected_while_an_attempt_is_still_active`、`test_regenerate_while_attempt_is_pending_returns_409`（M1）覆盖；这一步是界面接线，用浏览器验证。
- 浏览器实测 run 15：上面的请求序列（Chrome 控制台里 409 那一行是浏览器自己打印的“请求失败”，不是脚本错误）。
- 失败说明（`lease_expired`、`llm_http_*`）需要制造故障，放在 M2 收尾的 10 个场景里实测（场景 7）。
- `npm test` 14 个、build、lint 通过；后端单元 51、集成 40、ruff 通过（后端没改）。

**review 重点**

1. `onRegenerate` 里的顺序：先等 POST 成功，再 `reopen()`。反过来的话，新流可能在 `attempt_queued` 提交之前就连上，
   服务端看到 run 仍是已结束，补发 0 条就关闭，前端又判定“已结束”——新执行就看不到了。
2. `watching.current = true`：只有“看着它从执行中到结束”的时候才刷新左栏，打开一道早已结束的题不会多请求一次。

### M2-8：联调发现的问题——“半死”的 SSE 连接：服务端心跳事件 + 前端 25 秒无数据重连

**联调时看到了什么**

验证场景 4（执行中 API 断开）时，执行到一半 `docker compose stop api`、6 秒后再 `start`：页面卡住，之后的步骤再也没出现，也没有“正在重连”的提示。
API 日志里重启后**根本没有新的 `/events` 请求**。对照实验（两个 `curl -N` 同时订阅一个执行中的 run，然后 `docker compose kill api`）：

```text
直连 127.0.0.1:8000           → API 一死 curl 立刻退出（exit 18，连接被关闭）
经 Vite 代理 localhost:5173   → curl 一直挂着，直到自己的 40 秒超时（exit 28）
```

也就是说，后端进程死掉时，Vite 开发代理没有把浏览器这一侧的连接关掉。浏览器以为连接还开着，就一直等下去，
`EventSource` 的自动重连从来没有触发。这种“半死”的连接（half-open）在生产环境也会出现，比如手机切换网络、NAT 表项过期，
所以不能指望每一层都会把断开正确地传过来。另外还看到 `docker compose stop api` 花了 11 秒：
uvicorn 的“优雅退出”会等所有连接自己结束，而 SSE 连接永远不会自己结束，只能等 docker 10 秒后强杀。

**改了什么**

- [src/margin/api.py](../../src/margin/api.py#L248)：空闲 10 秒时发送的 `: ping`（SSE 注释）改为具名事件 `event: ping` + `data: {}`，不带 id。
- [web/app/src/useRunStream.ts](../../web/app/src/useRunStream.ts#L46)：`alive()` 计时器。收到任何东西（持久事件、片段、心跳、连接建立）都重新计时，
  超过 25 秒（[`SILENCE_MS`](../../web/app/src/useRunStream.ts#L23)）什么都没收到，就关掉这个连接、用 `?after=lastSeq` 重建。文件开头的说明从“三件事”变成“四件事”。
- [compose.yaml](../../compose.yaml)：api 的启动命令加 `--timeout-graceful-shutdown 5`。
- [web/app/src/styles/app.css](../../web/app/src/styles/app.css)：`#root { height: 100%; }`。这一条和心跳无关，是同一轮联调（场景 2）发现的：
  执行中页面不跟随到底部。原因是 React 挂在 `<div id="root">` 里，它没有高度，`.app` 的 `height: 100%` 失效，
  滚动的是整个页面而不是 `.app`（设计稿里 `.app` 直接在 body 下，没有这个问题），`useFollowBottom` 设置 `.app` 的滚动位置就没效果。
- [tests/test_api_pg.py](../../tests/test_api_pg.py#L139)：新增 `test_idle_sse_sends_heartbeat_event_without_id`；
  `test_sse_forwards_live_thinking_without_event_id` 原来过滤 `:` 开头的注释块，改成过滤 `event: ping`。

**为什么**

- **为什么心跳要用具名事件**：SSE 规范里冒号开头的行是注释，浏览器解析时直接丢掉，**不会交给 JS**。注释只能让中间的代理觉得连接不空闲，
  前端却无从得知“连接还活着”。改成 `event: ping` 后，前端用 `addEventListener('ping', …)` 就能收到。
- **为什么心跳不带 id**：浏览器会把最后收到的 id 记作 Last-Event-ID。如果心跳带了 id（比如 0），断线重连时服务端会从 0 开始补发，导致重复；
  不带 id 时浏览器记的仍是最后一个持久事件的 seq。新测试同时检查了这一点。
- **为什么是 25 秒**：服务端空闲时每 10 秒发一次心跳，执行中还有大量片段和步骤事件。25 秒相当于连续错过两次多的心跳，
  不会把“模型在慢慢想”误判成断线，真断了也不会让用户等太久。
- **为什么是“前端检测 + 重建”，而不是修 Vite 的代理**：开发代理只是这次暴露问题的地方，真正的问题是“中间任何一层都可能不传递断开”。
  心跳 + 客户端超时是长连接的通用做法（WebSocket 的 ping/pong 同理），换成 Nginx 也照样需要。
- **优雅退出的超时**：发布或重启 API 时，5 秒后主动断开 SSE，不等 docker 强杀。前端会自己重连，事件从库里按 seq 补发，不会丢。

**一个具体例子**

修复后重跑场景 4（run 21）：

```text
 1.6s  GET /api/runs/21/events?after=0 → 200 text/event-stream；收到持久事件 1–4 和片段
 5.6s  docker compose stop api（5 秒优雅退出后进程结束；Vite 仍然把浏览器那一侧挂着）
       worker 照常执行，事件 5、6… 写进库
20.6s  docker compose start api
36.3s  25 秒没收到任何数据 → 关掉旧连接（浏览器记为 ERR_ABORTED）→ GET /api/runs/21/events?after=6
       一次补发 7–14（含 attempt_finished）→ 正常结束、关闭
结果：跨两个连接的持久事件 1–14 连续，无重复、无缺失；页面 11 张工具卡片、思考全文与库里的 11 步一致
```

**怎么验证的**

- 新测试 `test_idle_sse_sends_heartbeat_event_without_id`：把兜底间隔改成 0.2 秒，执行 0.7 秒后结束，
  断言流里有 `event: ping\ndata: {}` 这一块，持久事件的 id 仍然是 1、2、3。改动之前它会失败（流里只有 `: ping`）。
- 后端单元 51、集成 41、ruff 通过；前端 `npm test` 14、build、lint 通过。
- 浏览器实测：上面的 run 21；api 容器已用新镜像和新的启动命令重建。

**review 重点**

1. [`alive()`](../../web/app/src/useRunStream.ts#L46) 在哪些地方被调用：`open()` 一开始就调用，所以连请求一直挂着、迟迟没有建立的情况也能兜住；
   正常结束和浏览器放弃重连这两个分支要先 `clearTimeout`，否则 25 秒后计时器还会再开一个连接。
2. 浏览器自己的自动重连（带 `Last-Event-ID` 请求头）在开发环境里一直没有触发过，因为 Vite 从不把断开传给浏览器。

### M2-10：来源栏两种排法——执行中吸顶列表、结束后只对齐回答的 [n]

**逐帧截图看到了什么**（改之前，run 32）

```text
P1 执行中卡片对齐过程区里的“引用”步骤，页面一直往下滚，卡片跟着滚出屏幕、被后来的卡片推开（偏离 +111、+207 px）
P2 结束后展开 / 收起过程区，卡片飞几千像素，而且比正文晚约 250 ms 到位
P3 执行结束、过程区自动收起的那一帧，屏幕上一片空白（当时滚在 2969 px 处）
P5 点开来源原文，50 ms 内就展开完，看起来是“跳”出来的
```

**改了什么**

- [components/Sources.tsx](../../web/app/src/components/Sources.tsx#L60) `useMarginLayout` 多了参数 `live`（最近一次执行还没结束），分两种排法：
  - 执行中：整栏加 `is-live` 类，CSS `position: sticky` 吸在屏幕顶部，卡片按引用编号顺序排成列表；
  - 结束后：卡片只对齐回答里的 [n]（[`anchorOf`](../../web/app/src/components/Sources.tsx#L26)），不再找过程区里的步骤。
  - 两种排法切换时用 [`switchMode`](../../web/app/src/components/Sources.tsx#L72)（FLIP，见下）。
- 照搬设计稿的两个“算终点”的函数：[`workShift`](../../web/app/src/components/Sources.tsx#L38)（过程区还要变化多少高度）、
  [`finalItemHeight`](../../web/app/src/components/Sources.tsx#L51)（卡片动画播完后的高度）。另加一个 MutationObserver 盯过程区的类名，
  点“展开”的那一刻就重算，不等高度开始变。
- [`SourceCard`](../../web/app/src/components/Sources.tsx#L170)：原文展开的目标高度改为量出来的 `scrollHeight`，删掉 app.css 里的 `max-height: 40em`。
- [pages/RunPage.tsx](../../web/app/src/pages/RunPage.tsx#L187) `useFollowBottom`：执行结束时，如果用户一直在跟随，等过程区收起动画（0.5 秒）后，
  把这次执行（收起后的“思考与检索 · n 步” + 回答）滚到屏幕顶部。
- [styles/app.css](../../web/app/src/styles/app.css#L14)：`.app { grid-template-rows: max-content }`（原因见下面的“联调时发现”）；
  `.panel-body.is-live` 吸顶；`.work { scroll-margin-top: 64px }`，滚到顶部时让出吸顶标题栏的高度。

**为什么**

- **执行中为什么不对齐步骤**：执行中过程区一直在变长、页面一直在滚，对齐到步骤的卡片注定在屏幕上乱跑。
  这时用户关心的是“已经找到了哪些证据”，一个固定在眼前的列表最好读。结束后回答出现，[n] 才是稳定的锚点。
- **结束后为什么过程区展开也不去对齐步骤**：之前的规则是“过程区展开就对齐步骤，收起就对齐 [n]”，一点展开，锚点从回答换到几千像素外的步骤，
  卡片就飞过去（P2）。现在锚点只有 [n]，展开过程区时回答整体下移，卡片跟着平移，和回答始终并排。
- **FLIP 是什么**：切换排法的那一刻，整栏从“吸在屏幕顶部”回到“页面里的位置”，坐标系一下子变了。
  First：记下每张卡片此刻在屏幕上的位置；Last：切换类名；Invert：关掉过渡，把卡片原地放回刚才的屏幕位置；Play：恢复过渡，设置新位置，卡片从原处滑过去。
  不这样做的话，卡片会先瞬移到页面顶部，再从屏幕外滑进来。
- **为什么要提前算终点**（`workShift`、`finalItemHeight`）：过程区收起、原文展开都是 0.5 秒的 CSS 动画。如果每一帧按当时量到的位置去追，
  卡片的 `top` 自己也有 0.5 秒过渡，每一帧都在“重新出发”，就会晚到、一顿一顿（P2 的 250 ms）。动画一开始就把终点算好，两边同时出发、同时到达。
- **原文展开为什么要量高度**：`max-height` 从 3 行过渡到 40em（约 640 px），但原文只有 220 px 高，动画在前 1/3 的时间里就走完了，看起来是跳的（P5）。
  量出真实高度后，0.5 秒的动画全程都在展开。

**联调时发现：sticky 没有生效**

第一次实测（run 34），执行中卡片的屏幕位置是 -1150、-1406…，整栏根本没吸住。浏览器里逐级查父元素：

```text

.side-panel                           高 900   ← 右栏只有一屏高，sticky 没有空间可“吸”
.app  grid-template-rows=900px                 ← 正文 3281 px，却只占了一行 900 px，其余溢出
```

原因：`.app` 的高度固定（100%），`.main` 又写了 `min-height: 100vh`。这种情况下 CSS Grid 的 `auto` 行只取元素的 min-height（900），
不会再长（容器没有多余空间）。之前结束后的页面能滚，是因为旁注卡片绝对定位在很低的地方、把右栏撑高了，行高被右栏带上去；
执行中卡片都排在顶部，行高就回到 900。改成 `max-content` 后，行高取正文实际高度，右栏跟着拉长，sticky 就能吸住。
左侧图标栏（同样是 sticky）以前在“没有引用的题”上其实也吸不住，这次一起修好了。

**联调时发现：结束时偶尔不滚**

第一版在“执行变为结束”的 effect 里读 `stick`（用户是否在页面底部附近）。实测有一次读到 `false`：
结束那一刻过程区收起、右栏换排法，页面高度和滚动位置都在变，这时的 `stick` 不代表用户的意图。改为记住“执行中最后一次更新时是否在跟随”（`following`）。

### M2-11：来源卡片入场动画；新卡片出现时从“引用”步骤画一条线，1.5 秒后收回

**改了什么**

- [styles/app.css](../../web/app/src/styles/app.css#L105)：`.margin-item` 加入场动画 `note-in`（0.5 秒淡入，同时从左边 12px 滑到原位）。
- [components/Sources.tsx](../../web/app/src/components/Sources.tsx#L163) 新增 `useAnnounce`：执行中引用数增加时，等 0.55 秒画一条从过程区里那一步到新卡片的曲线，
  1.5 秒后收回。`Sources` 多渲染一个 `<svg class="connector">`（样式在设计稿的 clean.css 里已经有了）。

**为什么**

- **入场为什么用 CSS 动画（@keyframes），不照搬设计稿的 `.is-hidden` + 过渡**：过渡要“先渲染成隐藏状态、下一帧再去掉类”，
  在 React 里就得多一个 state 和一个 effect；CSS 动画在元素插入页面时自动播放，一行样式就够。重新排序、改 top 时 React 复用同一个元素，动画不会重播。
- **为什么要画线**：执行中右栏是固定在屏幕顶部的列表（M2-10），和过程区里的“引用”步骤不再并排。线把两边连起来，用户能看到“这张卡片是这一步引用的”；
  1.5 秒后收回，不一直挡着正文。
- **为什么等 0.55 秒**：卡片入场动画 0.5 秒，等它基本到位再量终点坐标，线才正好落在卡片上。
- **为什么线的起点是过程区的右边缘**：从引用文字本身出发的话，线会像删除线一样压在文字上；从右边缘出发只穿过空白。
- **effect 的清理函数为什么要收线**：1.5 秒内又来了一张卡片，或执行结束（右栏换排法、卡片要滑走），旧的线必须马上收回，
  否则“收回”的定时器被清掉，线会一直留在页面上。
- **打开页面时已有的卡片不画**（`seen` 的初始值）：从历史列表打开一道已结束的题，不应该满屏画线。

### M2-13：过程区的三个动效——步骤长出来、思考逐段淡入、标题切换；跟随到底部改为盯正文高度

**改了什么**

- [styles/app.css](../../web/app/src/styles/app.css#L18)：`.steps > .step` 插入时播放 `step-in`：高度从 0 长到内容高度（`grid-template-rows` 0fr → 1fr）、淡入、轻微下移。
- [components/StepItem.tsx](../../web/app/src/components/StepItem.tsx#L151) `StreamingText`：正在输出的思考按“每次到达的片段”切成小段，新的一段包在 `<span class="tok">` 里淡入（base.css 现成的 `.tok` 动画）。
  最多保留最近 40 段单独淡入，更早的合并成普通文字。
- [components/Work.tsx](../../web/app/src/components/Work.tsx#L32) `SwapLabel`：过程区标题变化时（“正在执行 · 已完成 3 步” → “正在思考 · 已完成 3 步”），旧文字上移淡出、新文字从下方淡入。
- [pages/RunPage.tsx](../../web/app/src/pages/RunPage.tsx#L190) `useFollowBottom`：执行中“跟随到底部”从“收到事件就滚一次”改为 ResizeObserver 盯 `.thread` 的高度。

**为什么**

- **跟随为什么要改**：步骤现在要用 0.5 秒长出来。按事件滚的话，事件到达时新的一步高度还是 0，滚到底以后它才慢慢长高，最新一步会被挡在屏幕下方，
  直到下一个事件。盯高度的话，长高的每一帧都会触发，始终贴着底部。
- **“记住上一次的值、渲染时比较”**（`StreamingText`、`SwapLabel` 都这样写）：
  要知道“这次比上次多了哪一段”“标题从什么变成了什么”，就得记住上一次的值。放在 ref 里在渲染时读写，React 的 lint 规则不允许
  （渲染应该是纯函数）；放在 effect 里会先渲染一次旧样子再改。React 文档推荐的做法是放在 state 里、渲染时发现不一样就立刻 `setState`，
  React 会丢掉这次的输出、马上用新 state 重新渲染，不会多画一帧。
- **为什么只保留 40 段**：思考一次可能上千个片段，每段一个 `<span>` 会让 DOM 越来越大。淡入只有 0.4 秒，按每秒几十个片段算，40 段足够覆盖正在播放的那些。
  被合并进普通文字的那段已经播完动画，看不出变化。
- **标题淡入播完要去掉 `is-entering`**：base.css 的“扫光”动画（执行中标题一道光扫过）只加在没有 `is-entering` / `is-leaving` 的文字上。
  `e.animationName === 'label-in'` 这个判断目前不是必需的（这个元素上只有淡入会结束，扫光是无限循环、不会结束），
  写上是为了以后给标题再加动画时不被误触发。

**一个具体例子**（run 42，广晟控股 2022 年营业收入；每 30 ms 采样）

```text

       标题：is-leaving “正在思考 · 已完成 3 步” | is-entering “正在执行 · 已完成 4 步”，约 0.3 秒后旧文字移除
20.43  第 9 项（新一轮思考）出现：淡入中的片段 2 → 3 → … → 10，每段约 0.4 秒后变为完全不透明

```

- `npm test` 15、build、lint 通过；后端没改，单元 51、集成 41、ruff 通过。

### M2-14：结论数字滚动；回答底部加“复制”按钮

**改了什么**：[components/Answer.tsx](../../web/app/src/components/Answer.tsx)

- [`figureOf`](../../web/app/src/components/Answer.tsx#L44)：把“结论行显示什么”（判断题换回正确 / 错误、多个答案用顿号）从 `Verdict` 里抽出来，复制按钮也要用。
- [`CountUp`](../../web/app/src/components/Answer.tsx#L58)：结论是单个数字（如 `1206.37`）时，从 0 滚动到这个数，0.8 秒、先快后慢，小数位数不变。
  `ABC`、`2.58；7.65`、`正确` 这类不滚动。
- [`CopyButton`](../../web/app/src/components/Answer.tsx#L121) + [`plainText`](../../web/app/src/components/Answer.tsx#L144)：复制“结论 + 每条依据（[n] 引文（文档））”；
  成功后图标换成 ✓、文字变“已复制”，1.5 秒后恢复；剪贴板被浏览器拒绝时显示“复制失败”。
- [components/Icons.tsx](../../web/app/src/components/Icons.tsx)：加设计稿的 `i-copy` 图标。

**为什么**

- **滚动为什么直接改 `textContent`，不用 state**：一秒 60 帧，用 state 就是一秒重新渲染 60 次 Answer。数字只是显示效果，不影响别的组件，
  直接改这一个元素的文字最省事。React 不会把它改回去：组件重新渲染时 `value` 没变，React 比较后发现子节点相同，不碰 DOM。
- **为什么用 `useLayoutEffect`**：`useEffect` 在浏览器画完之后才执行，那一帧会先显示最终的数，再跳回 0 开始滚。
  `useLayoutEffect` 在画之前执行，第一帧就是 0。
- **复制失败为什么要处理**：剪贴板是浏览器接口（外部边界），页面不在前台、或用户关掉了权限都会被拒绝。不处理的话按钮没反应，用户不知道复制没成功。
- **复制的内容**：只放结论和依据原文，不放过程；文档名放在括号里，粘贴到别处也能看出出处。M2.5 有了成段的回答之后，改为复制回答正文。
