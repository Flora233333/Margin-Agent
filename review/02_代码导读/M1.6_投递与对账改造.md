### 数据流（一道题从提交到结束）

```text
api：写 run + attempt(pending) + outbox(pending)，NOTIFY outbox
 │
 ▼
dispatcher 一轮（被 NOTIFY 叫醒，或最多等 10 秒）
 │  ① 到了巡检时间（每 10 秒）：读队列状态 → expire_leases → resend_lost
 │       resend_lost 的前提：读得到队列、消费者 > 0、就绪数 = 0
 │       发出超过 1 分钟 × 2^重发次数 还是 pending → outbox 改回 pending（重发）；重发过 3 次 → delivery_lost
 │  ② 空位 = 消费者数 × 子进程数 − running − 已发出没人领；有空位才从 outbox 取最多“空位数”条发出
 │  ③ 等：下一条到期的 outbox（没有空位就直接等 10 秒）和下次巡检，取较早的
 ▼
RabbitMQ：就绪数几乎总是 0（有空位才发），消息到了马上被某个空闲子进程拿走
 ▼
worker 子进程：claim（attempt → running）→ 加载语料（第一次约 2 秒，缓存丢了约 100 秒，这期间照常续租）→ 执行
 ▼
finish / fail / 租约过期：同一事务 NOTIFY outbox → dispatcher 马上醒来，把排队的下一条发出去
```

## 逐步记录

### M1.6-1：注释和文档更正，删掉不生效的 `consumer_timeout` 配置

**改了什么**

- 删除 `deploy/rabbitmq/margin.conf`（里面只有一行 `consumer_timeout = 3600000`），
  并删掉 [compose.yaml](../../compose.yaml#L90) 里 rabbitmq 服务挂载它的那一行（数据卷那一行之后）。
- [src/margin/worker.py](../../src/margin/worker.py#L44) 的 `task_acks_late` 注释改了两处说法：
  - “进程被杀，消息回到队列”改成**只对主进程成立**：子进程被杀时主进程照样确认，消息不回队列；
  - “确认期限见 margin.conf”改成：4.3 起只有 quorum 队列检查确认期限，经典队列上不配。
- 文档同步：PLAN §5.2 的 Celery 配置一行、§5.7 第一层表格的“确认期限”一行、§5.7 切换步骤第 1 条；
  DECISIONS D19 的“代价”；M1.5 导读里 4 处（文件清单、阅读顺序、数据流、M1.5-2 的“为什么”）加了“M1.6 更正”。
  旧说法保留、标明更正，review 时能看出当时为什么那样写。

**为什么**

M1.5 review（Q10、Q19）查 RabbitMQ 官方文档发现两件事：

1. **确认期限在经典队列上不生效。** “Starting with RabbitMQ 4.3, delivery acknowledgement timeouts are only supported
   by quorum queues.” 我们的任务队列 `celery` 是 Celery 默认建的经典队列，所以那行配置读进去了、但从来不起作用。
   而且就算是 quorum 队列，4.3 起到期也只放回超时的那一条，不再“关闭整个通道”。留着它只会误导读代码的人。
2. **“进程被杀，消息回到队列”只对主进程成立。** RabbitMQ 只认识 worker 主进程那条连接；子进程是主进程 fork 出来干活的，
   跟 RabbitMQ 没有连接。子进程被杀（超过 25 分钟硬时限、内存不够被系统杀掉）时，Celery 的默认行为是主进程照样替它
   `ack`（`task_reject_on_worker_lost` 默认关），消息就此消失，不会回到队列。
   这时库里的 attempt 是 running，由租约过期（90 秒没续租）发现。

那“推出去还没确认的消息”在 RabbitMQ 这边有没有时限？经典队列上没有：一直挂着，直到 ack、reject 或连接断开。
真正收场的是我们自己的两层：Celery 硬时限 25 分钟（杀子进程）和租约 90 秒（巡检判 `lease_expired`）。

**一个具体例子**

```text
改之前  $ docker compose exec rabbitmq rabbitmq-diagnostics -q environment | grep consumer_timeout
              {consumer_timeout,3600000},     ← 配置文件读进去了（但经典队列不检查它）
改之后  $ docker compose up -d --wait rabbitmq        ← 挂载变了，compose 重建容器
        $ docker compose exec rabbitmq rabbitmq-diagnostics -q environment | grep consumer_timeout
              {consumer_timeout,1800000},     ← 回到默认值，同样只对 quorum 队列有意义
        $ docker compose exec rabbitmq ls /etc/rabbitmq/conf.d/
        10-defaults.conf                       ← 只剩镜像自带的
        $ docker compose exec rabbitmq rabbitmqctl -q list_queues name messages_ready consumers
        celery  0  1                           ← 队列还在（数据卷），worker 已重新连上
```

**怎么验证的**

- 上面的命令（2026-10-21，RabbitMQ 4.3.6）：重建后队列和消费者都正常。
- `pytest`、`pytest -m integration`、`ruff check src tests scripts` 全部通过（只改了注释和配置）。

**建议重点看**

- worker.py 那段注释：分清“主进程的连接断了”（消息回队列）和“子进程死了”（主进程替它 ack，消息没了）。
  这是 M1.6-2“先 claim 再加载”的出发点之一：子进程一旦拿到消息就可能悄悄没了，所以要尽早在 PG 里留下痕迹。

### M1.6-2：先 claim 再加载 + 前端“正在准备资料…”

**改了什么**

- [src/margin/worker.py](../../src/margin/worker.py#L175) `execute` 不再直接收语料对象，改收一个**加载函数** `load`：
  - 第一件事仍是 `lease.claim`；
  - 加载挪进了 `with LeaseKeeper(...)` 里、`try` 的第一行（[第 212 行](../../src/margin/worker.py#L212)）：
    `corpus, retriever = load()`。加载出错和模型报错一样走 `except Exception` → `lease.fail`；
  - 理解题目（另一个线程）在加载之前就提交了，它不用语料，正好和加载同时进行。
- Celery 任务 [execute_attempt](../../src/margin/worker.py#L243) 把 `_components`（带 `@cache` 的加载函数）原样传进去，不再自己先调用。
- [tests/test_worker_pg.py](../../tests/test_worker_pg.py#L45)：新增 fixture `load`（返回小语料），原有 18 处调用改成传它；
  新增测试 [test_corpus_is_loaded_after_claim_and_load_error_fails_the_attempt](../../tests/test_worker_pg.py#L273)。
- 前端 [Work.tsx](../../web/app/src/components/Work.tsx#L38)：执行中、0 步、没有实时片段时，过程区标题显示“正在准备资料…”
  （原来是“正在执行 · 已完成 0 步”）。e2e 新增一条，帧记录（`e2e/support.ts`）多记一个 `label`。

**为什么**

改之前的顺序是：收到消息 → 加载语料（约 2 秒；BM25 缓存丢了要重建约 100 秒）→ claim。
加载这段时间里，PG 看到的 attempt 一直是 pending，和“消息丢了”长得一模一样。M1.5 的对账只好设 2 分钟宽限期、
再加水位线、队列为空这些证据去猜；缓存丢了的时候还是会猜错、多发一条重复消息。更糟的是子进程在加载中死掉：
主进程照样 ack（M1.6-1），消息没了，attempt 停在 pending，要靠对账补发。

先 claim 之后：

- “消息发出 → PG 里变成 running”只剩几毫秒，后面 M1.6-5 才能用“发出 1 分钟还没 claim”判定丢失；
- 加载多久都有续租线程保着（每 15 秒续 90 秒），不会被误判；
- 加载中死了 → 90 秒后租约过期，判 `lease_expired`（看得见的失败，用户重新生成；M4 接管后自动接上）；
- 加载出错（例如语料路径配错）→ 立刻判失败，页面显示原因。

代价（D28 已接受）：加载中死掉不再自动补发，要用户点重新生成。

前端标题：先 claim 以后，“已领取、0 步”的时间可能长达 100 秒，“已完成 0 步”看着像卡住了，所以换成“正在准备资料…”。
只改文字，后端不加新事件——“0 步且没有思考片段”本身就说明还在加载（或者模型第一轮还没开始吐字）。

**一个具体例子**

语料路径配错时（实验 V9 会在真实环境做一遍）：

```text
改之前  消息到了 → _components() 抛 FileNotFoundError → 任务异常结束，主进程 ack
        PG：attempt 一直 pending，outbox sent → 2 分钟后对账补发 → 同样失败 → …… → 约 8 分钟后 delivery_lost
改之后  消息到了 → claim（running）→ load() 抛 FileNotFoundError → lease.fail
        PG：attempt failed，error = "FileNotFoundError"；页面：“执行出错（FileNotFoundError），这次执行没有完成。”
```

**怎么验证的**

- 新测试：`load` 里先查一次库，断言此时 attempt 已经是 running，再抛 `FileNotFoundError`；
  执行完断言 run 和 attempt 都是 failed、error 是异常类名。如果顺序写反（先加载），加载时看到的是 pending，
  而且异常会直接从 `execute` 抛出去，attempt 停在 pending——测试两处都会失败。
- e2e“正在准备资料…”：用旧的 `Work.tsx` 跑会失败（标题序列里没有这一项），新代码通过。
- `pytest`（63）、`pytest -m integration`（54）、ruff、`npm test`、`npm run e2e`（24）全部通过。

**建议重点看**

- `execute` 里 `load()` 的位置：为什么在 `with LeaseKeeper` 里面、`try` 里面，而不是 claim 之前。
- `_components` 的 `@cache`：加载抛异常时不缓存结果，所以修好配置、重启 worker 之后能正常加载。

### M1.6-3：dispatcher 的两个时间合成一个 10 秒

**改了什么**

- [src/margin/dispatcher.py](../../src/margin/dispatcher.py#L40)：`MAX_WAIT_SECONDS = 10`（兜底扫描）和
  `INSPECT_EVERY_SECONDS = 15`（巡检）合成 `TICK_SECONDS = 10`。`seconds_until_due`、`main` 和测试里的引用跟着改名。
- `main` 里巡检那一行加了注释：巡检仍然按自己的计时器 `last_inspect` 走。

**为什么**

两个数字讲起来要分别解释“10 秒是什么、15 秒是什么”，而它们的作用其实是一回事：dispatcher 多久自己看一眼。
合成一个后，故障速查表里的“多久发现”都只多一句“最多晚 10 秒”。巡检从 15 秒变成 10 秒，多出的开销是每 10 秒
两条小查询和一次 RabbitMQ 被动声明，可以忽略。

为什么巡检不能“每醒一次就做一次”：dispatcher 平时阻塞在 `wait_for_notify` 上，**每提交一道题、每结束一道题**
（M1.6-4 起）都会被 NOTIFY 叫醒。20 道题同时提交时一秒能醒好几次，巡检每次都要连 RabbitMQ，没必要。所以投递每次醒来都做，
巡检看 `time.monotonic() - last_inspect >= TICK_SECONDS`。

**一个具体例子**

```text
t=0     启动：投递一轮 + 巡检，last_inspect=0
t=3.2   有人提交 → NOTIFY 叫醒 → 投递；距上次巡检 3.2 秒，不巡检；接着最多睡 6.8 秒
t=10    睡到点（没有通知）→ 投递一轮（兜底）+ 巡检
```

**怎么验证的**

改名和常量调整，现有测试（`test_new_submission_wakes_dispatcher_within_one_second` 用 `TICK_SECONDS` 作为等待上限）全部通过；
真实环境下的巡检间隔在 M1.6-7 的实验里从日志时间看。

**建议重点看**

- `main` 循环里“投递每次都做、巡检按计时器做”的区别，以及最后一行等待时间的计算。

  `--concurrency`（[第 140 行](../../compose.yaml#L140)）用同一个 `${MARGIN_WORKER_CONCURRENCY:-4}`，两边不会配得不一样。
  `.env.example` 里加了说明（注释掉的默认值）。
- [dispatcher.free_slots](../../src/margin/dispatcher.py#L56)：`空位 = 总位子数 − 在途数`。在途 = running 的 attempt
  + 已发出（outbox sent）还没 claim（attempt pending）的，两个计数作为子查询放在一条 SQL 里。
- [dispatch_once](../../src/margin/dispatcher.py#L72) 多一个参数 `capacity`（总位子数），一轮最多发 `min(空位, BATCH)` 条，
  没有空位直接返回 0。积压的题留在 outbox 里（pending），仍按 `outbox.id` 先进先出。
- [seconds_until_due](../../src/margin/dispatcher.py#L297) 也收 `capacity`：没有空位时返回 10 秒，不返回 0。
- [main](../../src/margin/dispatcher.py#L332)：巡检挪到投递前面，并把读到的队列状态存在 `queue` 里；
  `capacity = 消费者数 × MARGIN_WORKER_CONCURRENCY`（[第 344 行](../../src/margin/dispatcher.py#L344)），
  读不到队列状态（RabbitMQ 连不上）或还没读过时为 0。
- 一道题结束的四个地方在同一事务里 `notify_outbox`：[lease.finish](../../src/margin/lease.py#L160)、
  [lease.fail](../../src/margin/lease.py#L170)、[lease.expire_leases](../../src/margin/lease.py#L203)（有过期的才发）、
  [dispatcher._fail_undelivered](../../src/margin/dispatcher.py#L269)。
- 测试：原有 6 处 `dispatch_once` 调用补上 `CAPACITY = 4`；新增
  [test_backlog_waits_in_outbox_until_a_slot_frees_up](../../tests/test_worker_pg.py#L364)。

**为什么**

M1.5 的做法是“outbox 里有就发”，发出去的消息全堆在 RabbitMQ 的队列里排队。积压时 PG 里看到的是一大片
“outbox sent、attempt pending”，排队的和丢了的长得一样，只能靠水位线、30 分钟兜底去猜（M1.6-5 会删掉它们）。

有空位才发以后，RabbitMQ 里只会有“马上就有子进程接手”的消息：

- 排队发生在 PG 的 outbox 里，看得见、可以查、以后 M3 要做“每人最多同时 N 道”“按用户轮流”只改这条 SQL 的条件和排序；
- “outbox sent、attempt pending”正常只持续几毫秒（M1.6-2 先 claim），持续 1 分钟就只能是丢了。

几个细节：

- **已发出未 claim 的也算在途**。只数 running 的话，刚发出去的几条还没被 claim，下一次醒来会以为还有空位，再多发几条。
- **消费者数用最近一次巡检的值**（最多 10 秒前），不在每次投递时都连 RabbitMQ。Celery worker 主进程在任务队列上是 1 个消费者，
  所以“消费者数 × 子进程数”就是总位子数。读不到 / 没有 worker 在线时 capacity 为 0，这一轮不发，题留在 outbox。
- **巡检挪到投递前面**：启动后的第一轮必须先知道有几个 worker；否则第一轮 capacity 为 0，启动前积压的题要多等 10 秒。
- **为什么 `seconds_until_due` 也要看空位**：积压时 outbox 里有一堆“已经到期”的 pending 行，原来的逻辑会返回 0，
  循环立刻再转一圈、还是发不出去、再返回 0……变成空转、不停查库。没有空位时就老老实实睡，等“有题结束”的通知或下一次巡检。
- **结束时 NOTIFY**：不叫醒的话，空出的位子要等最多 10 秒的兜底扫描才补上；20 道题排队时每道多等几秒。
  `lease.finish` 等函数原本就在一个事务里写状态和事件，NOTIFY 跟着事务提交才发出，dispatcher 被叫醒时一定能看到“位子空了”。

已知的小代价（D28 写过）：worker 容器被 kill 后，它手上 running 的题在租约过期前（约 100 秒）仍算在途，
别的 worker 的空位会被少算（实验 V8 观察）。

**一个具体例子**

1 个 worker（4 个子进程），一次提交 6 道题（run 1～6）：

```text
提交 → NOTIFY → dispatcher 醒来：空位 = 1×4 − 0 = 4 → 发 1、2、3、4；5、6 留在 outbox（pending）
RabbitMQ：4 条被 4 个子进程各拿走 1 条，就绪 0；子进程 claim → running
run 2 结束：lease.finish 同一事务 NOTIFY → dispatcher 醒来：空位 = 4 − 3 = 1 → 发 5
run 1 结束 → 发 6
```

**怎么验证的**

- 新测试：总位子数 1，提交 2 道：第一轮发 1 条；第二轮发 0 条（1 号已发出未 claim，也算在途），2 号的 outbox 仍是 pending；
  1 号 claim 后 0.2 秒在另一个线程里 `lease.finish`，dispatcher 的 LISTEN 连接 1 秒内收到通知，再投递就发出 2 号。
- 真实环境：`docker compose up -d --build` 后容器里 worker 命令是 `--concurrency 4`、dispatcher 读到
  `MARGIN_WORKER_CONCURRENCY=4`；提交 1 道题，正常投递、执行（20 道题的积压在实验 V3 验证）。
- `pytest`（63）、`pytest -m integration`（55）、ruff 全部通过。

**建议重点看**

- `free_slots` 为什么要把“已发出未 claim”算进在途。
- `seconds_until_due` 里“没有空位就睡 10 秒”那段：没有它会出什么问题。
- `main` 里巡检和投递的先后顺序。

### M1.6-5：只看时间的重发，删掉水位线

**改了什么**

- [dispatcher.py](../../src/margin/dispatcher.py#L182)：`requeue_lost` 改写并改名为 `resend_lost`（“补发”统一叫“重发”）：
  - **前提**（[第 209 行](../../src/margin/dispatcher.py#L209)）：读得到队列状态、消费者数不为 0、**就绪数为 0**，三条都满足才判，
    否则这一轮什么都不做；
  - **判定**（[第 221 行](../../src/margin/dispatcher.py#L221)）：outbox sent、attempt pending，且 `sent_at` 早于
    `now − 1 分钟 × 2^redeliveries`；
  - **动作**不变：没用完 3 次就把 outbox 改回 pending、`redeliveries + 1`，由投递去发；用完了走 `_fail_undelivered`（`delivery_lost`）。
- 删掉：宽限期 `GRACE`、水位线查询和 `WATERMARK_WINDOW`、30 分钟兜底 `FALLBACK`、重发后的 `notify_outbox`。
  新常量 `RESEND_AFTER = 1 分钟`（[第 49 行](../../src/margin/dispatcher.py#L49)）、`BACKLOG_WARN_SECONDS = 120`。
- `main`：就绪数连续 2 分钟不为 0 记一条 warning（每段积压只记一次，回到 0 后重新计时，[第 338 行](../../src/margin/dispatcher.py#L338) 起）；
  日志措辞从“补发”改成“重发”。`read_queue_state` 读不到时的日志改成“这一轮不投递、不判重发”。
- `dispatch_once` 的 docstring 里提到水位线的那句改掉；`models.py` 里 `ix_outbox_sent_at` 的注释写明“暂不删”；
  `Failure.tsx` 的错误码注释指向 `resend_lost`。
- [tests/test_reconcile_pg.py](../../tests/test_reconcile_pg.py) 重写：删掉水位线相关的 3 个，现在 5 个测试（其中一个分两种情况）。

**为什么**

M1.5 对账的难处在于“排队”和“丢了”分不清，只好用证据猜（D19）：

| | M1.5 | M1.6 |
|---|---|---|
| 候选 | 发出超过 2 分钟（宽限期吸收加载语料的时间） | 发出超过 1 / 2 / 4 / 8 分钟 |
| 判丢失 | ① 水位线越过 ② 队列为空 ③ 超过 30 分钟，任一条 | 只看时间 |
| 误判的边界 | 积压超过 30 分钟误补发；水位线要求一个队列 + 先进先出 + 额度等于子进程数 | 子进程数配错时 RabbitMQ 里出现积压 → 暂停重发 + 告警 |

M1.6-2（先 claim）和 M1.6-4（有空位才发）以后，“发出 → claim”只有几毫秒、RabbitMQ 里不积压，时间本身就是可靠的证据。

几个细节：

- **为什么要“就绪数为 0”这个前提**：有空位才发的前提是 `MARGIN_WORKER_CONCURRENCY` 配得和 worker 实际的子进程数一样。
  配大了（或者 RabbitMQ 刚重启、worker 卡住），消息会在 RabbitMQ 里排队，这时“发出 1 分钟没 claim”并不说明丢了。
  就绪数不为 0 就暂停判断，并在 2 分钟后记 warning 让人去查。代价是暂停期间真丢的消息也要等积压消失才能发现，可以接受。
- **退避间隔翻倍**：第一次重发后如果还是没人领，多半不是偶发丢消息（例如 worker 不认识任务名、消息被 reject 丢掉），
  隔得越来越久，既不刷屏，也给人留出处理时间。总共约 15 分钟判失败，比 M1.5 的约 8 分钟慢，但不会误判排队的题。
- **为什么到期的判断写在 Python 里**：候选只有“发出了还没 claim”的几条（正常时只有刚发出的），把 `now − 1 分钟 × 2^r`
  写进 SQL 也行，但 Python 一行 `if sent_at > now - RESEND_AFTER * 2 ** redeliveries` 更好读。`now` 仍取数据库的时间。
- **为什么删掉重发后的 NOTIFY**：重发发生在巡检里，巡检之后同一圈循环紧接着就投递；就算这一轮没空位，
  改回 pending 的行 `next_attempt_at = now()`，等有空位时自然会发。NOTIFY 叫醒的是 dispatcher 自己，本来就醒着。
- **重发不直接 publish**：仍然只把 outbox 改回 pending，真正的发送走 `dispatch_once`。发送失败（RabbitMQ 告警时一条约 27 秒）
  按 `tries` 退避，不算进重发次数，也不会卡在巡检里（D28 的替代方案对比）。
- 部分索引 `ix_outbox_sent_at` 现在没人用了，PLAN 写明“暂不删（省一个迁移）”。

**一个具体例子**

队列被人清空（实验 V4 会在真实环境做）：

```text
10:00:00  dispatcher 发出 attempt 12，outbox sent
10:00:01  有人 purge_queue celery，消息没了；attempt 12 一直 pending
10:01:00～10:01:10  巡检：就绪 0、消费者 1，sent_at 早于 now − 1 分钟 → outbox 改回 pending，redeliveries = 1
          同一圈接着投递：发出，sent_at = 10:01:0x → worker claim → 正常执行
（如果再丢：10:03 重发第 2 次，10:07 第 3 次，10:15 判 delivery_lost）
```

**怎么验证的**

| 测试 | 场景 |
|---|---|
| `test_unclaimed_one_minute_after_sending_is_resent` | 发出 1.1 分钟的重发、redeliveries = 1；发出 0.5 分钟的不动 |
| `test_resent_message_waits_twice_as_long_before_next_resend` | 已重发 1 次：1.5 分钟不动，2.5 分钟重发第 2 次 |
| `test_messages_waiting_in_queue_pause_resending` | 就绪数为 2 时，发出 10 分钟的也不动 |
| `test_no_resend_when_workers_cannot_be_seen`（两种） | 读不到队列状态 / 消费者数为 0：不重发、不耗次数 |
| `test_gives_up_eight_minutes_after_third_resend_and_allows_regenerate` | 重发 3 次后 7 分钟不动，8.5 分钟判 `delivery_lost`，之后能重新生成 |

`pytest`（63）、`pytest -m integration`（54：删 7 个、加 6 个）、ruff 全部通过。真实环境的 V4～V7 见实验一节。

**建议重点看**

**为什么**

M2 review Q11 发现：打开一道已结束的题，SSE 先补发历史事件，这些事件也会让这次执行经过“排队 → 执行中 → 结束”。
过程区的规则是“执行中就展开”，所以中间那一下其实是展开的。原来看不出来，只是因为补发的事件几乎同时到达，
React 把它们合成一次渲染、浏览器来不及画出中间状态——**这不是规则保证的**。网络慢、补发被拆成几批到达时，
就会闪一下展开（还会出现“正在执行”标题、转圈、页面跟着往下滚）。

原来的 `settledEarly` 等 `caught_up` 才确定，可已结束的题服务端补发完就关闭连接、不发 `caught_up`，这条路走不通。
`GET /runs/{id}` 在打开页面时就已经返回了 `run.status`，用它一开始就能确定。

**实现时的取舍（记进 STATUS“执行中的取舍”待确认）**：PLAN 写的是“补发事件只填内容、不展开过程区、不播出场动画”。
我先数了一下按字面做（照常渲染、只是不展开）要改的地方：过程区展开、标题文字和换字动画、标题转圈、
“正在理解题目”占位、来源栏的执行中排法、执行中自动滚到底——6 处，每处都可能漏一帧。
改成“补发没到齐的那次执行先不显示”只改一处，中间状态根本不会被渲染出来，更稳。
代价：慢网络下，补发到齐之前那次执行是空白的（题目照常显示），而不是一点点填进来；补发一般不到 1 秒，可以接受。

**为什么要改成逐帧取样**：`setInterval(20)` 和浏览器画帧不同步，展开一帧（约 16 毫秒）的状态可能正好落在两次取样之间。
`requestAnimationFrame` 在每次画帧前调用，画出来的每一帧都会被记到。用旧代码跑新测试，第一个断言就失败
（`f.open` 出现过 true），说明这个测试确实能抓到闪动。

**一个具体例子**

```text
        第 2 批（后 8 步）           → “正在执行 · 已完成 13 步”
        第 3 批（撰写、结束）         → 收起，回答出现
改之后  第 1、2 批 → 这次执行还没到结束事件，不显示（右栏也不说“没有引用”）
        第 3 批    → 整个出现：过程区收着，“思考与检索 · 13 步”，回答直接显示
```

**怎么验证的**

- 新 e2e：改之前失败（过程区展开过），改之后通过。
- 原有 replay / stream 的 e2e 全部通过（它们也换成了逐帧取样）：已结束的 5 种题、重新生成过的题、执行失败的题，
  以及执行中刷新、重新生成、半死连接这些“打开时还在执行”的路径不受影响。

### M1.6-7a：broker 重连后预取数不再被 Celery 调低（实验 V8 发现）

**改了什么**

- [worker.py](../../src/margin/worker.py#L62)：`celery_app.conf` 加 `worker_enable_prefetch_count_reduction=False`，注释写明原因。
- 新增 [tests/test_worker_celery.py](../../tests/test_worker_celery.py)：断言这项关着、预取倍数是 1。

**怎么发现的**

V8（执行中 kill worker）里，提交 6 道题，按设计应该 4 道 running、2 道在 outbox 排队。实际只有 3 道被 claim，
第 4 道（attempt 178）已经发出、却 20 秒没人领，旧 worker 的日志里只有 3 条 `received`。往前查：这个 worker 在 V6
（RabbitMQ 停 2 分钟）时重连过，当时日志写着：

```text
18:43:33 Temporarily reducing the prefetch count to 3 to avoid over-fetching since 1 tasks are currently being processed.
18:45:53 Prefetch count has been restored to the maximum of 4
```

**复现（2026-10-21，celery 5.6.3）**：提交 1 道题，执行中把 RabbitMQ 停 20 秒再启动，等它做完：

```text
worker 日志     Prefetch count has been restored to the maximum of 4
rabbitmqctl list_consumers queue_name prefetch_count
                celery  3                      ← RabbitMQ 那边还是 3
再一次提交 4 道  celery  ready 1  unacked 3      ← 只拿 3 条，第 4 条在 RabbitMQ 里排队 15 秒
```

**原因**：Celery 重连时（`consumer.py` 第 399 行起）按“还在执行的任务数”把预取数调低；
之后的“恢复”（`_restore_prefetch_count_after_connection_restart`，第 716 行）只是给 `self.qos.value` 赋值，
没有调用会向 RabbitMQ 发 `basic.qos` 的方法。所以 Celery 自己以为是 4，RabbitMQ 一直按 3 发，直到 worker 重启。

**为什么对我们是问题**：有空位才发（M1.6-4）的前提是“dispatcher 算的位子数 = worker 实际能拿的条数”。
worker 少拿一条，就有一条消息在 RabbitMQ 里排队（正是 M1.6 想消灭的），重发也因为“就绪数不为 0”暂停，
2 分钟后还会报“子进程数配错？”的 warning。一次 RabbitMQ 重启就会把 worker 永久降成 3 个并发。

**为什么关掉它是安全的**：Celery 调低预取是怕重连后“多拿”。我们这里发多少由 dispatcher 按空位决定，不会多发；
重连后回到队列的、还在执行的任务的那条消息，会被另一个子进程 claim 失败、几毫秒跳过（V6 里看到过）。

**怎么验证的**

- 修好后同样复现一遍：RabbitMQ 重启后 `list_consumers` 仍是 4；再提交 4 道，`ready 0, unacked 4`。
- 之后重做 V8，见实验一节。
- `pytest`（64）、`pytest -m integration`（54）、ruff 通过。

**建议重点看**

- 这是“日志说的”和“实际状态”不一致的例子：排查时以 RabbitMQ 那边的 `list_consumers` 为准。
- 测试只是一行配置断言（防止以后有人删掉），真正的验证是上面的复现步骤；Celery 修好这个问题后可以去掉这一项。
