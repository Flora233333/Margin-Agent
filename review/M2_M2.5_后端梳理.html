三、API 进程内部：一个 SSE 连接怎么同时等两种东西

时序图第 11～13、16～17 步发生在 API 进程里。一个 SSE 连接要等两种东西：PG 说“有新事件了”，以及 Redis 转来的片段。做法是两边都往同一个收件箱里放，stream_events 只等这一个收件箱。

为什么 PG 这边“每个进程一条连接”，Redis 那边却“每个 SSE 连接一条”：PG 的连接贵（默认上限 100），100 个人同时看就占满了；Redis 的连接便宜（默认上限 1 万），每个连接自己订阅最简单。

六、问答第一轮：接口、事件流、补发与回放（2026-10-14）

对应时序图 A（提交）、B（打开事件流）两段。一句话总结这一轮：前后端之间只传数据；页面怎么画由前端决定；“流式”和“直接显示全部”是同一套代码，区别只在打开那一刻库里已有多少事件。

Q1图里第 4 步的 GET 是什么意思？

POST /runs 之后为什么还要 GET /runs/5？

每次请求都带一个“动作类型”。POST 是提交，让后端新建或改动东西；GET 是读取，只查不改。GET /runs/5 读作“把 5 号 run 的情况给我”。

提交（POST）只拿回一个编号 {run_id: 5}。前端跳到 5 号题的页面以后，先 GET 一次，拿到“到目前为止的全貌”，再打开事件流接收之后的变化。对后端来说，这一步就是 runs.get_run 里几条只读 SQL，不碰 RabbitMQ，也不碰 worker。

Q2“跳到这道题自己的页面”是什么？GET 拿的是模板吗？

模板早就在浏览器里了，GET 拿的是填进模板的数据（JSON）。

  • 第一次打开网站时，浏览器把整个前端程序（所有页面模板）一次下载下来。
  • “跳页面”是地址栏从 / 变成 /runs/5，前端把画面换成 RunPage 模板。这一步完全在浏览器里完成，不问后端。
  • RunPage 模板一开始是空的，所以它发 GET /runs/5，拿回题目、标题、模型、执行时间这些数据，填进模板。

比方：模板是印好的空白成绩单，每个学生用的是同一张；GET 是去教务处查 5 号学生的分数，查回来填上。前后端之间从来不传页面，只传数据（JSON 和事件）。

Q3这样分工也方便以后做多轮问答吧？

对，不过主要的活在后端。前端改动小：数据里多一个“轮次列表”，每一轮的画法和现在的单题一样。后端至少要定三件事：

  1. 怎么存：例如新增“会话”表，一个会话下挂多个 run，每个 run 是一轮；
  2. 第二轮怎么带上第一轮：问“那它的毛利率呢？”，Harness 要拿到上一轮的问题、答案和引用，模型才知道“它”是谁；
  3. GET 返回什么：从“一道题”变成“整个会话的所有轮次”。

现在的事件流基本能直接用，因为每条事件都带着 run_id 和 attempt_id。多轮问答是一个新功能，不是现在顺手就有的。

Q4点开以前回答过的题，发的是什么？

走的还是同一套请求，后端没有专门给“历史页面”的接口：

① 左侧栏加载      GET /runs                  最近 50 道题：编号、问题、标题、状态、时间
② 点 12 号题      （不发请求）               地址变成 /runs/12，换成 RunPage 模板
③ RunPage 打开    GET /runs/12               题目、标题、模型、每次执行的开始和结束时间
                  GET /runs/12/events?after=0  从第 0 条起补发全部事件；题已结束，发完就关

刷新页面、从历史点进来、刚提交完，走的都是同一条代码路径（RunPage.tsx 开头的注释）。after=0 不是“新题专用”，意思是“我手上一条都没有”；断线重连时手上有了，就用 after=lastSeq 接着要。

发现：runs.get_run 会把每次执行的全部步骤都查出来返回，但 RunPage 画步骤用的是事件流补发的事件，GET 只用了题目、标题、时间这些。查步骤的那部分目前前端没用上。（我第一次回答时说“GET 拿回步骤，前端用它画”，这个说法不对，已更正。）

Q5现在有哪些 GET 和 POST，各干什么？

接口干什么后端调用谁在用
GET /health返回 {"ok": true}，证明进程活着无部署和监控
POST /runs提交新题：一个事务里写入 run、attempt、outbox 和 attempt_queued 事件，返回 202 和编号。必须带 Idempotency-Key 请求头，重复提交返回同一个 run_idruns.create_run输入框“提交”
GET /runs历史列表（最近 50 道）runs.list_runs左侧栏
GET /runs/{id}一道题的详情runs.get_run打开 RunPage
POST /runs/{id}/regenerate重新生成：新建 attempt 和 outbox；正在执行时返回 409runs.regenerate“重新生成”按钮
GET /runs/{id}/events?after=N事件流（SSE）：补发 N 之后的事件，连接保持，有新的就推，题目结束时关闭stream_eventsRunPage 一直挂着

只有两个 POST 会让 worker 干活，而且它们只写库（包括 outbox），由 dispatcher 去投递。前 5 个接口都是一问一答，只有最后一个是长连接。前端代码里的 /api/runs 是开发服务器的转发，去掉 /api 以后就是后端的路径。

Q6事件流（B 段 5～8 步）到底在干什么？

要解决的问题：一道题要跑一两分钟，前端想一有进展就显示。每秒 GET 一次，人一多库就被问爆了。SSE 的办法：浏览器发一个 GET，后端不马上结束回复，有新事件就往这条连接里写一段。这就像从“一直打电话问快递到哪了”，变成“订阅快递通知”。

  1. ⑤ 浏览器用自带的 EventSource 打开 /runs/5/events?after=0。
  2. ⑥ API 查库，先查状态，再查 seq > 0 的事件。刚提交时只有 seq 1。
  3. ⑦ 为了以后能被叫醒，API 先做两件准备工作。
    • hub.watch(5)：在本进程登记“我在看 5 号”，领一个收件箱；PG 通知到了，就往收件箱里丢一张“有新事件”（NEW_EVENTS）。
    • forward_deltas：订阅 Redis 的 run:5:live，收到逐字片段也丢进同一个收件箱。
    先自己放一张 NEW_EVENTS，是因为 ⑥ 查库和 ⑦ 登记之间有个空档：这期间写入的事件，通知发出时还没人登记，收不到。所以第一轮循环一定再查一次库。
  4. ⑧ 把查到的事件发给浏览器，再发 caught_up（“历史补完了”）。
之后循环：
while 题目没结束:
    等收件箱（最多 10 秒）
    ├─ NEW_EVENTS → 查库取 seq > 上次发到的位置 → 发给浏览器
    ├─ 片段       → 直接发 delta
    └─ 10 秒没动静 → 发 ping（“我还活着”），再查一次库兜底
题目结束 → 发完最后的事件 → 关闭连接

一句话：浏览器开一条不挂断的连接；API 平时等在收件箱上，PG 通知或 Redis 片段把它叫醒，它再去库里取新事件推过去。代码在 api.py:200-275。

Q7events 表长什么样？是按 run_id 嵌套的吗？

PG 里没有真正的嵌套。events 是一张平铺的表，一个事件一行，每行带 run_id。“嵌套”是按 run_id 筛选出来的效果。

run_id属于哪道题（外键 → runs）
seq这道题里的第几条，每道题从 1 开始；(run_id, seq) 唯一，自带索引

payload事件内容，JSON。不同事件内容长得不一样，统一放进一个 JSON 列，SSE 取出来原样发

103 |   5    |  2  | attempt_started
104 |   5    |  3  | step

SELECT * FROM events WHERE run_id = 5 AND seq > 0 ORDER BY seq;   -- events_after 做的事

为什么不用 id 当序号：① 每道题要从 1 连续编号，浏览器才好记“看到第几条了”；② 自增 id 的顺序不可靠：事务 A 拿到 10、B 拿到 11，B 先提交，读者先看到 11，A 那条 10 就永远漏掉了。seq 的来源是 add_event 先给 runs 表这道题的 last_seq 加 1（runs.py:41-44）。这条 UPDATE 会锁住这一行直到提交，所以后拿号的一定后提交。last_seq 相当于这道题的取号机。

Q9所以跑完的题收不到 caught_up？

对。api.py:243-252 的顺序是：先发查到的事件 → 状态已结束就 return → 没结束才发 caught_up（开关保证只发一次）。跑完的题走不到发 caught_up 那一行。

caught_up 的作用是让前端分清“回放”和“正在发生”：caught_up 之前到的直接显示，之后到的才播动画。重新生成过的题最能体现这一点：第 1 次执行早已结束，直接收起显示；第 2 次正在跑，结束时播收起动画。

Q10正在跑的题，切出去再切回来，看到的是最新的吗？会不会重新跑一遍？

  • 在网站里切到别的题：页面卸载，旧连接主动关掉（useRunStream.ts:104-108）。切回来重新 GET，并用 after=0 打开事件流，已完成的步骤整批补发，直接显示到最新，然后接着实时走。不会重跑一遍，worker 那边也完全不受影响。唯一看不到的是离开期间那一步的逐字思考，这一步结束时，step 事件会带完整思考补上。
  • 切到浏览器别的标签页：连接一直开着，切回来本来就是最新的。
  • 断网或 API 重启：前端记着 lastSeq，用 after=lastSeq 只补缺的。

切回来时过程区为什么是展开的：规则是 open = 用户点过的选择 ?? (执行中 || 刚结束停 0.7 秒)（Work.tsx:94）。补发的第一条 attempt_queued 一到，这次执行就算“进行中”（排队中也算），而且补发完它确实还在跑，所以从第一帧起就是展开的，这是正常状态。小细节：如果你手动收起过，切走再切回来会重新展开，因为“用户点过”只存在页面内存里，会随页面一起消失。

Q11那前端是等 caught_up 或 attempt_finished 到了才画画面吗？

不是。每收到一条事件就更新一次画面（useRunStream.ts:60-64）。跑完的题之所以看不到“先展开、刷数据、再收回去”，靠的是速度：7 条事件几乎同时到达，浏览器大约每 16 毫秒才绘制一次，React 又会把挨得很近的更新合并，所以屏幕上的第一帧已经是“结束、收起”的状态。

一句话：uvicorn 进程一直在跑；请求来了才调用路由函数；stream_events 只跑一下，就把生成器 generate 交给框架；框架在事件循环线程上不停地向 generate 要下一段，写给浏览器。generate 没东西可发时，就停在 await inbox.get()。往收件箱里放东西的有两方：hub 线程（盯着 PG）和 pump 协程（盯着 Redis），谁放了东西，谁就顺手把 generate 叫醒。

Q12new EventSource(...) 是 new 了个什么？在哪执行？

在前端执行（useRunStream.ts:69）。EventSource 是浏览器自带的类，不是我们写的，也不用安装。new EventSource(地址) 就是创建这个类的一个对象，相当于 Python 的 source = EventSource(url)，只是 JS 创建对象要多写一个 new。

对象一建好，就立刻发出一个普通的 GET，然后一直守着这条连接。它替前端包了三件事：

  1. 守着连接：后端的回复不结束，它就一直收；
  2. 解析文本：把 id: 4 / event: step / data: {...} 拆开，交给前端事先注册的 addEventListener('step', ...)；
  3. 断线重连：自动重连，并在请求头 Last-Event-ID 里带上最后收到的 id。
浏览器的通信工具特点我们为什么用 / 不用
fetch普通请求，一问一答也能读流，但解析和重连都要自己写
EventSource专门接收服务器推送（SSE）只需要“后端 → 前端”单向，刚好够用
WebSocket双向，两边随时都能发我们不需要浏览器往后端推，用它太重

SSE 的中文：Server-Sent Events，服务器推送事件。它是浏览器的标准：服务器回复一个不结束的 HTTP 响应，按 id: / event: / data: 的格式一段一段往下写。

Q13后端收到的是 SQL 吗？SSE 和查库什么关系？Redis 在哪绑定？

浏览器从来不直接碰数据库。一共三段连接，SSE 只是其中一段：

浏览器 ──① HTTP GET──▶ API（stream_events） ──② SQL──▶ PG
   ▲                          │  └──── 订阅 ────▶ Redis
   └──── ③ SSE（不挂断的回复）──┘
段传的是什么
① 浏览器 → APIHTTP 请求 GET /runs/5/events?after=0，不是 SQL
② API → PGAPI 自己发的 SQL：SELECT … FROM events WHERE run_id=5 AND seq>0
③ API → 浏览器这一段才叫 SSE：回复一直不结束，有新东西就接着写

查库、登记收件箱、订阅 Redis、往回复里写，全部发生在 stream_events 这一个函数里。比方：顾客（浏览器）打电话给客服（API）说“5 号订单有进展告诉我”；客服不挂电话，一边查仓库系统（PG），一边订阅物流短信（Redis），有消息就在电话里念给顾客听（SSE）。顾客只和客服说话。

Q15每次请求都是一个新的 stream_events 吗？generate 是谁调用的？return 到哪了？

代码只有一份，每次调用各有一套自己的变量。A 看 5 号、B 看 6 号同时打开，就是两次调用：各自的 run_id、last_seq、caught_up、收件箱和生成器，互不影响，和 Java 里同一个方法被调用两次一样。

生成器：函数体里有 yield 的函数，调用时不执行函数体，只得到一个“暂停着的执行过程”。之后每次有人向它要下一个值，它就往下跑到下一个 yield，交出值，然后停在那里。

def count():
    print("开始"); yield 1
    print("继续"); yield 2

g = count()   # 什么都没打印，只得到生成器 g
next(g)       # 打印“开始”，返回 1，停住
next(g)       # 打印“继续”，返回 2，停住

谁在要值：stream_events 查一次库、定义 generate，然后 return StreamingResponse(generate())，几毫秒就结束了。它 return 给调用它的 FastAPI，FastAPI 再交给 uvicorn。StreamingResponse 是框架（Starlette）提供的，拿到生成器后反复做这件事：

async for chunk in 生成器:      # 向 generate 要下一段 → generate 跑到下一个 yield
    await 写给浏览器(chunk)
# generate return → 回复结束，连接关闭

没有为这个用户开新线程。generate 是一个协程：一个能暂停、之后再接着跑的函数，暂停时只在内存里保存局部变量和停在哪一行，占几 KB。它跑在事件循环线程上。

每次 yield 出来的东西：一段纯文本，也就是浏览器在网络上收到的原文。\n\n（空行）表示一段结束。

"id: 4\nevent: step\ndata: {\"step_no\": 1, \"tool_name\": \"search_docs\", …}\n\n"   ← 持久事件（events 表的 payload）
"event: caught_up\ndata: {}\n\n"                                                     ← 历史补完
"event: ping\ndata: {}\n\n"                                                          ← 10 秒心跳
"event: delta\ndata: {\"attempt_id\": 12, \"epoch\": 1, \"turn\": 2, \"kind\": \"reasoning\", \"text\": \"先查年报\"}\n\n"   ← Redis 片段

Q16api.py 是单线程吗？await 是等待还是跳过？线程池是什么？

一个 API 进程里有三类线程（见本节开头的全景图）：

线程几个谁建的跑什么
事件循环线程1uvicorn 启动时（asyncio.run）所有 async def 代码：每个 generate、每个 pump、框架写网络
线程池最多 40，复用框架（AnyIO）按需建会卡住线程的同步代码：run_in_threadpool 里的查库；以及普通 def 写的路由（其余 5 个接口都是）
hub 线程1我们自己（hub.start()）守着 PG 的 LISTEN 连接

await 既不是傻等，也不是跳过：

  • 对这个函数来说是“等”：停在这一行，后面的代码不执行，等的东西到了才从这一行接着跑；
  • 对线程来说是“去干别的”：线程不卡在这里，回去跑别的连接的代码。

如果写成阻塞调用（例如在 async 函数里直接同步查库，或者 time.sleep），线程就被卡死，所有连接都得陪着等。所以查库要写成 await run_in_threadpool(...)：把查库交给线程池里的一个线程，事件循环线程先去忙别的，查完再回到这一行。线程池就是 Java 的 ExecutorService，run_in_threadpool(f) 相当于 CompletableFuture.supplyAsync(f, executor)。

with hub.watch(run_id) as inbox:                               # api.py:238  接住收件箱

hubpump
是什么普通线程，每个 API 进程 1 个协程（asyncio.create_task），每个 generate 1 个，在事件循环线程上

Q19事件循环是不是挨个去看收件箱？hub 和 pump 放了东西，它怎么知道？

不轮询。事件循环手里只有一张“待办”名单（loop._ready），停在 await 上的协程不在名单上，它根本不去看。谁往收件箱里放东西，谁就顺手把等着的协程放回待办。线程没事做时睡在操作系统的 select 上，能叫醒它的只有三样：网络连接来了数据、闹钟到点、有人往 self-pipe 写了字节。

收件箱怎么记住谁在等（asyncio.Queue 源码简化）：

async def get(self):
    while not self._items:
        ticket = loop.create_future()   # 开一张“提货单”
        self._getters.append(ticket)    # 登记：有人在等
        await ticket                    # generate 停在这里
    return self._items.pop(0)

def put_nowait(self, item):
    self._items.append(item)
    if self._getters:
        self._getters.pop(0).set_result(None)   # 在提货单上盖章 → “继续跑 generate”进待办

调度循环本身（简化）：

while True:
    for callback in 当前待办: callback()                 # ① 把待办做掉，每个协程跑到下一个 await 就交回来
    ready = selector.select(timeout=离最近闹钟还有多久)   # ② 没事就睡在这里（Linux epoll / Windows IOCP）
    把有数据的连接、到点的闹钟对应的协程放进待办          # ③

两路的差别：pump 本身就在事件循环线程上，它放东西时线程是醒着的，直接放进待办就行。hub 在另一个线程，事件循环可能正睡在 select 上；如果直接调用 put_nowait，不但没人去执行待办，两个线程同时改一个列表还会改乱。所以要用 loop.call_soon_threadsafe（event_hub.py:78）：先加锁把“放纸条”塞进待办，再往 self-pipe 写 1 个字节。self-pipe 是事件循环启动时给自己建的一对互通的 socket，select 一直盯着其中一头，字节一到就醒。

一个 API 进程里三类线程：事件循环线程 1 个、线程池最多 40 个、hub 线程 1 个。事件循环线程是主场：请求都先到它这里，另外两类都是从它这里派出去干活的，干完再把结果交回给它。

三条色带是三类线程：蓝 = 事件循环线程，紫 = 线程池，绿 = hub 线程。小卡片沿线移动 = 一件活或一个结果从一处交到另一处；红框 = 这一步在忙的地方。

Q22事件循环线程在我们的代码里体现在哪？

没有一行是“创建它”的。起点是启动命令（compose.yaml:124）：uvicorn margin.api:app --port 8000，uvicorn 进程的主线程就是它。之后能看到它的地方有三种：

  • 跑在它上面的：所有 async def。lifespan（api.py:43）、stream_events（201）、generate（233）、forward_deltas 和 pump（live.py:74、94）。asyncio.create_task(pump())（live.py:102）是在它上面再挂一个协程。
  • 在它上面让出的：每个 await。比如 api.py:231 查库、255 等收件箱、live.py:86 等 Redis 回复。
  • 直接拿到它的：只有 hub 里两处。asyncio.get_running_loop()（event_hub.py:62，意思是“正在运行我的那个事件循环”。watch 是在 generate 里调用的，所以拿到的就是它），以及 loop.call_soon_threadsafe(...)（78 行，hub 线程用它把活交回来）。

Q23那整个 api.py（包括初始化 hub）都是事件循环线程在跑吗？

代码在哪个线程什么时候

你的说法“这个文件由事件循环线程负责”作为大方向成立：文件是它加载的，每个请求都先到它这里，线程池和 hub 线程都是它派出去的。但具体到某个函数，要再问一句“它是 async def 吗？”。这个区别会决定代码写得对不对：

写法后果
普通 def 路由里 time.sleep(5) 或慢查询只占一个线程池线程，其他请求和 SSE 照常
async def（如 generate）里直接同步查库或 time.sleep(5)事件循环线程卡 5 秒，这个进程所有 SSE 全部停住
hub 线程直接调用 inbox.put_nowait跨线程改 asyncio 对象：可能没人被叫醒、数据可能改乱，所以必须用 call_soon_threadsafe

Q24叫醒事件循环的，是不是都是“网络通道来了数据”？Redis 不是缓存吗，怎么会操作 pump？

能叫醒事件循环的只有两类：

类别具体是什么
它盯着的某条连接来了字节浏览器连接（新请求、断开）；pump 的 Redis 连接（片段到了）；self-pipe（hub 线程或线程池写进来 1 个字节）
闹钟到点见 Q25

PG 那一路并不直接叫醒事件循环。PG 的通知连接由 hub 线程自己守着，不归事件循环管：

PG 通知 → hub 线程的连接来了字节 → hub 线程醒来 → 往 self-pipe 写 1 字节 → 事件循环醒来

Redis 不操作 pump，它只往连接里发字节。Redis 不是被 py 文件调用的库，而是一个独立运行的服务器程序（compose 里的 redis 容器），有自己的进程，这一点和 PG 一样。缓存只是它的一种用途；M2 用的是它的发布 / 订阅（pub/sub）：

① pump（我们的代码）连上 Redis，发 SUBSCRIBE run:5:live → Redis 记下“这条连接订阅了它”
② worker（我们的代码）发 PUBLISH run:5:live "…"        → Redis 把消息写进每条订阅连接
③ API 进程：pump 那条连接来了字节 → select 返回 → 事件循环跑 pump → pump 解码、放进收件箱（我们的代码）

比方：Redis 是广播电台，pump 是你家收音机。电台只发信号，收到信号后怎么播放，是收音机自己的事。PG 发 NOTIFY 也一样：PG 只往 hub 的连接里写字节。

Q25闹钟到点，是扫一遍待办吗？10 秒是固定值，事件循环怎么算睡多久？

每个连接的等待时长固定是 10 秒，但各个连接从不同时刻开始等。每次 wait_for(inbox.get(), 10) 都登记一个闹钟，记的是到点时刻 = 现在 + 10。事件循环把所有闹钟按时刻排在一个堆里，睡觉前只看最早的那个：

# asyncio/base_events.py 的 _run_once（简化）
if self._ready:           timeout = 0                                         # 有待办：不睡
elif self._scheduled:     timeout = max(0, self._scheduled[0]._when - now)    # 睡到最早的闹钟
else:                     timeout = None                                      # 没闹钟：一直睡到有连接来数据
self._selector.select(timeout)
while self._scheduled and self._scheduled[0]._when <= now:                  # 醒来：只把到点的挪进待办
    self._ready.append(heapq.heappop(self._scheduled))
  • 不是扫描：闹钟存在一个排好序的堆里，只看最前面那个。
  • 提前醒的情况：比如 108.0 时 A 的收件箱来了东西，A 那个 110.0 的闹钟就作废。等 A 处理完、重新开始等，再登记一个 118.0 的新闹钟。
  • 我们一直在用它：模型想得久、10 秒没有任何东西时，api.py:255 的闹钟就会响，于是发 ping、再兜底查一次库。
  • 还有别人的闹钟：uvicorn 的主循环每 0.1 秒 asyncio.sleep(0.1) 一次（检查是否该退出、更新日期头），所以事件循环最多睡 0.1 秒就会醒一下。看一眼没事，又接着睡，开销很小。

Q28后端往 Redis 里发的是什么？纯字符串吗？

是一个字符串，内容是按约定格式写的 JSON。中间的 Redis 和 API 都不解析它，原样往下传，最后由前端 JSON.parse。数据有两层格式：

层格式谁定的谁解析
外层SSE：id: / event: / data:，空行结束浏览器标准浏览器的 EventSource
内层data: 后面的 JSON：有哪些字段、各叫什么名字我们自己约定前端 JSON.parse

JSON 不是随手拼的字符串：json.dumps 会把引号、换行转义成 \"、\n。这一点很要紧，因为 SSE 是按换行分行的，正文里的真实换行如果不转义，会把一段消息截断。字段名在后端（live.py:58 的字典）和前端（timeline.ts 的 Delta 类型）各写一份，中间没有自动校验。两边对不上时，靠前端 e2e 测试拿录制下来的真实数据回放来发现。
